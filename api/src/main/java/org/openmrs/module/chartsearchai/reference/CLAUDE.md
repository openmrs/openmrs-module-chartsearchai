# Drug-safety API surface rules — do not bypass these methods

These rules bind the drug-reference and drug-safety subsystem. Most of that code is the
directory this file sits in, and not all of it: how a finding, a chip, an interaction-pair
extent or the reference slice reaches the answer and the wire is decided in
`LlmInferenceService` and `ChartSearchAiRestController`, and rules here bind those too.
They were split out of the root `CLAUDE.md` on 2026-09-06: that file is read in full at the
start of every session, and 77% of it was this one subsystem, carried by every session that
never touches it.

**Nothing guarantees this file reached you before you edit that code.** Whether a tool picks up a
nested instruction file on its own varies, and a session that greps and edits through shell
commands may never open this directory at all, so read this file in full before changing
anything here. The root `CLAUDE.md` carries the same instruction, because a rule that depends on
a lazy load is a rule that fails open.

What may be written here is governed by the root file's "Documenting a decision" section: the
directive belongs here, its evidence belongs in `docs/adr.md` or in the javadoc of the method it
constrains. Both files are held to that by `ProjectInstructionsGuardTest`.

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values. Where a bullet cites an ADR decision, that decision is canonical for the reasoning — including for alternatives already measured and rejected, which should not be re-proposed without new evidence.

## Text, names and folding

- **Diacritic folding**: Use `DrugReference.foldDiacritics()`; never `java.text.Normalizer` or a hand-rolled character map. **Fold once, where each operand is produced** (#330) — an entry's aliases in `setAliases` (`DrugReference.foldedAliases`, index-aligned with the raw list, derived in the sole writer and not memoised, which is why #172's rule does not reach it) and a scan's recorded name in a `DrugReference.FoldedName`, produced only by `DrugReference.fold`. Prose takes a folded `String` instead (`findByQuery` → `matchesFoldedText`), deliberately. **Never hand a folded string to an unfolded arity** — `foldedLower` is documented non-idempotent; the type prevents this for a recorded name but not for prose, so the one prose site (`DrugSafetyValidator.namesSubstance`) is held by a source guard. Do not merge `FoldedName` with `namedOccurrences`' `foldedLowerText` parameter — that one is prose folded under the prose rule, handing back positions into that exact string. Each boundary rule gets one named entry point per operand shape over one `foldedMatch` core; a CALLER must never choose an allowance of its own (#260). → ADR Decision 55; `FoldedOperandTest.everyAliasOfALoadedEntryIsItsOwnWitness` (its reach is the loaded data's — mutate the line and read the failures).
- **Matching a drug name**: three shapes, three accessors; do not swap one for another or widen one to serve another (#86, #128, #147). `DrugReference.matchesText()` for PROSE; `DrugReference.namedOccurrences()` when a caller needs WHERE a prose match sits (every occurrence with its span — one reported occurrence cannot answer #270's sub-span question); `DrugReference.matchesDrugName()` / `DrugReferenceService.findByDrugName()` / `lookupByToken()` for a clinician-entered drug NAME; `DrugReference.isNamed()` / `normalizeName()` for IDENTITY between two reference strings. **Never `String.indexOf` beside a `matchesText` gate** — that was #260, and the two disagreed in both directions, silently. RANKING those claims is a fourth question and `nameMatchStrength` is its one answer. → ADR Decision 52.
- **How strongly an entry claims a recorded name**: Use `DrugReference.nameMatchStrength()` — display name IS the recorded name, then another name IS it, then the earliest entry the name merely occurs INSIDE. Never re-rank by alias length or by preferring `canonicalRow`; both were measured and are worse. Since #209 this ranking also decides the candidate SET, through `findImpliedSubstances`. → #192; ADR Appendix A.

## Which candidates a string puts in play

- **Which candidates a recorded string puts IN PLAY**: `DrugReferenceService.findImpliedByQuery(text)` for PROSE, `findImpliedByDrugName(name)` for a recorded drug NAME. `findByQuery`/`findByDrugName` are the unranked primitives underneath and answer a different question. **Never build a chip arm's or the injector's candidate set by iterating `matchesText`/`matchesDrugName` yourself** — that was #209, where a chip named a substance the patient was not prescribed. `DrugReference.aliasesIn()`/`aliasesNaming()` are each their own boolean's witness and exist for this and nothing else. Both legs are needed together: the drug-in-play arm and the order-driven arm each skip what the other covered.
- **Which drug CLASS a question names**: `DrugReferenceService.namedDrugClass(question)` — a class NAME and never a member set, so it is not a third candidate-set accessor beside `findImpliedByQuery`/`findImpliedByDrugName` and a caller must never read its answer as putting substances in play (#354). Its vocabulary is `DrugClassTerms`, two INDEPENDENT sources unioned: the curated cross-reactivity groups' own `name`s, and a code table carrying a class that file cannot name, further SPELLINGS of one it can, and the class it does name — the last deliberately, so an operator's own groups file cannot lose it. **Never add a cross-reactivity group to make a word recognisable** — its `atcPrefixes` assert cross-reactivity and duplicate-class therapy — and never resolve a class to an ATC subtree, which was measured wrong in both directions for the reported class. The record it produces (`RESOURCE_TYPE_DRUG_CLASS_NOTE`) **names no member of the class**, because it is citable evidence — a rule binding the class NAME the note prints as well as the terms it is matched by. It closes by asking for a specific drug and **must promise nothing about what that resolves to** (false for a drug the loaded dataset does not carry); every clause of it is an imperative about the QUESTION or a claim about ENTRIES, because four wider sentences were written there and all four were measured false. Its words are pinned as a literal, so a fifth cannot be added by rewording. → ADR Decision 67; `DrugClassQuestionNoteTest.theNoteNamesNoSubstanceTheReferenceDataCarries`, `.aQuestionNamingAClassAndAResolvableDrugRaisesNoNote`, `.everyCuratedClassTermResolvesToNoSubstanceInTheShippedKnowledgeBase`, `.everyClassNameTheTableCanReportNamesNoSubstanceOfTheShippedKnowledgeBase`, `.theRenderedNoteIsExactlyTheseWords`.
  - **That record is prompt-facing, so the class is ALSO stated deterministically on the wire**: `ChartAnswer.getUnresolvedDrugClass()`, published as the `unresolvedDrugClass` response key. An injected record reaches a client only if the MODEL cites it, and on the issue's own reproduction it did not — nothing a `/search` consumer reads reported the class at all. Resolved ONCE per `LlmInferenceService` method by `ChartSearchAiUtils.unresolvedDrugClass(mappings)` off the POST-inject chart, so the key is non-null exactly when the prompt carries the note; **never re-ask `namedDrugClass` at a consumer**, which is not self-gating and knows nothing about `injectFromQuery`. `null` is the absence of a statement and never a denial. **The CLIENT contract carries the note's own two prohibitions** — README's `unresolvedDrugClass` section tells a client to render what the note STATES, and names the two refuted wordings it must not use (that the MODULE screens by substance; that naming a specific drug *would* be screened), because that rendered sentence is what a clinician reads when the answer does not relay the note, so a refuted wording is worse there than in the note. It must reach every surface carrying the answer — the ungrounded answer included, since the early `done` is what a user sees — so `ChartSearchAiRestController.putModuleStatements` composes `putSafetyChips` with it, and `ChartSearchAiUnresolvedDrugClassTest` fails the build on a second call to `putSafetyChips`. → ADR Decision 67; `LlmInferenceServiceUnresolvedDrugClassTest.aChartWithNoClassNoteStatesNoClassEvenWhereTheQuestionNamesOne`, `.searchStreaming_statesTheClassOnTheUngroundedAnswerTooAndNotOnlyOnTheFinalOne`.
- **Which substances a recorded drug name implies**: Use `DrugReferenceService.findImpliedSubstances(name)`. `lookupByToken()` answers exactly one row and is the primitive underneath — reaching for it directly is how a combination allergen ends up checked against a single constituent (#193) and how a presentation filed apart from its parent moiety produces no chip at all (#195), both silently and fail-closed. The widening lives here, in what the recorded *string* is read to name — not in `substanceKey` (identity), not in `nameMatchStrength` (ranking).
- **Which of the substances a recorded name implies it actually NAMES**: Use `DrugReferenceService.findNamedSubstances(drugName, implied)`, and ask it before PRINTING a substance's own label in a sentence reporting the patient's record. A strict subset of `findImpliedSubstances`, which is additive on purpose. Its equal-claimant leg admits a row on a rank TIE, which a combination the KB spells without a separator satisfies — and so does a row the chart never mentions (#268). **Never build a candidate set from it** (package-private for that reason): a caller resolving with it drops every substance a name implies without naming. Two PRINTING callers: `DrugSafetyValidator.addAllergyContraindications`, where a name does not name the row, its sentences state the relationship rather than asserting the allergy (#238); and `DrugReferenceService.substancesNamedByBridge` (#353).

## Substance identity and classification

- **Substance identity, and which row represents a substance**: `DrugReference.substanceKey()` / `substanceGroupKey()` for "are these rows one substance?"; `DrugReference.canonicalRow()` / `namesNoRoute()` / `namesItsSubstance()` to pick the row that names it. A substance has N rows in DDInter, so anything enumerating matching entries produces N of something unless it goes through these — #145, #162, #163, #174, #186, one defect in seven places. Identity is `drugbank_id` resolved **per substance-name family**, deliberately not `rxcui` or `rxnorm_name` (both shared by `Omeprazole` and `Esomeprazole`) and not the display stem alone (#187). `canonicalRow` has two rungs — route-qualification (`namesNoRoute`), then, for two rows of ONE substance tied on that, the row the data files the family under (`namesItsSubstance`). Do not compare display STEMS. Nothing pins their ORDER because since #250 nothing can. **A qualification COUNT over this fold needs its unit** — "elected rows answering `!namesNoRoute()`" and "elected rows whose raw name carries a trailing parenthetical" were one predicate before #250 and are two different families after it; mutate each and read the failures. For a chip's SUBJECT the two rankings compose in a fixed order in `DrugSafetyValidator.interactionSubject()`: `nameMatchStrength` first, then `canonicalRow` among rows tied on that (#194). Do not reverse it (#187) and do not call `canonicalRow` directly at a chip-subject site — one substance must not be named two ways in one response. → ADR Decisions 43, 56; `SubstanceNameRowTest.theSubstanceNameIsMatchedAgainstTheWholeDisplayNameAndNotItsStem`, `.noRouteQualifiedPresentationIsElectedToSpeakForItsSubstance`, `DuplicateTherapySelfChipTest.anOrderKnownOnlyByACodeTheRowItselfPublishesIsStillSkipped`, `SubstanceNameRowTest.aFamilyWithAnUnqualifiedRowElectsOneAndNoOtherRowSpeaksForIt` (guards a weakening of the PREDICATES, not a KB refresh — a data change reaches `SubstanceNameRowTest.everyFamilyElectingAQualifiedRowOverAPlainSiblingIsNamedRatherThanCounted` instead).
- **Whether an ATC subgroup may justify a clinical claim**: THREE predicates, chosen by **the claim you are about to make**. `DrugReference.isLocallyAppliedAtcCode()` separates the code classifying a SUBSTANCE from ones classifying a locally applied presentation — **a preference between candidates wherever the caller holds no evidence about which presentation the patient was given, which is every caller but one**. `DrugSafetyValidator.sharedClass` is that rule and still returns a locally applied subgroup where that is all a pair shares; `DrugReference.codesAtSites` (#234) may DROP a code, decided by `ATC_GROUPS_BY_SITE` against the order's own recorded route or dose form. A caller with no such evidence gets the preference and never the veto; adding a third caller means saying which of the two it is. `isUnclassifyingAtcCode()` is the DUPLICATE-THERAPY bar (a group asserting nothing at all); `isPurposeOnlyAtcCode()` is the CROSS-REACTIVITY bar and **subsumes** it. That ordering is what makes three lists composable. `sharedClass` takes the arm as a parameter and is the only caller of the latter two; **never ask one arm's question with the other's predicate** (#183).
  - **The two arms may legitimately name DIFFERENT classes for one pair. That is the settlement, not a defect** (#183/#184) — the preference among survivors is still one method (#171), but the candidate SETS differ, so naming them alike would make one of the two sentences false.
  - **The criterion, stated so it can be re-applied.** A subgroup licenses only the claim its own published NAME asserts, and a residue ("Other …"/"Various …") inherits its parent's assertion recursively — *unless it contributes a term none of its ancestors' names carry*. A name stating a chemical family, a derivative class or a molecular TARGET licenses both claims; one stating only an indication, an organism acted against, a therapeutic area or a diagnostic use licenses duplicate therapy alone; one whose ancestry is residue all the way up to a bare LEVEL-1 anatomical main group licenses neither. Level 1 and not level 2 — ATC's level 2 is its THERAPEUTIC tier.
  - **Derived from the index, never from the reported cases.** All 939 level-4 names in the WHO ATC/DDD index were read and the criterion applied to each. #161's list was hand-picked and its hardening found it incomplete in a way that reproduced the defect it was fixing (#263). Add a member only by re-deriving the criterion, and record the measured KB impact in the ADR.
  - **Do not re-propose a uniform ATC veto.** Measured and rejected on its own stated test; the decision carries the ratio and the classes the loss falls on. → ADR Decision 34; ADR Appendix A.
- **Which of a substance's codes describe the presentation the patient was GIVEN**: Use `DrugReference.codesForRecordedAdministration(codes, recordedTerms)`, reading the terms off the order — `PatientClinicalContext.ActiveDrugOrder.getAdministrationTerms()`, every name the order's route concept and its drug's dosage-form concept PUBLISH, never the drug's NAME. **Every name, through `PatientClinicalContextBuilder.addConceptNames` and never `addConceptName`**: `Concept.getName()` returns the locale-preferred spelling ahead of the fully specified one, so reading one name leaves #234's own defect standing silently. A term list is not a substitute — a vocabulary of site WORDS cannot reach a spelling that is not one. Do not widen `addConceptName` to do it (it would change which reference entries an ORDER's name reaches). `DrugSafetyValidator.codesForThisSubstancesPresentations` is the single production caller of it and of `narrowsAnyCode`, and that is the only place either belongs; do not apply it inside `sharedClass`, which compares two code sets for four callers. 
  - **The site table is a PARTITION of `LOCALLY_APPLIED_ATC_GROUPS`, not a list beside it** — `ATC_GROUPS_BY_SITE` plus `LOCALLY_APPLIED_GROUPS_NAMING_NO_SITE` account for all 17 prefixes, and `S` is expanded into ATC's own `S01`/`S02`/`S03`. 
  - **A term must name ONE site**: `cream`/`ointment`/`lotion` and `topical` are deliberately absent; Decision 50 says why of each. A term naming a route of ENTRY (`ROUTES_OF_ENTRY`) REFUSES the site walk rather than merely failing to match it. It **declines** — returning codes untouched — where no term names a site AND where the substance is filed under none at the site a term does name (both paths are the one `kept.isEmpty()` tail); for several orders of one substance the question is asked per order and of what the data can EXPRESS (`narrowsAnyCode`), never of what the terms merely NAME. It can remove CODES and never a partner. → ADR Decision 50; `UnmappedOrderAdministrationSiteTest.aRouteSpelledAsAnInflectionOfItsTermStillSelectsItsSite`, `.everyLocallyAppliedCodeInTheShippedKnowledgeBaseIsAccountedFor` (a DATA guard over the shipped KB, so a group absent from it still escapes), `ActiveOrderAdministrationTermsTest.everySpellingTheRouteConceptPublishesIsCarried`.

## Loading, caching and observability

- **What reference dataset is actually loaded**: Use `DrugReferenceService.getLoadStatus()` (or `GET /chartsearchai/drugreferencestatus`). Never re-read the global properties to infer it — the load is **lazy**, so a check made right after flipping a GP reads the *previous* source (#149/#154).
- **Memoising anything derived from `getAll()`**: hold it in a **per-call local, never in a field** — #172's rule, binding `DrugSafetyValidator`, `DrugReferenceInjector` and `DrugReferenceService` alike. **The reason nine comments once gave for it — hot-reload — is measured false**; `DrugReferenceLoadContextTest.loadStatusDoesNotDriftFromTheCachedEntriesWhenTheGlobalPropertiesChange` pins the static half, so read that rather than re-measuring. **Keep the rule; two TECHNICAL reasons hold today**: these beans are Spring singletons, so a field memo is one unsynchronized `HashMap` shared by every concurrent request; and SOME memos are keyed on something unbounded, so as fields they grow for the life of the JVM or answer for whoever asked first. Say which applies at a given site rather than reciting both — the second does not bind every site. A further reason, binding no site in particular, is why the discipline is worth keeping even where neither bites: a module whose memos are all per-call is one a reload path can be added to later without re-auditing every one. Do not extend the rule to `CrossReactivityGroup.setAtcPrefixes`, a production write path that must stay authoritative after a read. → `RecordedAllergenMemoScopeTest` pins ONE shape of it (a memo outliving the entries it was resolved from); a field REASSIGNED once per pass stays green on it, and a single-threaded case cannot observe the sharing that is the first reason above.
- **Whether a loaded dataset is VALID, and what the loader did about it**: Use `DrugReferenceValidity`, reported through `DrugReferenceLoad.getFindings()` for the ENTRY dataset and `CrossReactivityGroupsLoad.getFindings()` for the curated groups file (#266) — two loads, two sections on `GET /chartsearchai/drugreferencestatus`, never one findings list a reader cannot attribute to a file. **Never add a guard for one bad-data shape at its own call site**: #150, #156, #196 and #211 were four such shapes in one code path, and a guard apiece would give as many answers to what this loader considers valid. Rules binding anything added here:
  - **The remedy is decided per rule and never uniform by default** — drop the offending VALUE where the rest of the entry is usable, repair only what the data already says, otherwise report. No rule refuses a file: an additive net that refuses its dataset produces the inert safety layer #149 exists to flag.
  - **A rule must stay silent on an untouched default.** Both path GPs default to files the module never creates, so a rule keyed on "a path is configured and the file was not read" fires on every install. Compare against `ChartSearchAiConstants.DEFAULT_DRUG_REFERENCE_DATA_FILE_PATH` / `DEFAULT_DRUG_REFERENCE_CROSS_REACTIVITY_FILE_PATH`, pinned to `omod/src/main/resources/config.xml` by `GlobalPropertyDefaultsTest`.
  - **Resolve a dataset file through `ReferenceDataFiles`, never your own stream** — `loadWithClasspathFallback` where the module ships a copy, `loadOperatorFile` where it does not. A source opening its own stream has no collector, so it can raise nothing, which is exactly how `atc` came to have no validity channel. Stated over the READ and not over a fallback since #266: `sourceFormat=atc` bundles none, so `loadOperatorFile` reaches `configuredDataFileNotRead` with `ORIGIN_NONE` and that rule's detail branches on it — a load that read nothing in the named file's place must not be told its count "looks healthy". `DrugReferenceSourceValidityChannelTest` fails a source INHERITING `lastLoadFindings()`'s default and cannot see one that declares it and returns a constant empty list.
  - **Silence is the ABSENCE of a finding, never a muted one.** Every finding reaches both channels — the log at the moment it happens, and `toMap()` afterwards, carrying its rule, remedy and count. `toMap()` is never scoped. **What IS scoped is the log LEVEL, and only it**: `logTo(log, origin)` reports a DATA rule about the dataset the module SHIPS at INFO and everything else at WARN, because the default is a redistributed KB whose known defective rows no operator can fix. The list that may soften is `DATA_RULES`; anything unclassified is loud, and `DrugReferenceFindingLoudnessTest` fails the build on a rule left out of it. **Do not read this as "observable but not loud"** — that was tried for the mistyped-`sourceFormat` case and ruled wrong (`CrossReactivityGroupsLoad`'s javadoc carries why the log alone is the muted silence this file forbids), and #149 exists because a wrong load logged at INFO reads like a right one. A CONFIGURATION rule is loud wherever the entries came from. Never scope `toMap()`, and never widen the softening to a configuration rule. → ADR Decisions 36, 48.
- **Whether this install's contraindication screen had a CONDITION rule to ask**: `DrugSafetyValidator.conditionRuleCoverage()`, read off the answer as `ChartAnswer.getConditionRuleCoverage()` and published VERBATIM as the `conditionRuleCoverage` key (#378). Resolved ONCE per `LlmInferenceService` method and set on every answer it produces — the ungrounded early-`done` included, since that is what a user sees. **Never `Arm.HAND_AUTHORED_RULES` for this question**: that arm admits an `allergy` rule too, so its `published` states condition coverage an allergy-only dataset does not have — #378's own defect one install over. `Arm.CONDITION_RULES` asks `evaluatesConditionAgainstTheChart`, which CALLS `evaluatesAgainstTheChart` rather than re-expressing it, so the arm and the screen cannot drift. **Three values, and `unloaded` is not `absent`. Never gate this on the `drugSafety` toggles** — the verdict is the DATASET's, so a gate withholds it exactly where the arms are off; the decision records a refuted reason for the same rule, so read it before re-proposing one. **It says what the DATASET publishes and never what was screened** — a client rendering `published` as "conditions checked" is the failure the key exists to remove. **What it cannot speak to is enumerated in ONE place**, `ChartAnswer.getConditionRuleCoverage()`, and repeated for the client author in `README.md`; point at it rather than restating it. One spelling of a verdict, `DrugReferenceLoad.Coverage.wireToken()`, shared with `/chartsearchai/drugreferencestatus`. → ADR Decision 75; `ShippedDrugReferenceDefaultTest`, `DrugReferenceLoadContextTest.anAllergyOnlyDatasetServesTheUnionAndNotTheConditionLeg`, `ConditionRuleCoverageGateContextTest.theVerdictIsStatedEvenWhereTheContraindicationArmsAreSwitchedOff`, `LlmInferenceServiceConditionRuleCoverageContextTest`, `ChartSearchAiConditionRuleCoverageTest`, `ArchitectureGuardTest.everyAnswerThisModuleBuildsCarriesTheConditionRuleCoverage`.
- **How much of the prompt is this module's own reference material**: `ChartSearchAiUtils.referenceSlice(mappings)`, read off the answer as `ChartAnswer.getReferenceSlice()`; it reaches the audit row's `reference_slice_records` / `reference_slice_chars` (#229). Never re-derive it at a consumer, and never re-sum it inside `saveAuditLog` — by then the chart it measured is gone (#178). Resolved ONCE per `LlmInferenceService` method and the SAME object reaches every answer that method produces; `LlmInferenceServiceReferenceSliceTest` pins that by identity rather than equality, because two derivations over one chart are equal. **Null is not zero** and both columns are nullable for it: zero says the prompt carried no reference material, null says the producer stated no measurement. Zero says what the prompt carried and never why — so it is not evidence a corpus raises nothing, and the injector's log is what separates a swallowed failure from an honest miss. `ChartAnswer.getReferenceSlice()` is canonical for that; do not read its list of causes as complete. The neighbouring `input_tokens`/`output_tokens` do NOT follow this convention. It counts the reference GROUP, so `active_drug_order` records are outside it. **A hardcode inside `referenceSlice` is caught since #354 added the third reference type** — `ChartSearchAiReferenceGroupTest.everyDeclaredResourceTypeConstant_isCountedIntoThePromptCostSliceExactlyWhenItIsReferenceMaterial` reddens on it. `MAX_INTERACTION_RENDER_CHARS` is a per-record budget and deliberately not a bound on the NUMBER of records. → ADR Decision 57.

## Safety findings: strength, completeness and provenance

- **How strongly a finding licenses a clinical call**: `DrugSafetyValidator.licensesWithholding(SafetyWarning)` — of the FINDING, never of the rating alone (`ratingLicensesWithholding` is the weaker primitive) — and read its answer off the RECORD (the clause `renderFinding` appends), never by re-deriving it from the severity word in the prose. `minor` and `unknown` are cautions; `moderate`, `major` and **unrated** withhold, and unrated is not low-rated — `severityPriority` already sorts a curated rule above `major`. One definition, because the answer's strength and the chip's ordering must not disagree. The clause is **prompt-facing only**. The caution branch is **not a "Yes"** (#107 arm C): the graded lead states the drug can be given and names the caution, and `LlmProviderTest`'s never-"Yes" token stays pinned.
  - **Every finding the model reads states exactly one clause, and silence is not another answer.** A CONTRAINDICATION states a withholding-class clause; #283 scoped the clause to interaction findings once and that was measured wrong. An OVERDOSE finding cannot reach `renderFinding` today and wants NO clause; it falls to the empty default, **and that default is a defect waiting on a caller, not a safe fallback** — whoever makes the arm reachable gives it its own clause in the same change. → `SafetyFindingSeverityStrengthTest.everyInjectedFindingStatesExactlyOneStrengthClause`.
  - **STRENGTH and REFERENT are two axes** (#348). A finding about a medication the patient is ALREADY TAKING states the counterpart clause of the same strength; the referent is `SafetyWarning.isAboutACurrentMedication()`, **set by the arm and never read off the detail**, true only from the two ORDER-DRIVEN arms — and from the contraindication arm only where no SIBLING ROW put the substance in play, because its chips fold on the SUBSTANCE while its own skip is row-scoped. **Both arms or neither, both classes or neither, and a clause with no prompt branch quoting it is inert.** Neither branch may instruct a refusal or a permission — each opens by NAMING the medication, carries the prohibition on refusing, and may not borrow the PROPOSAL-caution branch's own permission lead, read off the paragraph rather than copied; a CONTENT rule and not an existence one (`SafetyVerdictSeverityGradationTest.assertCurrentMedicationBranch`, one mutation per half — but a permission in ANY OTHER wording only through `.theTwoCurrentMedicationBranchesAreExactlyTheseWords`). The ANSWER axis is measured, with one arm tried and refuted and three residues named. → ADR Decisions 72, 44; `CurrentMedicationFindingStrengthTest.everyFindingOnAScreeningQuestionStatesOneVocabulary`.
  - **A SET of findings states one lead, decided by the STRONGEST**, and the ranking must name the loser as well as the winner: the phrase `a reason to withhold it` occurs inside `STRENGTH_CAUTION` negated, so a bare antecedent is satisfied by a caution read shallowly. That nesting is of the class PHRASES, not of the clauses, and it is the only one the four have. Do not rest the lead on emission ordering, and do not word it as a fallback — `LlmProviderTest` fails the safety paragraph on the substring `otherwise` in any casing (#107 arm D). → `SafetyVerdictSeverityGradationTest.aSetOfFindingsStatingDifferentStrengthsIsLedByTheStrongest`, `.aSetMixingAProposalCallAndACurrentMedicationCallIsLedByTheStrongest`, `.theOnlyStrengthClassNamedInsideAnothersWordsIsTheOneDecision37Handles`.
  - **A FOLDED finding takes the stronger claim**, which is why the question is asked of the warning: #171's fold puts the class arm's sentence onto a rated rule's chip while `getSeverity()` keeps reporting the RULE's rating. `SafetyWarning.carriesUnratedRelationship()` carries the fold across.
  - **Which finding a TRUNCATED answer keeps is decided by the order the arm appends in, so order on the FINDING and never on the rating** (#346). The two pairwise arms rank on `severityPriority` alone; the drug-in-play arm is the one that FOLDS, so `DrugSafetyValidator.FINDING_STRENGTH_DESCENDING` asks `licensesWithholding` first and only then `severityPriority` — ordered on `getSeverity()` alone a folded Minor that withholds sinks below the cautions it outranks. Two stated limits, both deliberate: its unrated class-only chips trail its rule chips, and it sorts per drug IN PLAY, so a response carrying two subjects is not one ranked list. → `DrugInPlayFindingStrengthOrderTest`, and `DrugInPlayFindingStrengthKeyOrderContextTest` for the KEY ORDER — a folded `unknown` under a lowered floor is the one arrangement the two keys answer differently, so swap them and read its failure; `DdiDrugReferenceSourceTest.replacingAGroupsWinnerLeavesATiedPartnerBehindIt` is what pins the collapse's own half of the order now that severity decides the rest.
  - **The graded lead is a THIRD verdict class, and any gate reading the answer's lead has to know it.** `caution_led` lives in `eval/drift-metric/score_probe_safety.py` and never in `score_directness.classify`, the locked metric for the directness gate. Counting the lead without `unsupported_caution` beside it is fail-open; so is counting it into `verdict_led` without the A/B comparing the CLASS. **The lead is ANCHORED on the cell's own drug and nothing but name material may stand between that and the modal**, two rules neither subsuming the other. **The marker list is gone; do not reintroduce one.** A cell with no drug scores false. Whether the RATING licenses a caution is deliberately not checked — that is `licensesWithholding`, and a second copy in Python is the drift `adverse_finding` refuses. A shape that evades the anchor is a new case in `CAUTION_LEAD_CASES`, not a looser anchor. → ADR Decision 37 for what each rule was measured to hold; `eval/drift-metric/fixtures/probe-safety/caution-over-major/`.
  - **Pin the PREMISE, not the conclusion, and do not let that guard look better defended than it is.** `SafetyFindingSeverityStrengthTest.theTypeThatStatesNeitherClauseCannotReachTheRendererBeforeThereIsAnAnswer` reddens when the dose arm becomes reachable from the injector. `.everyInjectedFindingStatesExactlyOneStrengthClause` does NOT, because it iterates the findings ONE fixed arrangement produced and no arrangement of `injectRecords` produces an overdose finding. → ADR Decision 37.
- **Which of this patient's own orders a finding says its substances came from**: `DrugSafetyValidator.chartOrderBridges()`, read off the warning as `SafetyWarning.chartOrderBridges()`, rendered by `DrugReferenceInjector.chartOrderClause` off `FINDING_CHART_ORDER_LEAD` — what makes a brand-named prescription's finding citeable (#349). **One shared method, called at each arm's chip-wording site and never re-derived by the injector** — a second walk is the two-resolutions-that-agree shape #151 forbids. Not decided inside `interactionWarning`, which takes the list as a parameter, so each call site needs its own case — neuter one and read the failures. A RESOLUTION and never an identity, so it states no class membership of the prescription; #339's rounds 5-6 do not reach it.
  - **The SUBJECT is attributed against every order; the PARTNER only against the orders its own arm let witness it, and the CALLER supplies that set.** `addActiveOrderPairInteractions` hands `ordersOtherThan`; `addInteractionWarnings` hands the whole list.
  - **The order's own silence test is the one name a chart record DISPLAYS (`displaysANameOfAny`), never every name it RECORDS nor the string the chip prints** (#347), and no longer `resolvesFrom`'s name leg negated; its javadoc has the residues.

  - **An order the module could read no name for bridges nothing** — through `displayNamesADrug`, which since #349 also asks whether a display is worth PRINTING beside a name that stays.
  - **Prompt-facing AND published, as each chip's `chartOrderBridges` (#347)** — VERBATIM, so the accessor's name IS the key. `StatedInteractionChips` must still NOT key on it, whoever can read it. → ADR Decisions 64, 70; `ChartSearchAiSafetyWarningSeverityWireTest`, `ChartSearchAiChartOrderBridgeTest` (STRUCTURAL).
- **Whether a reported interaction list is COMPLETE**: `ChartAnswer.getPairChipExtent()` (the wire's `interactionPairs`), stated by THREE arms through the `PairChipExtent.Sink` that `LlmInferenceService` hands `DrugSafetyValidator.validate` — never re-derived at a consumer, and **never inferred from the chip count**: `getReported()` counts above-floor rule PAIRS while `addInteractionWarnings` raises `interaction` chips of its own into the same list. 
  - **The two PAIRWISE arms speak first and are never summed with the third** (#356), which states `of(n, n)` only where neither of them did. 
  - **What it counts and what it does not**: this arm's rule chips for the substances the QUESTION put in play — unrated rules included, `clearsSeverityFloor` exempting them — and never its unrated class chips (neither pairwise arm has a class leg) nor a chip raised for a drug only the ANSWER named, an extent over `inPlay` being #336's defect reversed. A chart recording no active medication states nothing, unlike the screening arm's `of(0, 0)` there. 
  - **Zero is a measurement and absence is not** — `found == 0` says an arm ran and related nothing; `null` says the producer stated nothing. Never read `null` as completeness. 
  - **A pairwise arm a cede leaves with no pair states nothing, never zero** (#336, #370) — one rule on both, read as KEPT NONE having ceded at least one, and recorded AT the cede since not every skip is one. Nothing stands behind the screening arm, so its `null` reaches a client; never widen the #356 fallback to rescue it (Decision 65). 
  - **Published once**, on `validate`'s normal return, from a local the three arms assign — never per arm. The statement is a COUNT and never the withheld list, and must reach every surface carrying chips: `ChartSearchAiRestController.putSafetyChips` writes both keys, and `ChartSearchAiInteractionPairExtentTest` fails the build on a second write of the `safetyWarnings` KEY. A synthetic chip is refused (it would reach the prompt with neither strength clause and break `getType()`'s three-value contract). → ADR Decisions 60, 65, 69, 71; `PairChipExtent`'s class javadoc for what `null` covers; `PairChipExtentContextTest.aDrugInPlayScreenThatRelatesNoActiveOrderStatesZeroRatherThanNothing`, `.aDrugOnlyTheAnswerNamedStatesNothingOnItsOwn`, `.aDrugTheAnswerAddsIsNotCountedIntoTheQuestionsOwnScreen`, `.aClassOnlyRelationshipIsNotCountedAsAPairFound`, `.aScreenThatCededEveryPairItRelatedStatesNothingRatherThanACompleteScreenOfNone`.
- **Whether an injected record may state what THIS patient's chart records**: FOUR questions, four predicates; conflating any two produces a confident false statement in citable evidence (#208 item 2).
  - **Does the chart record it?** `DrugSafetyValidator.recordedContraindicationKind()` — the chip arm's own match, shared and never copied.
  - **Could the module even ask?** `DrugSafetyValidator.evaluatesAgainstTheChart()`; its token half is the matcher's own emptiness rule (`PatientClinicalContext.matchableToken`), extracted from `containsToken` so "not matchable" and "did not match" cannot drift.
  - **Was the chart read at all?** `PatientClinicalContext.contraindicationRecordsRead()` — **a chart the module could not read is not a chart that records nothing.** The builder swallows a failed allergy or condition read into an EMPTY set: right for a chip, wrong for a record that would then tell the model this patient records none of a drug's contraindications *because nobody looked*.
  - **Does anything CORROBORATE that match?** `DrugSafetyValidator.corroboratedByTheChart()`, the UNION of `aMatchedRecordNamesTheEntry()` and `allergicSubstanceKeys()` (#269) — one spelling both injected channels ask since #308. **Neither half is right alone; they fail in opposite directions and the union is MONOTONE.** That union is the ALLERGY answer, scoped to a self-named rule as the chip's demotion is — mutate the scope out and read the failures. A CONDITION rule takes a third leg, `aMatchedConditionCarriesTheToken`: a word BOUNDARY, since no arm resolves a condition to a substance (#309). The CHIP still states it unqualified; never tighten the match to fix that (fail-open).
  - **The composed gate** is `DrugReferenceInjector.statesTheChartsContraindicationReading`, which also requires `DrugSafetyValidator.reportsContraindications()` (both `drugSafety` toggles) because the reading is the record's half of a chip and must not outlive one, and is decided ONCE per injection so two records of one chart cannot disagree. **The remedy is a THIRD named section that asserts nothing about the patient, never a denial** — and its lead states what the MODULE established rather than a categorical about the chart, because a leg can miss a record that really does name its subject. `DrugReferenceInjector.FINDING_UNCORROBORATED_MATCH` is appended by `renderFinding` off `SafetyWarning.restsOnAnUncorroboratedChartMatch()`, set from this same predicate — a second copy there is how the two records would come apart again, silently. **Do not read that as licence to move the strength**: what Decision 42 deferred, and #308 took, is PROVENANCE, not strength. Never silence either. **The rule under all of it: never render silence as denial, and never render an accident as the chart's own words.** A negative claim needs the three chart-reading answers; a POSITIVE one needs the first, third and fourth (never the second — a matched rule is evaluable by construction); a chip needs only the first. → ADR Decisions 42, 73.

## Contraindications and chip scoping

- **Which collapse unit a contraindication rule is on**: `DrugSafetyValidator.contraindicationFinding()`, and `selfNamedAllergyRule()` for the one question the key turns on. A rule's key is its normalized `(type, token)` — **except** an ALLERGY rule whose token is one of the subject entry's own names, which reports the allergen arm's fact and is keyed on the SUBSTANCE so the two fold into one chip (#146). Which wording survives is decided by CONTENT and never by arm (#88 settled that "arm X yields to arm Y" is the wrong dedup whenever the yielding arm can carry the content). The chip ledger (`ContraindicationChips`) and `DrugReferenceInjector.contraindicationSections` key on that unit precisely so one recorded allergy cannot be one chip and two clauses (#190 item 1).
  - **A note is necessary and NOT sufficient** (#223). The fold's premise is that such a rule reports the allergen arm's fact, and `PatientClinicalContext.hasAllergyToken` is bare containment deliberately. So `contraindicationRank` asks a second question, **of the RECORD rather than the whole list**: it takes the witnesses (`allergensMatching`, sharing the boolean's own primitives so the two cannot drift) and puts each to the entry through `matchesDrugName`. A rule none of its matched records names is `SELF_NAMED_RULE_MATCHED_BY_CONTAINMENT_ALONE`, below `IDENTITY` — still raised, since the arms fire on different evidence. Ask it per witness and against the ENTRY.
  - **Tightening the MATCH instead was measured and declined** — it trades a false positive for a false NEGATIVE in a safety net, all its losses on the CLASS token `penicillin`, and makes one property structurally unconstructible.
  - **The self-naming test is `DrugReference.isNamed`, never `findImpliedSubstances`.** Both operands are canonical REFERENCE strings, so the question is name identity; a curated token may name a CLASS (`nsaid`), and resolving tokens to entries wholesale collapses a class-level rule into an identity chip (#160). What bounds the fold to its own subject is not the predicate but that it is asked OF the entry the rule is filed on.
  - **Since #308 the corroboration answer (`DrugSafetyValidator.corroboratedByTheChart`) over that unit has two spellings that must move together** — `contraindicationSections`' MAX for the record and `addContraindications`' fold for the finding. Deliberately not unified, and deliberately over the SAME unit. **The unit is TWO stages, not one**: after the key, the record resolves its three sections over clause TEXT, since two rules of different keys may render one string. **And that stage is asked of TWO strings** — `contraindicationClauses` JOINS the distinct notes a key collapses while a finding prints the winning rule's note alone. There is **no** third conjunct reading the key fold at that read site, and its absence is deliberate. What the map's OR still decides is which rule of a key carries it. Resolving it in `ContraindicationChips` instead is wrong twice: that key is the SUBSTANCE, and the gate skips rules before they arrive to be folded. **One unit buys agreement about one ROW, not about one substance** — a sibling row's sentence can replace the rendered row's and bring its own corroboration answer. → ADR Decision 44 (both directions, one case each); `UncorroboratedFindingProvenanceTest.aClauseAnotherKeyOfThisEntryStatesAsRecordedIsNotHedged`, `.theWordsTheFindingPrintsAreNotHedgedWhereAnotherKeyStatesThemAsRecorded`, `.oneCorroboratedRuleOfACollapsedKeyClearsTheClauseForTheWholeKey`, `.aRuleTheSubjectMatterGateSKIPSStillCarriesItsClausesCorroboration`.
- **Whether an ORDER-DRIVEN contraindication chip may be raised at all**: the active-order arm is scoped to what the RESPONSE is about, and `DrugSafetyValidator.SubjectMatter` is the only thing deciding it. A chip is raised where either SIDE is in subject matter — the drug (`names(DrugReference)`) or the recorded finding the rule fired on (`names(Contraindication)`, asked of the rule's OWN token and never the patient's whole list) — plus three widenings read off the question through `QueryScopeRouter.asksAboutMedications`/`asksAboutAllergies`/`asksAboutConditions`. Three and not two, and asked per LIST: the recorded side is an allergy OR a condition, and a conditions question must not widen her allergy records as well, or the three collapse into "asks about her chart". 
  - **Do not re-widen it to "every active order on every question"** — that was #143's over-reach and a category error: this module answers questions and has no subscription, acknowledgement or unprompted delivery path, so an unconditional finding here is an alert with none of an alerting system's machinery (measured live: four different questions returned the same two chips byte for byte). Do not narrow it either — to the drug side alone loses a chip whose ALLERGY was what was asked about; to a topic-intent gate loses `Can I give her bupivacaine?`. What is deliberately given up is announcing a prescribing error nobody asks a drug-shaped question about; that belongs on a surface with acknowledgement. 
  - **Its corpus is the CITED records and must never be the echo test's** (#360): those two were one list until the echo test widened to take in the RECITABLE reference records uncited, and an injected record names the patient's own prescriptions — so a shared list makes her prescription subject matter on a question about her cancer, which is the gate's DRUG side. It exposes the FINDING side too, a note-less rule rendering its token verbatim into the record's clauses, and nothing pins that half. `DrugSafetyValidator.AttributionTexts` allocates them separately for that reason; alias them and read the failure. → `ActiveOrderContraindicationTest.aPrescribedAllergyIsNotRaisedWhereTheResponseIsAboutSomethingElse`, `SubjectMatterScopedContraindicationTest.anUncitedReferenceRecordNamingHerPrescriptionIsNotSubjectMatter`.

## Active orders and co-medications

- **Which reference entries the patient's ACTIVE ORDERS are**: `DrugReferenceService.findForActiveOrders()` — ATC ∪ name ∪ each order's own CONCEPT (#353: `findByBridgedConcept`, RANKED, asked alike by `DrugSafetyValidator.resolvesFrom`, never a leg in `hasActiveDrug`), and the one list every consumer takes. `findByActiveOrders` is the ATC-only primitive underneath and answers a different question — *which of those orders did a DICTIONARY map to ATC* — which is not a slightly smaller answer but one that can be **empty**; the sparsity is the dictionary's, never the reference data's. It is package-private for that reason: do not widen it back, and never build a candidate set from it. That admission was #151: the injector resolved the primitive while `validate` screened the union, so the two layers disagreed about which orders the patient HAD — **silently, and in one direction**, the symptom being a Major chip whose supporting reference record was not in the prompt. **The remedy is not two resolutions that agree**: wherever a caller already holds the resolved list, pass it down rather than resolving again. Since #255 that is taken for the PRE-ANSWER pass too — a PARAMETER and never a memo, so #172's constraint is met by the shape rather than by discipline. What travels is the INPUT and deliberately not the enriched CONTEXT. **The POST-ANSWER resolution stands and is a different question.** The list is **unmodifiable**, and that is a contract rather than caution: since #255 the list one caller holds can be the same object another reasons over. → ADR Decisions 58, 53, 68; ADR Appendix A.
- **Which co-medications the class arm reasons about**: `DrugSafetyValidator.CoMedications` — **the per-pass memo, never `orderPartners()` directly** (#256) — and its answer is the patient's **whole** active-order list, never the subset a concept dictionary happened to classify. That second leg is #228 and is not optional — the arm was blind on the MAJORITY of prescriptions, silently. Two rules bind anything added here and **each was a defect that shipped green**:
  - **The exact-code leg of the restating-existing-therapy skip applies ONLY where the partner's codes are the CHART's** (`OrderPartner.codesFromDataset`). On a partner reached by NAME the codes are the DATASET's, so the leg would ask whether two reference rows share a code — which this KB says is not identity, and is why `substanceKey` exists. Unscoped, it silences exactly the chip #228 adds.
  - **The cross-leg dedup is `alreadyACoMedication`, never a map lookup**: the walk keys some partners on the ORDER and some on the SUBSTANCE, so a substance-key lookup cannot see the first kind.
  - **Resolved ONCE per `validate` pass, lazily** — a question putting no substance in play resolves nothing, and an eager hoist would make the commonest question slower. `CoMedications` carries a memo for each dataset resolution a pass would otherwise repeat; do not read the list of them as a list to keep, read it as the rule. `entryForAtcCode`'s cache is held for the PASS because `ruleAbout` asks it again after `orderPartners` has finished. **The sweep has a name of its own, `sweepForAtcCode`, and that is what makes the guard checkable** — while it and the pass-memoised `entryForAtcCode` were two arities of one name, dropping the `cache` argument reinstated a full `getAll()` walk with the suite green; under two names that mutation does not compile. Never call `sweepForAtcCode` outside `entryForAtcCode(String, Map)`. **And the cap is not the lever**: `maxPairChips` bounds chips and not work, and an early stop would change which pairs are dropped (#131). → ADR Decision 54, ADR Appendix A; `CoMedicationResolutionPerPassTest` (pins the sweep invariant, and structurally the bean's whole FIELD BUDGET off `getDeclaredFields` — a `static final` COLLECTION counts as that one mutable field too).
- **Which partner a rule is about**: `DrugSafetyValidator.activeOrderEntryFor()`. Both surfaces that group per partner — `bestRulePerPartner` for the chip, `DrugReferenceInjector.onePerPartner` for the record — key on the ACTIVE-ORDER entry it resolves, falling back to the case-folded `partnerLabel` for the dataset tail (#190 item 2). Do not key either on the label alone (two names of one order become two notes beside one chip — `warfarin`/`coumadin`, #136), and do not resolve a partner across the whole dataset instead (#188). The bound is what makes this safe: resolution is against the patient's own orders, so wherever it merges two labels the chip merged them first. → ADR Appendix A.
- **Whether a co-medication IS the drug being asked about**: the restating-existing-therapy skip in `DrugSafetyValidator.classRelationships`, TWO tests OR-ed with neither removable. Substance identity is the question — `substanceGroupKey()` against `OrderPartner.substances` — because deciding it by codes alone was #185. The shared-exact-code leg stays beside it for the case identity cannot reach, and since #228 applies ONLY there: a context carrying only the flattened code set (#118) has no order to name the partner, so the code is all there is, and dropping the leg raises a chip this arm has never raised. `resolvesFrom`'s javadoc explains why the same over-skip is safe THERE and does not transfer here.
- **What a co-medication is known to contain**: `OrderPartner.substances`, populated on exactly ONE rung — inside `orderPartners`' `unnameableCode && order != null` branch, over EVERY order `ordersCarrying` returns rather than the first. **Both halves of that scoping were got wrong once each and both mistakes passed the entire suite.** Widening it to every partner an order produced silences a chip that NAMES one; narrowing the read to the partner's own naming order, or to the first carrier, makes a suppression depend on the sequence `OrderService` returned the prescriptions in. **Since #339 it also decides which chips are NAMED** — `CoMedications.partnerNaming` indexes a co-medication under every key in this set — so narrowing it for a silencing reason silently moves chip NAMES too, and the two properties are pinned by different cases. Read through `findImpliedByDrugName` and never the unranked matcher underneath (#209). → `DuplicateTherapySelfChipTest` (silencing); `OneOrderNameAcrossOneResponseTest.twoRulesAboutOneCombinationPrescriptionNameItOnce` (naming).

An active order the module can read no name for still reaches the per-order list; skipping it left its codes in the flattened union with no order behind them, so ONE prescription became a duplicate-therapy chip per uncovered code (#290). Its display is its own codes labelled as codes and its `names` set is **empty**, deliberately: that set is matched against chart prose, so a code in it would match free text — the cost being that this order class is uuid-only for the #118 reconciliation. 
  - **Ask before letting a display DISPLACE a name another source supplied, never before merely labelling something that has no other name** — and since #292 the question is `DrugSafetyValidator.displayNamesADrug(order)`, **two conditions neither of which is sufficient**: that the order answers `hasKnownName()` AND that its display is non-blank, because a blank display resolves to the bare ATC code, which is the absence of a name displacing one. `nameByOrder` asks it **of itself**, and since #298 the order-rung constructor does too, so no caller supplies the answer; what must not ask it is `recordNameSource`, which derives the name source from the flag. Never re-derive the question as "are its names empty" — a proxy the public constructor lets a caller falsify, silently losing a real drug name. `orderCarrying` prefers a carrier answering true, and falls back to the first only where NO carrier does, because then there is nothing better to pick — so two unnameable orders sharing one unnameable code stay list-order dependent, which no test covers. → ADR Decision 40.
- **Which of an entry's interaction rules the injected record renders, and in what order**: `DrugReferenceInjector.renderTier` — THREE segments, one predicate, and the only expression of that partition. Promoted (the chart names the partner and the rule clears `DrugSafetyValidator.configuredSeverityFloor`), then the rules the chart names that the floor FILTERED, then the dataset tail. `promotedCount` counts the first and `OrderedInteractions.chartNamedCount` the second, so `render` tells all three apart.
  - **Never re-express relevance as the floor.** One predicate answering both questions is what silenced the patient's own drugs while rendering the same "listed but unrated" sentence for strangers (#357). And never promote on relevance alone, which was measured and rejected — the comment in `orderedInteractionNotes` carries that measurement, and says which half of it this change does not cover.
  - **Each segment has its own rendering rule and they are not smaller versions of each other.** A PROMOTED note takes the segment-1 slot the budget yields to, and its full text while the budget allows (one that will not fit has always rendered compact). The FILTERED segment states the source's shared sentence on its first note and names the rest with their ratings, because that sentence does not vary between members and full-for-every-member spends the budget saying one thing. The dataset TAIL keeps its own representative behind both, keyed on "anything patient-specific was shown" and never on the promoted count alone, or the breadth it exists to supply is unreachable for exactly the patients it was written for. **That question has ONE name, `OrderedInteractions.nothingPatientSpecific()`**, read by `render` to decide whether the tail is CAPPED and by `orderedInteractionNotes` to decide whether it is SORTED: never re-derive `promotedCount + chartNamedCount` at either site, or a maintainer changing what `tailStart` counts — as #357 did once — has to remember a condition in another method. Its javadoc carries what that drift actually reddens, which is not nothing.
  - **`onePerPartner` reads the same tier**, so the collapse cannot discard the row that decides which segment a partner lands in — asked at BOTH boundaries, not just promotion's. Across tiers it can elect a LESS severe row, deliberately.
  - **Where NOTHING is patient-specific the tail IS the record, so it names up to `MAX_TAIL_PARTNERS_WHEN_NOTHING_PATIENT_SPECIFIC` partners in the compact `name (Severity)` form, most severe first** (#355) — not in full notes, which is the prose the model recited, and not in dataset order, where the cap evicts the entry's worst partner. `SEVERITY_DESCENDING` asks whether a note NAMES its partner FIRST, so a rule with no name to shorten to cannot take the one slot the budget cannot refuse; `InteractionNote` takes the RULE, never a precomputed flag. **Guard that key over the SHAPES `partnerLabel` distinguishes — the product of {absent, blank, non-blank} over the two fields its `firstNonBlank` reads — never one case per substitution, and assert every cell of that product is FILED rather than that every filed cell is asserted**; `InteractionNote.namesItsPartner`'s javadoc carries why, and what the matrix does not reach. → ADR Decision 66; `InjectedInteractionRelevanceOrderTest`, `InjectedInteractionRelevanceOrderContextTest` (the floor boundary is the CONFIGURED one, which the shipped floor cannot show), `DrugReferenceInjectorTest.aSubFloorInteractionIsNotPromotedEvenWhenThePatientIsOnThatDrug` (whose assertion #357 replaced, deliberately — the decision records it), `.withNoPatientRelevantPartnerTheDatasetTailStatesBreadthCompactlyMostSevereFirst`, `.aTailRuleWithNoPartnerToNameDoesNotDisplaceOneThatDoes`, `.everyRuleShapeThatNamesAPartnerLeadsANamelessParagraphAndEveryOtherShapeTrailsIt` (the shape matrix; the five single-substitution cases beside it are not subsumed by it and one of them, `.aNamelessRuleCarryingASeverityStillDoesNotDisplaceARowThatNamesItsPartner`, is what holds a re-derivation reading the SEVERITY).

## Naming a partner in a response

- **The words an interaction chip puts between its subject and the active order it names**: `DrugSafetyValidator.ACTIVE_ORDER_INTERACTION_PHRASE`, spelled out once and read from there. Since #377 `ActiveOrderCitationFidelityCheck` recognises that same claim in an ANSWER, so the renderer and the recogniser are one string. Re-inlining the literal breaks nothing the day it is done — the spellings are equal, measured — and that is the hazard: it removes the coupling, so a later edit to either side diverges with the suite green. → `ActiveOrderInteractionPhraseTest.theRenderedPhraseIsSpelledOutInExactlyOnePlaceInProduction` (a SOURCE scan over `api/src/main`, blind to a second phrase spelled differently); ADR Decision 76.
- **Naming an interaction partner**: `DrugSafetyValidator.partnerLabel()` — the rule's own match token, else its ATC code — is the GROUPING key for every rule chip (`SubjectRule.partnerKey`, `DrugReferenceInjector.onePerPartner`), not for a class-only chip, which is labelled by the ladder and always was. **Since #339 it is no longer what most rule chips SAY.**
  - **A RULE chip's rendered name is `DrugSafetyValidator.reconciledPartnerName`**, for EVERY rule chip in both active-order arms (#292's scope was the folded chip alone). This label survives only where that method declines. `CoMedications.partnerNaming` has three rungs — the ladder's `labelEntry`, `OrderPartner.substances`, and the co-medication this pass attributed a CHART-recorded ATC code to — because ONE prescription can resolve to two reference substances with a partner keyed on only one. The third rung asserts no identity; `unambiguouslyNames` still decides whether the name may be printed.
  - **A CLASS-only chip's name — and the class sentence of a folded chip whose arms did not reconcile — is `DrugSafetyValidator.classPartnerName`**: the ladder's label with ONE thing re-decided. Asking the row question at the rule chip alone was measured to be half a migration.
  - **Which ROW either of them displays is a second question and its answer is `SubstanceSubjects.subjectOf`, never the ladder's own election.** The ladder elects with `canonicalRow` alone; every other name slot elects with `interactionSubject`, and taking the ladder's answer at a chip site is #187. The ELECTION moves only the ENTRY rung — a label an ORDER supplied has no row to elect, and a bare code or `[ATC …]` is the absence of a name (#155/#290).
  - **Nothing else about that label is re-decided. On the ORDER rung the DISPLAY stands, and #339's rounds 5–6 tried to re-decide that and were reverted.** Every other name available there is a CONSTITUENT of a prescription the dataset cannot fully name, while `classRelationships` cites the shared subgroup over ALL of the partner's codes — so naming a constituent states a class membership false of the drug named, in text `renderFinding` copies verbatim into a citable `safety_finding` with `STRENGTH_WITHHOLD`. **Do not re-propose a second conjunct there**; the decision records what the reverted rounds bought (a legibility reading), what they cost, and that the refusal also made a prescription's name question-dependent. → ADR Decision 63.

That fallback is not cosmetic — electing alone turned a permit into a refusal and printed two names in one folded detail. **A contested token is admissible only at `NAME_IS_THE_DISPLAY_NAME`**, and the alias trim #296 added is load-bearing: untrimmed, `isNamed` and `matchesDrugName` disagree and the fold refuses what its gate admits.
