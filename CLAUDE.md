# Rules

- When a test fails, fix the pipeline/production code — never weaken assertions, revert test data, or change expected values to match wrong behavior.
- Prefer root-cause fixes over incremental symptom patches. Diagnose *why* something is broken before proposing a fix. Start with the best solution, not the quickest.
- Before claiming a filter is correct, verify what it RETURNS — the records, not the count or the final answer. A filter returning 32 irrelevant records is not correct even if the LLM answers rightly from them.
- Do not analyze in circles without fixing.
- Tests must call the actual production pipeline — no simulations, mocks, or reimplementations of pipeline logic in test code. This includes unit tests for internal methods: do not call them directly with hand-crafted inputs. Every test must exercise the full production path using real data (the patient test datasets, the real querystore-backed retrieval).
- **Never re-express a production predicate in a script that measures the knowledge base for a figure you will quote** in javadoc, a PR body or an issue. Compile against the built jar or drive the real code through a throwaway test, and say which method produced any figure you record. `substanceKey`, `normalizeAtcToken`, `isLocallyAppliedAtcCode`, `containsBoundedToken` and `canonicalRow` carry accumulated special cases a fresh implementation quietly drops, so a script that is 98% right produces plausible numbers that are wrong in exactly the tail being investigated (measured 2026-08-07 — a Python reimplementation of `substanceKey` disagreed with production on family counts; #191).
- **Quote the figure the system already recorded, and where you must derive one, say what produced it and what it is a share OF — wherever it is published, a page or a report included.** #243 records the knowledge-base form of this.
- When a multi-step pipeline exists (e.g. normalize → transform → embed), tests must call the composed production method, not manually chain the individual steps. Manually chaining steps in tests can mask bugs where the production code assembles the pipeline differently. If no composed method exists, extract one and use it from both production and test code.
- Tests are the specification. Modifying tests to make them pass is changing the spec — only fix the production code to satisfy the existing tests.
- Before presenting changes, review your own diff multiple times. On each pass, check every item below. Keep reviewing until a pass finds nothing to fix.
  1. Does the change match the plan?
  2. Is the logic correct — edge cases, off-by-one errors, null/empty handling?
  3. Are there any regressions — does existing behavior stay intact?
  4. Is anything missing — incomplete implementation, forgotten call sites?
  5. Does it use the real production pipeline, not a simulation or mock?
  6. Were any tests weakened to make them pass — assertions loosened, test data reverted, expected
     values changed? If so, that's the "tests are the specification" rule above; revert and fix
     the production code instead.
  7. Were all rules followed — this file's, and those of every nested instruction file
     covering code the change touches?
- Follow test-driven development: for every bug fix or new feature, first write a failing test that defines the expected behavior, then write production code to make it pass. Write the strictest assertion — if it doesn't fail, tighten it until it does.
- Always create a plan before writing code. Read the relevant code, outline the approach, then implement.
- Never commit code with known regressions. When a change fixes one case but breaks another, the root cause is usually in shared infrastructure, not the individual call site — diagnose the shared problem before patching stages.
- Retrieval is owned by openmrs-module-querystore (issue #51). chartsearchai no longer has an in-process embedding/Lucene/Elasticsearch pipeline, scoring/ranking code, an embedding store, or a retrieval eval harness — do not reintroduce them. Retrieval changes *and retrieval-quality evaluation* belong in the querystore module, not here.
- **Keep Bash output scoped — it is context, and the tail dominates.** Never `cat` a file you are about to grep; scope every recursive grep to `api/src`/`omod/src` and never to `.`; report a build as its FAILURES plus a computed total rather than every `Tests run:` line. **This rule does not reach reading production code** — file-region reads are where the findings come from. Trim the overhead, never the reading. → ADR Appendix A.
- **The local-LLM subprocess rules are NOT in this file either.** They are in `api/src/main/java/org/openmrs/module/chartsearchai/api/impl/CLAUDE.md`, beside the code they bind. Read it before changing how this module addresses, authenticates or starts the `llama-server` subprocess.
- **The drug-reference and drug-safety rules are NOT in this file.** They are in `api/src/main/java/org/openmrs/module/chartsearchai/reference/CLAUDE.md`, beside the code they bind. Read that file in full before changing anything in that directory. Do not wait to be handed it: whether a tool loads a nested instruction file on its own varies by tool and by how the files are reached, and a session that greps and edits through shell commands may never open that directory at all — so this is the instruction, not a convenience. Some of those rules also bind code OUTSIDE that directory: how a safety finding, a chip, an interaction-pair extent or the reference slice reaches the answer and the wire is decided in `LlmInferenceService` and `ChartSearchAiRestController`, so read it before changing those too.

# Documenting a decision

**This file is directives and pointers. The evidence lives in `docs/adr.md` and in javadoc.** Why it was
cut to that shape, and what that cut measured, is `docs/adr.md` Appendix A.

So when you learn something worth keeping:

- **A rule someone must obey** — "use X, never Y" — belongs in the instructions: the directive,
  its issue number, and a pointer to the test that pins it.
  **The file is decided by the code the rule binds** — beside that code where it all sits in one
  directory, in this file where it binds several packages at once. One sentence per rule wherever a
  rule fits in one; where an entry point carries several, give each its own sub-bullet rather than
  a paragraph.
- **Why the rule is that way**, what was measured, what was tried and reverted, what a mutation
  reddens — the ADR decision, or the javadoc of the method it constrains. Not here.
- **Do not publish a count that tracks the code.** A test-suite total, a per-mutation tally
  ("reddens exactly these N cases"), an exclusivity claim ("the rest of the suite is green") —
  every one of those has gone stale here, and a stale one tells a
  maintainer the failure that mattered was collateral. State which named test a mutation reddens,
  name the residue, and stop. A figure that does NOT move with the code — an external fact, a
  past run's measurement, a structural partition — may stay, provided it carries what it is a
  count OF; where its force depends on a denominator, put it in the ADR with its date instead.
- **Do not restate an argument that already has a home.** Link the decision instead.

Most of that is enforced, over this file and every nested one: `ProjectInstructionsGuardTest`
fails the build on a suite total, an elided identifier, a cited symbol, path or ADR decision that
does not resolve, an unclosed code span or bold run, a nested instruction file this file does not name, a
file over its size budget, and one BULLET carrying more prose than its own budget — that last
measured without its trailing pointer run. It cannot check
whether a rule is TRUE — only that its pointers land and its figures are not of the kind that rot.

# API surface rules — do not bypass these methods

**What remains below has no one directory to sit beside**, each rule binding code in several packages at once. It is not a claim that the rules the drug-safety bullet above points at bind only theirs.

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values. Where a bullet cites an ADR decision, that decision is canonical for the reasoning — including for alternatives already measured and rejected, which should not be re-proposed without new evidence.

## Text and vector helpers

- **Prefixed text**: Use `ChartSearchAiUtils.buildPrefixedText(resourceType, text)`. Never call `getEmbeddingPrefix()` directly (it is private) or hardcode prefix strings like `"Clinical observation: "`.
- **Cosine similarity**: Use `ChartSearchAiUtils.cosineSimilarity()`. Never reimplement the formula.

## Citations and grounding

- **Whether a citation may be grounding-verified**: Use `ChartSearchAiUtils.isGroundingDemoteOnly(type)`, a named view of `referenceGroup()`. For any question that is not about grading, ask `referenceGroup(type)` against `REFERENCE_GROUP_REFERENCE` directly — do NOT borrow this one, which NAMES a grounding rule. **Never test `resourceType` against `drug_reference`** (#122). **Mutate the site you are about to change and read the failures.** What each site reddens differs and no mapping is published. Do not assume a site is covered because a neighbour is; `ReferenceProseFidelityCheck`'s own gate is still unguarded. The wire serializer is guarded separately (next bullet). The same rule binds consumers of the wire format — `README.md` requires a client to treat every `group=reference` citation alike, and that half of #201 is a change in `openmrs-esm-chartsearchai`.
- **Whether a grounding verdict may be PUBLISHED**: `ChartSearchAiRestController.groundedForWire()` is the ONLY place a `grounded` value reaches the wire. A `reference`-group citation always serializes `null` — never `true`, never `false` (#201): only `group` tells "this citation is not about that record" apart from "this claim may not be supported". Never publish `ref.getGrounded()` directly, and never re-derive the carve-out from a type name. → `ChartSearchAiReferenceGroundingWithholdingTest.theWireSerializerMustNotNameAReferenceGroupResourceType` (scope is exactly the controller's own class files; a hardcode elsewhere is invisible).
- **Where one sentence ends and the next begins**: ONE terminator set, `ChartSearchAiUtils.SENTENCE_TERMINATORS`, and three questions over it, each with its own entry point — `SENTENCE_BOUNDARY` SPLITS a text into units, `mayEndASentence` asks whether a sentence COULD have ended in one GAP (`ReferenceProseFidelityCheck`, #337), `DrugSafetyValidator.endSentence` asks whether a string already ends one. **Never a fourth regex or a character literal at a call site** (#260's shape). The two prose questions are not interchangeable: the splitter is strict (terminator followed IMMEDIATELY by whitespace), the gap question weak (terminator ANYWHERE in the gap; a MARKED cut is stepped over, and only for the operand whose cuts are being judged — ADR Decision 95), and the difference is load-bearing both ways. The set is interpolated through `Pattern.quote` so it can be edited as a SET; shrinking it is the silent failure, which is why `ReferenceProseFidelityTest.everyWayASentenceCanEndInTheSharedRuleEndsAnAnswerSentence` spells the members out as LITERALS.
- **Whether the answer's rendering of a cited reference record is faithful**: `ReferenceProseFidelityCheck` (#337) reports, at WARN, an answer that reproduces at least `MIN_REPRODUCED_WORDS` consecutive words of a cited reference-group record and then states different words inside the sentence it was reproducing. It scopes itself with `ChartSearchAiUtils.referenceGroup` and never a type name. **The `safetyWarnings` chips are NOT that check and never were.** Do not restate that claim anywhere: link the decision, or point at the family `CitationGroundingVerifier`'s class javadoc enumerates rather than listing it again. **Sweep the CLAIM in several phrasings, over comments as well as docs** — the decision says how. → ADR Decision 61.
  - **Its answer is PUBLISHED** (#337 round two): `ChartAnswer.getUnfaithfullyRenderedCitations()`, the `unfaithfullyRenderedCitations` key — the CITATION and never a word of either text. Resolved ONCE at the check's own call site, never re-derived at a consumer. `null` is no measurement, `[]` a measurement of none, and `[]` is **not** a certificate of faithfulness. **Do not move the check ahead of `searchStreaming`'s ungrounded handoff.** `ClassCodeFidelityCheck` publishes nothing, deliberately. → ADR Decision 74; `ChartSearchAiUnfaithfulRenderingTest`.
- **Whether the answer quoted a cited record's dosing ceiling and left a STRICTER one unstated**: `DosingCeilingFidelityCheck` (#276), at WARN, gating on `RecordMapping.getDosingCeilings()` and never a type name. Written in ONE place, `DrugReferenceInjector`'s `drug_reference` mapping, from the clauses `render` APPENDED and never the bands behind them, spelled by `dailyCeiling`. **Never re-derive it from the text**, `getOrderActive`'s rule (#317). **Strictest-first BY THE NUMBER, ordered at the writer; never sort it at a consumer**. → ADR Decision 96.
  - **Its answer is PUBLISHED**: `ChartAnswer.getUnstatedDosingCeilings()`, the `unstatedDosingCeilings` key — the CITATION and both ceilings, never a word of either text. Resolved ONCE at its own call site; `null` is no measurement, `[]` **not** a certificate. **It is not a claim the answer is WRONG** — README binds a client to that. → `DosingCeilingFidelityTest`, `ChartSearchAiUnstatedDosingCeilingTest`.
- **Whether a chart citation can be the ACTIVE ORDER its sentence names**: `ActiveOrderCitationFidelityCheck` (#377) reports, at WARN, a chart-group citation in the marker RUN after `DrugSafetyValidator.ACTIVE_ORDER_INTERACTION_PHRASE` whose type `ChartSearchAiUtils.mayDescribeAMedicationOrder` refuses, or whose `RecordMapping.getOrderActive()` is `FALSE`. **The unit is that run and never the sentence.** The predicate is an ALLOW-LIST, so an undeclared type is REPORTED. **Its answer is PUBLISHED** — `ChartAnswer.getMisattributedOrderCitations()`, the `misattributedOrderCitations` key: `null` is no measurement, `[]` a measurement of none and **not** a certificate. It tests what a record CAN be, never which order the finding came from. → ADR Decisions 76, 81; `ActiveOrderCitationFidelityTest`, `MedicationOrderRecordTypeTest`.
- **Whether a chart citation was attached by the MODULE rather than emitted by the model**: `RecordReference.isAttachedByTheModule()`, published as `attachedByTheModule`. Written in ONE place, `LlmInferenceService.extractCitedReferences`, which surfaces a cited record's `RecordMapping.getDerivedFrom()` (#305) — **after `seen.addAll(inline)` and never before it**, or a record the model cited inline only is published as the MODULE's. Set only by the two contraindication factories (`SafetyWarning.chartRecords()`), and FIXED at construction rather than unioned over the collapsed key. **Never key the provenance map where `PatientClinicalContextBuilder` collects it**: `PatientClinicalContext.lowerKeys` is the rule. **Such a citation is `Disposition.UNVERIFIABLE` in BOTH modes**, and `withGrounded` must carry the flag across. → ADR Decision 80; `FindingChartRecordProvenanceContextTest`, `LlmInferenceServiceFindingProvenanceContextTest`, `CitationGroundingVerifierTest.aCitationTheModuleAttachedPublishesNoVerdictAndSpendsNothing`, `ChartSearchAiFindingProvenanceTest`.
- **Whether a cited chart record NAMES the drug of the order it is about**: `RecordMapping.getOrderDrugNamed()` — three-valued, and `null` ("cannot say") is every retrieved record. Written in exactly ONE place, `DrugReferenceInjector`'s `active_drug_order` mapping, off `DrugSafetyValidator.displayNamesADrug`; never from the rendered text, which is `getOrderActive`'s rule for the same reason. **A citation of a record answering `FALSE` is `Disposition.UNVERIFIABLE` in BOTH modes** (#294), never `DEMOTE_ONLY`, whose kept FAIL leaves the same false *Unsupported* standing through Tier-1. **Never read `null` as membership, and never re-key it on the TYPE** — either blanks the NAMED record's verdict too, the one #118 injected the type for. → ADR Decision 93; `ArchitectureGuardTest.theOrderNamingStampIsWrittenInOnePlace`, `CitationGroundingVerifierTest.codesOnlyActiveOrder_aCosineFailIsWithheldRatherThanPublished`.
- **Inline citation markers**: `ChartSearchAiUtils.INLINE_CITATION` is the single parsing pattern and is deliberately single-index. Compact shorthand (`[6, 7]`, `[6/7]`) is normalized upstream by `LlmAnswerExtractor.normalizeSlashCitations(text, citations)` and ONLY when the structured citations array corroborates the group — never loosen the pattern or split bracket groups elsewhere; an uncorroborated numeric bracket is a clinical value (`[120, 80]`). **Decoding a marker to an INDEX is `ChartSearchAiUtils.citedIndexes`**; reading the pattern directly is for callers needing what a set of indexes cannot carry. **And an index is not a citation until the answer's own resolution admits it** — intersect with what `extractCitedReferences` produced. → ADR Decision 59; `ArchitectureGuardTest.classCodeFidelityCheckReachesMarkersOnlyThroughTheSharedDecodeStep` (CLASS-scoped, a source-text check, so a hand-rolled dialect written BESIDE a retained call is out of its reach).
- **Reading an index out of the structured `citations` field**: `LlmAnswerExtractor.citationIndex()` — an integral JSON number, or a string that is entirely one integer (#219). The asymmetry with prose is deliberate and neither side may cite the other to widen itself: an array entry has no competing reading so its TYPE is coerced and reported at WARN, while a bracket in answer text can always be a clinical value. The widening is over types only; `LlmInferenceService.extractCitedReferences` remains the only thing deciding which indices become references. The same accessor also reads the whole field when it is not an array (#221, via `readNonArrayCitations`) — container and entries must admit the same JSON types. Do not give the container a rule of its own.
- **Whether a non-conformant `citations` field is reported**: it is, at WARN, in both shapes — an array whose entries misbehave (`reportNonConformantCitations`) and a container that is not an array (`readNonArrayCitations`). Two channels for one failure was the inconsistency, not the warning. **The one silent case is an explicit `null`, and the reason is not "it is not an array"** — it is what the container ASSERTS: `null` asserts ABSENCE, the same statement as an omitted field. Everything else reaching `readNonArrayCitations` asserts PRESENCE of something unusable. Do not fold the two on the strength of both being non-arrays.

## Chart assembly

- **Chart assembly**: Use `ChartBuildingStrategy.buildChart()` → `QueryStoreChartBuilder.build()`. Never fetch or serialize a patient chart by another path; querystore owns retrieval.
- **Which chart-assembly mode produced an answer**: `ChartBuildingStrategy.searchModeLabel(chart)`, read off the answer as `ChartAnswer.getSearchMode()`. Never re-derive it at a consumer from `chartsearchai.chartMode` or `chartsearchai.embedding.preFilter` (#178). The label is computed from `PatientChart`'s own stamps (`isQueryScoped()`, `isPreFiltered()`), never a fresh GP read, which also means labelling needs no `Context`. Every stamp must be carried across `DrugReferenceInjector.injectRecords` — a dropped stamp is lost silently and **fail-open**. And `SEARCH_MODE_QUERY_SCOPED` is defined AS `CHART_MODE_QUERY_SCOPED`, so renaming that GP token silently rewrites every subsequent row for readers outside this module. → `ChartSearchAiAuditSearchModeTest` pins the four spellings as literals.
- **Whether a chart record's drug order is still in force, and when it stopped**: `SerializedRecord.getOrderActive()` / `getOrderStopDate()`, and `PatientChartSerializer.RecordMapping`'s same two where a consumer reads a built chart. Both written in exactly ONE place, `QueryStoreChartBuilder.toSerializedRecords`, the funnel all three build paths share; never re-derive either, and in particular never from the rendered text. That was #317, and the date #315. 
  - **It is three-valued and the third value is the guard** — `TRUE` in force, `FALSE` this patient's order and not in force, `null` the module cannot say. **The situations `null` covers are enumerated in exactly ONE place, the `SerializedRecord.orderActive` field javadoc**; point at it rather than restating it, here or in a decision. Never collapse it to a boolean, and never read `isEmpty()` on an active-order set as "could not read". 
  - **Evaluate each order in its own try** — `Order.isActive()` THROWS, and a chart-wide try takes the mark off every record for that patient. 
  - **The date is core's `Order.getEffectiveStopDate()`**, never a field choice made here, and its asymmetry with this mark is enumerated in ONE place — the `SerializedRecord.orderStopDate` javadoc — which every other site points at rather than restating. A missing date is never "in force". PUBLISHED as `orderStopDates` by `ChartSearchAiUtils.orderStopDates`, over the answer's markers INTERSECTED with its resolution, gated on the STAMP and never a type name; `null` no measurement, `[]` not a certificate. Only `PatientChartSerializer` may pass `RecordMapping` a non-null date (#432). → ADR Decision 98; `ArchitectureGuardTest.theOrderStopDateStampIsWrittenInOnePlace`, `ArchitectureGuardTest.theOrderStopDateReachesAMappingFromTheSerializerAlone`. 
  - **`describesEndedOrder` is now AND-ed with this, never ranked against it**, and each can only exclude more. Do not "simplify" it into a precedence rule. Scoped to `drug_order` deliberately. Mutate the guards and read the failures. → ADR Decisions 46, 47.

- **One mechanism, one chip, and the orders it names**: `DrugSafetyValidator.collapseSharedMechanisms` states a mechanism ONCE, naming every active order it covers, each chip carrying them as `SafetyWarning.namedPartners()`. **It may not drop a partner or move a rating, and returns the PAIR count, not the chip count.** → ADR Decision 99; `SharedMechanismChipCollapseTest`.
  - **An order the prose leaves unnamed is named by the MODULE, not a second inference**: `FindingPartnerCoverageCheck.withUnstatedPartnersNamed` APPENDS, after `measure`, only the CITED findings' orders (`citedFindingIndexes`; #516). → ADR Decision 100.

## Model files

- **Fetching a model file**: `scripts/model-manifest.sh` — `fetch_and_verify` against the pinned revision and sha256 `model-manifest.tsv` records, `fetch_or_degrade` for what chart search needs, or `fetch_and_verify_override` on the dispatched path. That manifest is the ONE source of either (#444, #449). Never spell a `huggingface.co` URL at a call site, nor fetch a model beside the library. → ADR Decision 106; `ModelDownloadPinningGuardTest`.

## Tests and eval

- **Test datasets**: Use `TestDatasetHelper.FULL_PATIENT_DATASET`, `TestDatasetHelper.SECOND_PATIENT_DATASET`, `TestDatasetHelper.toSerializedRecords()`, `TestDatasetHelper.inferResourceType()`, `TestDatasetHelper.stripDatasetPrefixAndDate()`. Never duplicate these helpers in individual test files.
- **Category hints in tests**: Use `TestDatasetHelper.FULL_DATASET_CATEGORY_HINTS` (and per-dataset variants). Never duplicate hints maps in individual test files.
- **Stripping category hints**: Use `ChartSearchAiUtils.stripCategoryHints()`. Never reimplement the hint-detection pattern.
- **Which citations a capture scorer may score**: `eval/drift-metric/metric_score.py`'s `model_cited(references)` — the MODEL's own, never every entry of the array (#305), or a gate moves without the model's behaviour moving. ONE home, because every reader defaults the wire key to falsy for older captures, so a RENAME of it re-admits every attached citation — fail-open, which is why `--selftest` spells the key as a literal. `eval/grounding-scope/grounding_scope_ab.py` TAGS instead and spells the key a second time. → ADR Decision 80.
- **Saying an absent-data answer may name its topic two ways**: put the alternatives in `expectedAnswerContainsAny` (OR). **Never add a second element to `expectedAnswerContains` for that** — it is AND, so a second element makes the case stricter, the opposite of what a second correct name needs (#216). Neither list is the place to accommodate a wording you have not measured — an OR element is a new way to pass. → `AbsentDataEvalTest.anAnswerNamingNoTopicFailsEveryCaseThatNamesOne`. Where a single stem covers the variants (`smok`, `vaccin`) that stem in the AND list is the narrower expression and stays.
