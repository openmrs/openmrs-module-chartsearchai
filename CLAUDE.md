# Rules

- When a test fails, fix the pipeline/production code — never weaken assertions, revert test data, or change expected values to match wrong behavior.
- Prefer root-cause fixes over incremental symptom patches. Diagnose *why* something is broken before proposing a fix. Start with the best solution, not the quickest.
- Before claiming the filter is correct, verify what it actually returns — check the records, not just the count or the final answer. A filter returning 32 irrelevant records is not correct even if the LLM produces the right answer from them.
- Do not go in circles analyzing a problem without fixing it.
- Tests must call the actual production pipeline — no simulations, mocks, or reimplementations of pipeline logic in test code. This includes unit tests for internal methods: do not call internal methods directly with hand-crafted inputs. Every test must exercise the full production code path using real data (e.g. the patient test datasets and the real querystore-backed retrieval path).
- **Never re-express a production predicate in a script that measures the knowledge base for a figure you will quote** in javadoc, a PR body or an issue. Compile against the built jar or drive the real code through a throwaway test, and say which method produced any figure you record. `substanceKey`, `normalizeAtcToken`, `isLocallyAppliedAtcCode`, `containsBoundedToken` and `canonicalRow` carry accumulated special cases a fresh implementation quietly drops, so a script that is 98% right produces plausible numbers that are wrong in exactly the tail being investigated (measured 2026-08-07 — a Python reimplementation of `substanceKey` disagreed with production on family counts; #191).
- **Quote the figure the system already recorded, and where you must derive one, say what produced it and what it is a share OF — wherever it is published, a page or a report included.** #243 records the knowledge-base form of this; the same error reached a measurement of the pipeline's own transcripts on 2026-09-02, where a cost recomputed from published per-token rates was published beside the value the sessions themselves record, and its gap was then stated over the derived base rather than the recorded one.
- When a multi-step pipeline exists (e.g. normalize → transform → embed), tests must call the composed production method, not manually chain the individual steps. Manually chaining steps in tests can mask bugs where the production code assembles the pipeline differently. If no composed method exists, extract one and use it from both production and test code.
- Tests are the specification. Modifying tests to make them pass is changing the spec — only fix the production code to satisfy the existing tests.
- Before presenting changes, review your own diff multiple times. On each pass, check every item below. Keep reviewing until a pass finds nothing to fix.
  1. Does the change match the plan?
  2. Is the logic correct — edge cases, off-by-one errors, null/empty handling?
  3. Are there any regressions — does existing behavior stay intact?
  4. Is anything missing — incomplete implementation, forgotten call sites?
  5. Does it use the real production pipeline, not a simulation or mock?
  6. Were any tests modified? If so, that's a rule violation — revert and fix the production code instead.
  7. Were all rules in this file followed?
- Follow test-driven development: for every bug fix or new feature, first write a failing test that defines the expected behavior, then write production code to make it pass. Write the strictest assertion — if it doesn't fail, tighten it until it does.
- Always create a plan before writing code. Read the relevant code, outline the approach, then implement.
- Never commit code with known regressions. When a change fixes one case but breaks another, the root cause is usually in shared infrastructure, not the individual call site — diagnose the shared problem before patching stages.
- Retrieval is owned by openmrs-module-querystore (issue #51). chartsearchai no longer has an in-process embedding/Lucene/Elasticsearch pipeline, scoring/ranking code, an embedding store, or a retrieval eval harness — do not reintroduce them. Retrieval changes *and retrieval-quality evaluation* belong in the querystore module (it owns the index and the e5-base-v2 embedder), not here.
- **Keep Bash output scoped — it is context, and the tail dominates.** Measured over one full `resolve-ticket` run, 33 of 329 Bash calls produced 52% of all output. Never `cat` a file you are about to grep; scope every recursive grep to `api/src`/`omod/src` and never to `.`; report a build as its FAILURES plus a computed total rather than every `Tests run:` line. **This rule does not reach reading production code** — file-region reads were the largest category and are where the findings came from. Trim the overhead, never the reading.

# Documenting a decision

**This file is directives and pointers. The evidence lives in `docs/adr.md` and in javadoc.** It
was cut to that shape on 2026-08-31, having grown from 5 KB to 159 KB in the twenty-six days
before by accreting rejected alternatives, measured ratios and review-round narrative — until
94% of it was one subsystem and a single bullet ran to 39,603 characters, while `docs/adr.md`
(63 decisions) and the javadoc (`DrugSafetyValidator` is 74% comment lines) already held the
same reasoning. Three copies is how this file came to contradict itself, repeatedly, and how
quoted figures went stale unnoticed.

So when you learn something worth keeping:

- **A rule someone must obey** — "use X, never Y" — belongs here: the directive, its issue
  number, and a pointer to the test that pins it. One sentence per rule wherever a rule fits in
  one; where an entry point carries several, give each its own sub-bullet rather than a paragraph.
- **Why the rule is that way**, what was measured, what was tried and reverted, what a mutation
  reddens — belongs in the ADR decision, or in the javadoc of the method it constrains. Not here.
- **Do not publish a count that tracks the code.** A test-suite total, a per-mutation tally
  ("reddens exactly these N cases"), an exclusivity claim ("the rest of the suite is green") —
  every one of those has gone stale here, some within a single commit, and a stale one tells a
  maintainer the failure that mattered was collateral. State which named test a mutation reddens,
  name the residue, and stop. A figure that does NOT move with the code — an external fact, a
  past run's measurement, a structural partition — may stay, provided it carries what it is a
  count OF; where its force depends on a denominator, put it in the ADR with its date instead.
- **Do not restate an argument that already has a home.** Link the decision instead.

Most of that is enforced: `ProjectInstructionsGuardTest` fails the build on a suite total, an
elided identifier, a cited symbol, path or ADR decision that does not resolve, an unclosed code
span, and on this file exceeding its size budget. It cannot check whether a rule is TRUE — only
that its pointers land and its figures are not of the kind that rot.

# API surface rules — do not bypass these methods

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values. Where a bullet cites an ADR decision, that decision is canonical for the reasoning — including for alternatives already measured and rejected, which should not be re-proposed without new evidence.

## Text, names and folding

- **Prefixed text**: Use `ChartSearchAiUtils.buildPrefixedText(resourceType, text)`. Never call `getEmbeddingPrefix()` directly (it is private) or hardcode prefix strings like `"Clinical observation: "`.
- **Cosine similarity**: Use `ChartSearchAiUtils.cosineSimilarity()`. Never reimplement the formula.
- **Diacritic folding**: Use `DrugReference.foldDiacritics()`; never `java.text.Normalizer` or a hand-rolled character map. **Fold once, where each operand is produced** (#330) — an entry's aliases in `setAliases` (`DrugReference.foldedAliases`, index-aligned with the raw list, derived in the sole writer and not memoised, which is why #172's rule does not reach it) and a scan's recorded name in a `DrugReference.FoldedName`, produced only by `DrugReference.fold`. Prose takes a folded `String` instead (`findByQuery` → `matchesFoldedText`), deliberately. **Never hand a folded string to an unfolded arity** — `foldedLower` is documented non-idempotent; the type prevents this for a recorded name but not for prose, so the one prose site (`DrugSafetyValidator.namesSubstance`) is held by a source guard. Do not merge `FoldedName` with `namedOccurrences`' `foldedLowerText` parameter — that one is prose folded under the prose rule, handing back positions into that exact string. Each boundary rule gets one named entry point per operand shape over one `foldedMatch` core; a CALLER must never choose an allowance of its own (#260). → ADR Decision 55; `FoldedOperandTest.everyAliasOfALoadedEntryIsItsOwnWitness` (its reach is the loaded data's — mutate the line and read the failures).
- **Matching a drug name**: three shapes, three accessors; do not swap one for another or widen one to serve another (#86, #128, #147). `DrugReference.matchesText()` for PROSE; `DrugReference.namedOccurrences()` when a caller needs WHERE a prose match sits (every occurrence with its span — one reported occurrence cannot answer #270's sub-span question); `DrugReference.matchesDrugName()` / `DrugReferenceService.findByDrugName()` / `lookupByToken()` for a clinician-entered drug NAME; `DrugReference.isNamed()` / `normalizeName()` for IDENTITY between two reference strings. **Never `String.indexOf` beside a `matchesText` gate** — that was #260, and the two disagreed in both directions, silently. RANKING those claims is a fourth question and `nameMatchStrength` is its one answer. → ADR Decision 52.
- **How strongly an entry claims a recorded name**: Use `DrugReference.nameMatchStrength()` — display name IS the recorded name, then another name IS it, then the earliest entry the name merely occurs INSIDE. Never re-rank by alias length or by preferring `canonicalRow`; both were measured and are worse. Since #209 this ranking also decides the candidate SET, through `findImpliedSubstances`. → #192; ADR Appendix A.

## Which candidates a string puts in play

- **Which candidates a recorded string puts IN PLAY**: `DrugReferenceService.findImpliedByQuery(text)` for PROSE, `findImpliedByDrugName(name)` for a recorded drug NAME. `findByQuery`/`findByDrugName` are the unranked primitives underneath and answer a different question. **Never build a chip arm's or the injector's candidate set by iterating `matchesText`/`matchesDrugName` yourself** — that was #209, where a chip named a substance the patient was not prescribed. `DrugReference.aliasesIn()`/`aliasesNaming()` are each their own boolean's witness and exist for this and nothing else. Both legs are needed together: the drug-in-play arm and the order-driven arm each skip what the other covered.
- **Which drug CLASS a question names**: `DrugReferenceService.namedDrugClass(question)` — a class NAME and never a member set, so it is not a third candidate-set accessor beside `findImpliedByQuery`/`findImpliedByDrugName` and a caller must never read its answer as putting substances in play (#354). Its vocabulary is `DrugClassTerms`, two INDEPENDENT sources unioned: the curated cross-reactivity groups' own `name`s, and a code table carrying a class that file cannot name, further SPELLINGS of one it can, and the class it does name — the last deliberately, so an operator's own groups file cannot lose it. **Never add a cross-reactivity group to make a word recognisable** — its `atcPrefixes` assert cross-reactivity and duplicate-class therapy — and never resolve a class to an ATC subtree, which was measured wrong in both directions for the reported class. The record it produces (`RESOURCE_TYPE_DRUG_CLASS_NOTE`) **names no member of the class**, because it is citable evidence — a rule binding the class NAME the note prints as well as the terms it is matched by. It closes by asking for a specific drug and **must promise nothing about what that resolves to** (false for a drug the loaded dataset does not carry); every clause of it is an imperative about the QUESTION or a claim about ENTRIES, because four wider sentences were written there and all four were measured false. Its words are pinned as a literal, so a fifth cannot be added by rewording. → ADR Decision 67; `DrugClassQuestionNoteTest.theNoteNamesNoSubstanceTheReferenceDataCarries`, `.aQuestionNamingAClassAndAResolvableDrugRaisesNoNote`, `.everyCuratedClassTermResolvesToNoSubstanceInTheShippedKnowledgeBase`, `.everyClassNameTheTableCanReportNamesNoSubstanceOfTheShippedKnowledgeBase`, `.theRenderedNoteIsExactlyTheseWords`.
  - **That record is prompt-facing, so the class is ALSO stated deterministically on the wire**: `ChartAnswer.getUnresolvedDrugClass()`, published as the `unresolvedDrugClass` response key. An injected record reaches a client only if the MODEL cites it, and on the issue's own reproduction it did not — nothing a `/search` consumer reads reported the class at all. Resolved ONCE per `LlmInferenceService` method by `ChartSearchAiUtils.unresolvedDrugClass(mappings)` off the POST-inject chart, so the key is non-null exactly when the prompt carries the note; **never re-ask `namedDrugClass` at a consumer**, which is not self-gating and knows nothing about `injectFromQuery`. `null` is the absence of a statement and never a denial. **The CLIENT contract carries the note's own two prohibitions** — README's `unresolvedDrugClass` section tells a client to render what the note STATES, and names the two refuted wordings it must not use (that the MODULE screens by substance; that naming a specific drug *would* be screened), because that rendered sentence is what a clinician reads when the answer does not relay the note, so a refuted wording is worse there than in the note. It must reach every surface carrying the answer — the ungrounded answer included, since the early `done` is what a user sees — so `ChartSearchAiRestController.putModuleStatements` composes `putSafetyChips` with it, and `ChartSearchAiUnresolvedDrugClassTest` fails the build on a second call to `putSafetyChips`. → ADR Decision 67; `LlmInferenceServiceUnresolvedDrugClassTest.aChartWithNoClassNoteStatesNoClassEvenWhereTheQuestionNamesOne`, `.searchStreaming_statesTheClassOnTheUngroundedAnswerTooAndNotOnlyOnTheFinalOne`.
- **Which substances a recorded drug name implies**: Use `DrugReferenceService.findImpliedSubstances(name)`. `lookupByToken()` answers exactly one row and is the primitive underneath — reaching for it directly is how a combination allergen ends up checked against a single constituent (#193) and how a presentation filed apart from its parent moiety produces no chip at all (#195), both silently and fail-closed. The widening lives here, in what the recorded *string* is read to name — not in `substanceKey` (identity), not in `nameMatchStrength` (ranking).
- **Which of the substances a recorded name implies it actually NAMES**: Use `DrugReferenceService.findNamedSubstances(drugName, implied)`, and ask it before PRINTING a substance's own label in a sentence reporting the patient's record. A strict subset of `findImpliedSubstances`, which is additive on purpose. Its equal-claimant leg admits a row on a rank TIE, which a combination the KB spells without a separator satisfies — and so does a row the chart never mentions (#268). **Never build a candidate set from it** (package-private for that reason): a caller resolving with it drops every substance a name implies without naming. Sole caller `DrugSafetyValidator.addAllergyContraindications`; where a name does not name the row, its sentences state the relationship rather than asserting the allergy (#238).

## Substance identity and classification

- **Substance identity, and which row represents a substance**: `DrugReference.substanceKey()` / `substanceGroupKey()` for "are these rows one substance?"; `DrugReference.canonicalRow()` / `namesNoRoute()` / `namesItsSubstance()` to pick the row that names it. A substance has N rows in DDInter, so anything enumerating matching entries produces N of something unless it goes through these — #145, #162, #163, #174, #186, one defect in seven places. Identity is `drugbank_id` resolved **per substance-name family**, deliberately not `rxcui` or `rxnorm_name` (both shared by `Omeprazole` and `Esomeprazole`) and not the display stem alone (#187). `canonicalRow` has two rungs — route-qualification (`namesNoRoute`), then, for two rows of ONE substance tied on that, the row the data files the family under (`namesItsSubstance`). Do not compare display STEMS. Nothing pins their ORDER because since #250 nothing can. **A qualification COUNT over this fold needs its unit** — "elected rows answering `!namesNoRoute()`" and "elected rows whose raw name carries a trailing parenthetical" were one predicate before #250 and are two different families after it; mutate each and read the failures. For a chip's SUBJECT the two rankings compose in a fixed order in `DrugSafetyValidator.interactionSubject()`: `nameMatchStrength` first, then `canonicalRow` among rows tied on that (#194). Do not reverse it (#187) and do not call `canonicalRow` directly at a chip-subject site — one substance must not be named two ways in one response. → ADR Decisions 43, 56; `SubstanceNameRowTest.theSubstanceNameIsMatchedAgainstTheWholeDisplayNameAndNotItsStem`, `.noRouteQualifiedPresentationIsElectedToSpeakForItsSubstance`, `DuplicateTherapySelfChipTest.anOrderKnownOnlyByACodeTheRowItselfPublishesIsStillSkipped`, `SubstanceNameRowTest.aFamilyWithAnUnqualifiedRowElectsOneAndNoOtherRowSpeaksForIt` (guards a weakening of the PREDICATES, not a KB refresh — a data change reaches `SubstanceNameRowTest.everyFamilyElectingAQualifiedRowOverAPlainSiblingIsNamedRatherThanCounted` instead).
- **Whether an ATC subgroup may justify a clinical claim**: THREE predicates, chosen by **the claim you are about to make**. `DrugReference.isLocallyAppliedAtcCode()` separates the code classifying a SUBSTANCE from ones classifying a locally applied presentation — **a preference between candidates wherever the caller holds no evidence about which presentation the patient was given, which is every caller but one**. `DrugSafetyValidator.sharedClass` is that rule and still returns a locally applied subgroup where that is all a pair shares; `DrugReference.codesAtSites` (#234) may DROP a code, decided by `ATC_GROUPS_BY_SITE` against the order's own recorded route or dose form. A caller with no such evidence gets the preference and never the veto; adding a third caller means saying which of the two it is. `isUnclassifyingAtcCode()` is the DUPLICATE-THERAPY bar (a group asserting nothing at all); `isPurposeOnlyAtcCode()` is the CROSS-REACTIVITY bar and **subsumes** it. That ordering is what makes three lists composable. `sharedClass` takes the arm as a parameter and is the only caller of the latter two; **never ask one arm's question with the other's predicate** (#183).
  - **The two arms may legitimately name DIFFERENT classes for one pair. That is the settlement, not a defect** (#183/#184) — the preference among survivors is still one method (#171), but the candidate SETS differ, so naming them alike would make one of the two sentences false.
  - **The criterion, stated so it can be re-applied.** A subgroup licenses only the claim its own published NAME asserts, and a residue ("Other …"/"Various …") inherits its parent's assertion recursively — *unless it contributes a term none of its ancestors' names carry*. A name stating a chemical family, a derivative class or a molecular TARGET licenses both claims; one stating only an indication, an organism acted against, a therapeutic area or a diagnostic use licenses duplicate therapy alone; one whose ancestry is residue all the way up to a bare LEVEL-1 anatomical main group licenses neither. Level 1 and not level 2 — ATC's level 2 is its THERAPEUTIC tier.
  - **Derived from the index, never from the reported cases.** All 939 level-4 names in the WHO ATC/DDD index were read and the criterion applied to each. #161's list was hand-picked and its hardening found it incomplete in a way that reproduced the defect it was fixing (#263). Add a member only by re-deriving the criterion, and record the measured KB impact in the ADR.
  - **Do not re-propose a uniform ATC veto.** Measured and rejected: it loses real signal 2.4× faster than it removes false claims, and the penicillins, cephalosporins, aminoglycosides, benzodiazepines and statins are all on the losing side. → ADR Decision 34; ADR Appendix A.
- **Which of a substance's codes describe the presentation the patient was GIVEN**: Use `DrugReference.codesForRecordedAdministration(codes, recordedTerms)`, reading the terms off the order — `PatientClinicalContext.ActiveDrugOrder.getAdministrationTerms()`, every name the order's route concept and its drug's dosage-form concept PUBLISH, never the drug's NAME. **Every name, through `PatientClinicalContextBuilder.addConceptNames` and never `addConceptName`**: `Concept.getName()` returns the locale-preferred spelling ahead of the fully specified one, and reading one name left #234's own defect standing silently for three of the 3.7.1 dictionary's nine site-naming routes. A term list is not a substitute — a vocabulary of site WORDS cannot reach a spelling that is not one. Do not widen `addConceptName` to do it (it would change which reference entries an ORDER's name reaches). `DrugSafetyValidator.codesForThisSubstancesPresentations` is the single production caller of it and of `narrowsAnyCode`, and that is the only place either belongs; do not apply it inside `sharedClass`, which compares two code sets for four callers. **The site table is a PARTITION of `LOCALLY_APPLIED_ATC_GROUPS`, not a list beside it** — `ATC_GROUPS_BY_SITE` plus `LOCALLY_APPLIED_GROUPS_NAMING_NO_SITE` account for all 17 prefixes, and `S` is expanded into ATC's own `S01`/`S02`/`S03`. **A term must name ONE site**: `cream`/`ointment`/`lotion` are deliberately absent because the union reading is worse than none, and `topical` is absent because ATC uses the word for the anorectum too — read as the skin it SILENCES a real claim. A term naming a route of ENTRY (`ROUTES_OF_ENTRY`) REFUSES the site walk rather than merely failing to match it. It **declines** — returning codes untouched — where no term names a site AND where the substance is filed under none at the site a term does name (both paths are the one `kept.isEmpty()` tail); for several orders of one substance the question is asked per order and of what the data can EXPRESS (`narrowsAnyCode`), never of what the terms merely NAME. It can remove CODES and never a partner. → ADR Decision 50; `UnmappedOrderAdministrationSiteTest.aRouteSpelledAsAnInflectionOfItsTermStillSelectsItsSite`, `.everyLocallyAppliedCodeInTheShippedKnowledgeBaseIsAccountedFor` (a DATA guard over the shipped KB, so a group absent from it still escapes), `ActiveOrderAdministrationTermsTest.everySpellingTheRouteConceptPublishesIsCarried`.

## Citations and grounding

- **Whether a citation may be grounding-verified**: Use `ChartSearchAiUtils.isGroundingDemoteOnly(type)`, a named view of `referenceGroup()`. For any question that is not about grading, ask `referenceGroup(type)` against `REFERENCE_GROUP_REFERENCE` directly — do NOT borrow this one, which NAMES a grounding rule. **Never test `resourceType` against `drug_reference`** — that is how `safety_finding` was graded as chart evidence for two releases (#122). **Mutate the site you are about to change and read the failures.** #354 added a THIRD reference-group type, which is what these guards were waiting for — but what each site reddens differs, and three successive attempts to write that mapping down here were each falsified by the next measurement, so no mapping is published. Do not assume a site is covered because a neighbour is, and note that `ReferenceProseFidelityCheck`'s own gate is still unguarded, which the third type did not change. The wire serializer is guarded separately (next bullet). The same rule binds consumers of the wire format — `README.md` requires a client to treat every `group=reference` citation alike, and the reference frontend still keys its badge, label and chart-tab route off `resourceType`, so that half of #201 is a change in `openmrs-esm-chartsearchai`.
- **Whether a grounding verdict may be PUBLISHED**: `ChartSearchAiRestController.groundedForWire()` is the ONLY place a `grounded` value reaches the wire. A `reference`-group citation always serializes `null` — never `true`, never `false` (#201) — because only `group` tells "this citation is not about that record" apart from "this claim may not be supported", and a client reading it as the latter rendered a deterministic Major-interaction finding as *Unsupported*, in red. Never publish `ref.getGrounded()` directly, and never re-derive the carve-out from a type name. → `ChartSearchAiReferenceGroundingWithholdingTest.theWireSerializerMustNotNameAReferenceGroupResourceType` (scope is exactly the controller's own class files; a hardcode elsewhere is invisible).
- **Where one sentence ends and the next begins**: ONE terminator set, `ChartSearchAiUtils.SENTENCE_TERMINATORS`, and three questions over it, each with its own entry point — `SENTENCE_BOUNDARY` SPLITS a text into units, `mayEndASentence` asks whether a sentence COULD have ended in one GAP (`ReferenceProseFidelityCheck`, #337), `DrugSafetyValidator.endSentence` asks whether a string already ends one. **Never a fourth regex or a character literal at a call site** (#260's shape). The two prose questions are not interchangeable and the difference is load-bearing both ways: the splitter is strict (terminator followed IMMEDIATELY by whitespace); the gap question is weak (terminator ANYWHERE in the gap) because both its uses are silencing. The set is interpolated through `Pattern.quote` so it can be edited as a SET. Shrinking it is the silent failure, which is why `ReferenceProseFidelityTest.everyWayASentenceCanEndInTheSharedRuleEndsAnAnswerSentence` spells the members out as LITERALS rather than iterating the constant.
- **Whether the answer's rendering of a cited reference record is faithful**: `ReferenceProseFidelityCheck` (#337) reports, at WARN and never to the wire, an answer that reproduces at least `MIN_REPRODUCED_WORDS` consecutive words of a cited reference-group record and then states different words inside the sentence it was reproducing. It scopes itself with `ChartSearchAiUtils.referenceGroup` and never a type name. **The `safetyWarnings` chips are NOT that check and never were** — they carry the deterministic text but are an independent list nothing reconciles against the answer. Do not restate that claim anywhere: say what checks it (`ClassCodeFidelityCheck` for an ATC token, this one for prose) or link the decision. **Sweep the CLAIM in several phrasings, over comments as well as docs** — one sweep was defeated by a wording carrying none of its search tokens, the next by an enumeration that said "in its javadoc" and so scoped itself out of a line comment. → ADR Decision 61.
- **Inline citation markers**: `ChartSearchAiUtils.INLINE_CITATION` is the single parsing pattern and is deliberately single-index. Compact shorthand (`[6, 7]`, `[6/7]`) is normalized upstream by `LlmAnswerExtractor.normalizeSlashCitations(text, citations)` and ONLY when the structured citations array corroborates the group — never loosen the pattern or split bracket groups elsewhere; uncorroborated numeric brackets are clinical values (`[120, 80]`) and splitting them fabricates references. **Decoding a marker to an INDEX is `ChartSearchAiUtils.citedIndexes`**; reading the pattern directly is for callers needing something a set of indexes cannot carry — each marker's text offset, or the text with markers removed. **And an index is not a citation until the answer's own resolution admits it** — that check intersects what it decodes with the list `extractCitedReferences` produced, which promotes every IN-RANGE bracketed integer, so what the intersection excludes is a number the chart has no record for. → ADR Decision 59; `ArchitectureGuardTest.classCodeFidelityCheckReachesMarkersOnlyThroughTheSharedDecodeStep` (CLASS-scoped, a source-text check, so a hand-rolled dialect written BESIDE a retained call is out of its reach).
- **Reading an index out of the structured `citations` field**: `LlmAnswerExtractor.citationIndex()` — an integral JSON number, or a string that is entirely one integer (#219: the json_schema is server-enforced, so a remote that approximates it can send `["9","10"]`). The asymmetry with prose is deliberate and neither side may cite the other to widen itself: an array entry has no competing reading so its TYPE is coerced and reported at WARN, while a bracket in answer text can always be a clinical value. The widening is over types only; `LlmInferenceService.extractCitedReferences` remains the only thing deciding which indices become references. The same accessor also reads the whole field when it is not an array (#221, via `readNonArrayCitations`) — container and entries must admit the same JSON types, and routing both through one reader is what stops them drifting. Do not give the container a rule of its own.
- **Whether a non-conformant `citations` field is reported**: it is, at WARN, in both shapes — an array whose entries misbehave (`reportNonConformantCitations`) and a container that is not an array (`readNonArrayCitations`). Two channels for one failure was the inconsistency, not the warning. **The one silent case is an explicit `null`, and the reason is not "it is not an array"** — it is what the container ASSERTS: `null` asserts ABSENCE, the same statement as an omitted field, so nothing is lost and nothing is guessed. Everything reaching `readNonArrayCitations` asserts PRESENCE of something unusable. Absence honoured is not a defect; presence discarded is. Do not fold the two on the strength of both being non-arrays.

## Loading, caching and observability

- **What reference dataset is actually loaded**: Use `DrugReferenceService.getLoadStatus()` (or `GET /chartsearchai/drugreferencestatus`). Never re-read the global properties to infer it — the load is **lazy**, so a check made right after flipping a GP reads the *previous* source (#149/#154).
- **Memoising anything derived from `getAll()`**: hold it in a **per-call local, never in a field** — #172's rule, binding `DrugSafetyValidator`, `DrugReferenceInjector` and `DrugReferenceService` alike. **The reason nine comments once gave for it — hot-reload — is measured false**; `DrugReferenceLoadContextTest.loadStatusDoesNotDriftFromTheCachedEntriesWhenTheGlobalPropertiesChange` pins the static half, so read that rather than re-measuring. **Keep the rule; two TECHNICAL reasons hold today**: these beans are Spring singletons, so a field memo is one unsynchronized `HashMap` shared by every concurrent request; and SOME memos are keyed on something unbounded, so as fields they grow for the life of the JVM or answer for whoever asked first. Say which applies at a given site rather than reciting both — the second does not bind every site. A further reason, binding no site in particular, is why the discipline is worth keeping even where neither bites: a module whose memos are all per-call is one a reload path can be added to later without re-auditing every one. Do not extend the rule to `CrossReactivityGroup.setAtcPrefixes`, a production write path that must stay authoritative after a read. → `RecordedAllergenMemoScopeTest` pins ONE shape of it (a memo outliving the entries it was resolved from); a field REASSIGNED once per pass stays green on it, and a single-threaded case cannot observe the sharing that is the first reason above.
- **Whether a loaded dataset is VALID, and what the loader did about it**: Use `DrugReferenceValidity`, reported through `DrugReferenceLoad.getFindings()` for the ENTRY dataset and `CrossReactivityGroupsLoad.getFindings()` for the curated groups file (#266) — two loads, two sections on `GET /chartsearchai/drugreferencestatus`, never one findings list a reader cannot attribute to a file. **Never add a guard for one bad-data shape at its own call site**: #150, #156, #196 and #211 were four such shapes in one code path, and a guard apiece would give as many answers to what this loader considers valid. Rules binding anything added here:
  - **The remedy is decided per rule and never uniform by default** — drop the offending VALUE where the rest of the entry is usable, repair only what the data already says, otherwise report. No rule refuses a file: an additive net that refuses its dataset produces the inert safety layer #149 exists to flag.
  - **A rule must stay silent on an untouched default.** Both path GPs default to files the module never creates, so a rule keyed on "a path is configured and the file was not read" fires on every install. Compare against `ChartSearchAiConstants.DEFAULT_DRUG_REFERENCE_DATA_FILE_PATH` / `DEFAULT_DRUG_REFERENCE_CROSS_REACTIVITY_FILE_PATH`, pinned to `omod/src/main/resources/config.xml` by `GlobalPropertyDefaultsTest`.
  - **Resolve a dataset file through `ReferenceDataFiles`, never your own stream** — `loadWithClasspathFallback` where the module ships a copy, `loadOperatorFile` where it does not. A source opening its own stream has no collector, so it can raise nothing, which is exactly how `atc` came to have no validity channel. Stated over the READ and not over a fallback since #266: `sourceFormat=atc` bundles none, so `loadOperatorFile` reaches `configuredDataFileNotRead` with `ORIGIN_NONE` and that rule's detail branches on it — a load that read nothing in the named file's place must not be told its count "looks healthy". `DrugReferenceSourceValidityChannelTest` fails a source INHERITING `lastLoadFindings()`'s default and cannot see one that declares it and returns a constant empty list.
  - **Silence is the ABSENCE of a finding, never a muted one.** Every finding reaches both channels — the log at the moment it happens, and `toMap()` afterwards, carrying its rule, remedy and count. `toMap()` is never scoped. **What IS scoped is the log LEVEL, and only it**: `logTo(log, origin)` reports a DATA rule about the dataset the module SHIPS at INFO and everything else at WARN, because the default is a redistributed KB whose known defective rows no operator can fix. The list that may soften is `DATA_RULES`; anything unclassified is loud, and `DrugReferenceFindingLoudnessTest` fails the build on a rule left out of it. **Do not read this as "observable but not loud"** — that was tried for the mistyped-`sourceFormat` case and ruled wrong: #154 built that endpoint because an operator cannot be expected to poll it, and #149 exists because a wrong load logged at INFO reads like a right one. A CONFIGURATION rule is loud wherever the entries came from. Never scope `toMap()`, and never widen the softening to a configuration rule. → ADR Decisions 36, 48.
- **How much of the prompt is this module's own reference material**: `ChartSearchAiUtils.referenceSlice(mappings)`, read off the answer as `ChartAnswer.getReferenceSlice()`; it reaches the audit row's `reference_slice_records` / `reference_slice_chars` (#229). Never re-derive it at a consumer, and never re-sum it inside `saveAuditLog` — by then the chart it measured is gone (#178). Resolved ONCE per `LlmInferenceService` method and the SAME object reaches every answer that method produces; `LlmInferenceServiceReferenceSliceTest` pins that by identity rather than equality, because two derivations over one chart are equal. **Null is not zero** and both columns are nullable for it: zero says the prompt carried no reference material, null says the producer stated no measurement. Zero says what the prompt carried and never why — so it is not evidence a corpus raises nothing, and the injector's log is what separates a swallowed failure from an honest miss. `ChartAnswer.getReferenceSlice()` is canonical for that; do not read its list of causes as complete, and note that the neighbouring `input_tokens`/`output_tokens` do NOT follow this convention. It counts the reference GROUP, so `active_drug_order` records are outside it. **A hardcode inside `referenceSlice` is caught since #354 added the third reference type** — `ChartSearchAiReferenceGroupTest.everyDeclaredResourceTypeConstant_isCountedIntoThePromptCostSliceExactlyWhenItIsReferenceMaterial` reddens on it, measured by mutation on that commit. `MAX_INTERACTION_RENDER_CHARS` is a per-record budget and deliberately not a bound on the NUMBER of records. → ADR Decision 57.

## Safety findings: strength, completeness and provenance

- **How strongly a finding licenses a clinical call**: `DrugSafetyValidator.licensesWithholding(SafetyWarning)` — of the FINDING, never of the rating alone (`ratingLicensesWithholding` is the weaker primitive) — and read its answer off the RECORD (the clause `renderFinding` appends), never by re-deriving it from the severity word in the prose. `minor` and `unknown` are cautions; `moderate`, `major` and **unrated** withhold, and unrated is not low-rated — `severityPriority` already sorts a curated rule above `major`. One definition, because the answer's strength and the chip's ordering must not disagree. The clause is **prompt-facing only**. The caution branch is **not a "Yes"** (#107 arm C): the graded lead states the drug can be given and names the caution, and `LlmProviderTest`'s never-"Yes" token stays pinned.
  - **Every finding the model reads states exactly one clause, and silence is not another answer.** A CONTRAINDICATION states a withholding-class clause; #283 scoped the clause to interaction findings once and that was measured wrong. An OVERDOSE finding cannot reach `renderFinding` today and wants NO clause; it falls to the empty default, **and that default is a defect waiting on a caller, not a safe fallback** — whoever makes the arm reachable gives it its own clause in the same change. → `SafetyFindingSeverityStrengthTest.everyInjectedFindingStatesExactlyOneStrengthClause`.
  - **STRENGTH and REFERENT are two axes** (#348). A finding about a medication the patient is ALREADY TAKING states the counterpart clause of the same strength; the referent is `SafetyWarning.isAboutACurrentMedication()`, **set by the arm and never read off the detail**, true only from the two ORDER-DRIVEN arms — and from the contraindication arm only where no SIBLING ROW put the substance in play, because its chips fold on the SUBSTANCE while its own skip is row-scoped. **Both arms or neither, both classes or neither, and a clause with no prompt branch quoting it is inert.** → ADR Decisions 68, 44; `CurrentMedicationFindingStrengthTest.everyFindingOnAScreeningQuestionStatesOneVocabulary`.
  - **A SET of findings states one lead, decided by the STRONGEST**, and the ranking must name the loser as well as the winner: the phrase `a reason to withhold it` occurs inside `STRENGTH_CAUTION` negated, so a bare antecedent is satisfied by a caution read shallowly. That nesting is of the class PHRASES, not of the clauses, and it is the only one the four have. Do not rest the lead on emission ordering, and do not word it as a fallback — `LlmProviderTest` fails the safety paragraph on the substring `otherwise` in any casing (#107 arm D). → `SafetyVerdictSeverityGradationTest.aSetOfFindingsStatingDifferentStrengthsIsLedByTheStrongest`, `.aSetMixingAProposalCallAndACurrentMedicationCallIsLedByTheStrongest`, `.theOnlyStrengthClassNamedInsideAnothersWordsIsTheOneDecision37Handles`.
  - **A FOLDED finding takes the stronger claim**, which is why the question is asked of the warning: #171's fold puts the class arm's sentence onto a rated rule's chip while `getSeverity()` keeps reporting the RULE's rating. `SafetyWarning.carriesUnratedRelationship()` carries the fold across.
  - **Which finding a TRUNCATED answer keeps is decided by the order the arm appends in, so order on the FINDING and never on the rating** (#346). The two pairwise arms rank on `severityPriority` alone; the drug-in-play arm is the one that FOLDS, so `DrugSafetyValidator.FINDING_STRENGTH_DESCENDING` asks `licensesWithholding` first and only then `severityPriority` — ordered on `getSeverity()` alone a folded Minor that withholds sinks below the cautions it outranks. Two stated limits, both deliberate: its unrated class-only chips trail its rule chips, and it sorts per drug IN PLAY, so a response carrying two subjects is not one ranked list. → `DrugInPlayFindingStrengthOrderTest`, and `DrugInPlayFindingStrengthKeyOrderContextTest` for the KEY ORDER — a folded `unknown` under a lowered floor is the one arrangement the two keys answer differently, so swap them and read its failure; `DdiDrugReferenceSourceTest.replacingAGroupsWinnerLeavesATiedPartnerBehindIt` is what pins the collapse's own half of the order now that severity decides the rest.
  - **The graded lead is a THIRD verdict class, and any gate reading the answer's lead has to know it.** `caution_led` lives in `eval/drift-metric/score_probe_safety.py` and never in `score_directness.classify`, the locked metric for the directness gate. Counting the lead without `unsupported_caution` beside it is fail-open; so is counting it into `verdict_led` without the A/B comparing the CLASS. **The lead is ANCHORED on the cell's own drug and nothing but name material may stand between that and the modal**, two rules neither subsuming the other. **The marker list is gone; do not reintroduce one.** A cell with no drug scores false. Whether the RATING licenses a caution is deliberately not checked — that is `licensesWithholding`, and a second copy in Python is the drift `adverse_finding` refuses. A shape that evades the anchor is a new case in `CAUTION_LEAD_CASES`, not a looser anchor. → ADR Decision 37 for what each rule was measured to hold; `eval/drift-metric/fixtures/probe-safety/caution-over-major/`.
  - **Pin the PREMISE, not the conclusion, and do not let that guard look better defended than it is.** `SafetyFindingSeverityStrengthTest.theTypeThatStatesNeitherClauseCannotReachTheRendererBeforeThereIsAnAnswer` reddens when the dose arm becomes reachable from the injector. `.everyInjectedFindingStatesExactlyOneStrengthClause` does NOT, because it iterates the findings ONE fixed arrangement produced and no arrangement of `injectRecords` produces an overdose finding. → ADR Decision 37.
- **Which of this patient's own orders a finding says its substances came from**: `DrugSafetyValidator.chartOrderBridges()`, read off the warning as `SafetyWarning.chartOrderBridges()` and rendered by `DrugReferenceInjector.chartOrderClause` off `FINDING_CHART_ORDER_LEAD` — the bridge that makes a finding about a brand-named prescription citeable at all (#349, where a Major chip stood beside an answer denying the records addressed interactions). **One shared method, called at each arm's chip-wording site and never re-derived by the injector** — a second walk there is the two-resolutions-that-agree shape #151 forbids. It is NOT decided inside `interactionWarning`, which takes the list as a parameter, so each call site needs its own case — neuter one to an empty list and read the failures. It is a RESOLUTION and never an identity, so it states no class membership of the prescription and #339's rounds 5-6 do not reach it.
  - **The SUBJECT is attributed against every order; the PARTNER only against the orders its own arm let witness it, and the CALLER supplies that set.** `addActiveOrderPairInteractions` hands `ordersOtherThan` (the same `resolvesFromAny` reduction `activeOrdersOtherThan` performs, which exists so one prescription cannot report the two halves of one tablet as an interacting pair); `addInteractionWarnings` makes no such reduction and hands the whole list. Doing the reduction inside the helper for both arms left the partner unbridged on a combination prescription — #349's own defect inside the clause that closes it.
  - **The silence test is the order's RECORDED NAMES against the substance (`recordsANameOf`), never the string the chip prints.** A printed name is a `displayLabel()`, which `matchesOrderName` can only match whole, so putting it to the display bridges `Aspirin 81mg` as if the chart named nothing. The condition is "`resolvesFrom` is true and its NAME leg is not what made it true", i.e. the ATC leg alone.
  - **An order the module could read no name for bridges nothing** — through `displayNamesADrug`, which since #349 has a third caller asking it for a third reason: whether a display is worth PRINTING beside a name that stays. That is not the LABELLING case CLAUDE.md exempts, because here the refusal is the point.
  - **Prompt-facing only, so `StatedInteractionChips` must NOT key on it** — that key decides which chips are emitted. → ADR Decision 64; `InteractionFindingChartOrderBridgeTest.aCombinationOrderCarryingBOTHSubstancesBridgesBothSides`, `.eachSubstanceIsAttributedOnlyToTheOrderThePassResolvedItFrom`, `.anOrderNamingTheSubstanceOnlyByAnAliasIsNotBridged`, `.theChipDetailIsTheWordsItAlwaysWas`.
- **Whether a reported interaction list is COMPLETE**: `ChartAnswer.getPairChipExtent()` (the wire's `interactionPairs`), stated by THREE arms through the `PairChipExtent.Sink` that `LlmInferenceService` hands `DrugSafetyValidator.validate` — never re-derived at a consumer, and **never inferred from the chip count**: `getReported()` counts above-floor rule PAIRS while `addInteractionWarnings` raises `interaction` chips of its own into the same list, so a client counting chips publishes a ratio of two things. That was #336, where a truncated screen left 0 signals on the wire. **The two PAIRWISE arms speak first and are never summed with the third** (#356): their statement is about a list a cap can truncate, the drug-in-play arm's is not, and that arm states `of(n, n)` only where neither of them did. **What it counts and what it does not**: this arm's rule chips for the substances the QUESTION put in play — unrated rules included, since `clearsSeverityFloor` exempts them — and never its unrated class chips (neither pairwise arm has a class leg) nor a chip raised for a drug only the ANSWER named — an extent accumulated over `inPlay` states one for a question that resolved no drug, which is #336's defect reversed. A chart recording no active medication states nothing, and that is deliberately unlike the screening arm, which states `of(0, 0)` on the same chart. **Zero is a measurement and absence is not** — `found == 0` says an arm ran and related nothing; `null` says the producer stated nothing. Never read `null` as completeness. Published once, on `validate`'s normal return, from a local the three arms assign — never per arm, or a degraded pass would describe chips its fail-safe had discarded. The statement is a COUNT and deliberately not the withheld list. It must reach every surface carrying chips, which is why `ChartSearchAiRestController.putSafetyChips` writes both keys and `ChartSearchAiInteractionPairExtentTest` fails the build on a second write of the `safetyWarnings` KEY. A synthetic chip is refused (it would reach the prompt with neither strength clause and break `getType()`'s three-value contract). → ADR Decisions 60, 65; `PairChipExtent`'s class javadoc for what `null` covers; `PairChipExtentContextTest.aDrugInPlayScreenThatRelatesNoActiveOrderStatesZeroRatherThanNothing`, `.aDrugOnlyTheAnswerNamedStatesNothingOnItsOwn`, `.aDrugTheAnswerAddsIsNotCountedIntoTheQuestionsOwnScreen`, `.aClassOnlyRelationshipIsNotCountedAsAPairFound`.
- **Whether an injected record may state what THIS patient's chart records**: FOUR questions, four predicates; conflating any two produces a confident false statement in citable evidence (#208 item 2).
  - **Does the chart record it?** `DrugSafetyValidator.recordedContraindicationKind()` — the chip arm's own match, shared and never copied.
  - **Could the module even ask?** `DrugSafetyValidator.evaluatesAgainstTheChart()`; its token half is the matcher's own emptiness rule (`PatientClinicalContext.matchableToken`), extracted from `containsToken` so "not matchable" and "did not match" cannot drift.
  - **Was the chart read at all?** `PatientClinicalContext.contraindicationRecordsRead()` — **a chart the module could not read is not a chart that records nothing.** The builder swallows a failed allergy or condition read into an EMPTY set: right for a chip, wrong for a record that would then tell the model this patient records none of a drug's contraindications *because nobody looked*.
  - **Does anything CORROBORATE that match?** `DrugSafetyValidator.corroboratedByTheChart()`, the UNION of `aMatchedRecordNamesTheEntry()` and `allergicSubstanceKeys()` (#269) — one spelling both injected channels ask since #308. The fourth question exists because the first predicate's match is deliberately BARE containment. **Neither half of the union is right alone and they fail in opposite directions**; the union is MONOTONE and that is the whole argument for it. Scoped to a self-named ALLERGY rule, exactly as the chip's demotion is, and load-bearing — mutate the scope out and read the failures.
  The composed gate is `DrugReferenceInjector.statesTheChartsContraindicationReading`, which also requires `DrugSafetyValidator.reportsContraindications()` (both `drugSafety` toggles) because the reading is the record's half of a chip and must not outlive one, and is decided ONCE per injection so two records of one chart cannot disagree. **The remedy is a THIRD named section that asserts nothing about the patient, never a denial** — and its lead states what the MODULE established rather than a categorical about the chart, because both legs can miss a recorded allergy that really does name the drug. `DrugReferenceInjector.FINDING_UNCORROBORATED_MATCH` is appended by `renderFinding` off `SafetyWarning.restsOnAnUncorroboratedChartMatch()`, set from this same predicate — a second copy there is how the two records would come apart again, silently. **Do not read that as licence to move the strength**: ADR Decision 42 deferred whether the finding states its PROVENANCE, not its strength. Never silence either. **The rule under all of it: never render silence as denial, and never render an accident as the chart's own words.** A negative claim needs the three chart-reading answers; a POSITIVE one needs the first, third and fourth (never the second — a matched rule is evaluable by construction); a chip needs only the first. → ADR Decision 42.

## Contraindications and chip scoping

- **Which collapse unit a contraindication rule is on**: `DrugSafetyValidator.contraindicationFinding()`, and `selfNamedAllergyRule()` for the one question the key turns on. A rule's key is its normalized `(type, token)` — **except** an ALLERGY rule whose token is one of the subject entry's own names, which reports the allergen arm's fact and is keyed on the SUBSTANCE so the two fold into one chip (#146). Which wording survives is decided by CONTENT and never by arm (#88 settled that "arm X yields to arm Y" is the wrong dedup whenever the yielding arm can carry the content). The chip ledger (`ContraindicationChips`) and `DrugReferenceInjector.contraindicationSections` key on that unit precisely so one recorded allergy cannot be one chip and two clauses (#190 item 1).
  - **A note is necessary and NOT sufficient** (#223). The fold's premise is that such a rule reports the allergen arm's fact, and `PatientClinicalContext.hasAllergyToken` is bare containment deliberately. So `contraindicationRank` asks a second question, **of the RECORD rather than the whole list**: it takes the witnesses (`allergensMatching`, sharing the boolean's own primitives so the two cannot drift) and puts each to the entry through `matchesDrugName`. A rule none of its matched records names is `SELF_NAMED_RULE_MATCHED_BY_CONTAINMENT_ALONE`, below `IDENTITY` — still raised, since the arms fire on different evidence. Ask it per witness and against the ENTRY.
  - **Tightening the MATCH instead was measured and declined** — it trades a false positive for a false NEGATIVE in a safety net, all its losses on the CLASS token `penicillin`, and makes one property structurally unconstructible.
  - **The self-naming test is `DrugReference.isNamed`, never `findImpliedSubstances`.** Both operands are canonical REFERENCE strings, so the question is name identity; a curated token may name a CLASS (`nsaid`), and resolving tokens to entries wholesale collapses a class-level rule into an identity chip (#160). What bounds the fold to its own subject is not the predicate but that it is asked OF the entry the rule is filed on.
  - **Since #308 the corroboration answer (`DrugSafetyValidator.corroboratedByTheChart`) over that unit has two spellings that must move together** — `contraindicationSections`' MAX for the record and `addContraindications`' fold for the finding. Deliberately not unified, and deliberately over the SAME unit. **The unit is TWO stages, not one**: after the key, the record resolves its three sections over clause TEXT, since two rules of different keys may render one string. **And that stage is asked of TWO strings** — `contraindicationClauses` JOINS the distinct notes a key collapses while a finding prints the winning rule's note alone. There is **no** third conjunct reading the key fold at that read site, and its absence is deliberate. What the map's OR still decides is which rule of a key carries it. Resolving it in `ContraindicationChips` instead is wrong twice: that key is the SUBSTANCE, and the gate skips rules before they arrive to be folded. **One unit buys agreement about one ROW, not about one substance** — a sibling row's sentence can replace the rendered row's and bring its own corroboration answer. → ADR Decision 44 (both directions, one case each); `UncorroboratedFindingProvenanceTest.aClauseAnotherKeyOfThisEntryStatesAsRecordedIsNotHedged`, `.theWordsTheFindingPrintsAreNotHedgedWhereAnotherKeyStatesThemAsRecorded`, `.oneCorroboratedRuleOfACollapsedKeyClearsTheClauseForTheWholeKey`, `.aRuleTheSubjectMatterGateSKIPSStillCarriesItsClausesCorroboration`.
- **Whether an ORDER-DRIVEN contraindication chip may be raised at all**: the active-order arm is scoped to what the RESPONSE is about, and `DrugSafetyValidator.SubjectMatter` is the only thing deciding it. A chip is raised where either SIDE is in subject matter — the drug (`names(DrugReference)`) or the recorded finding the rule fired on (`names(Contraindication)`, asked of the rule's OWN token and never the patient's whole list) — plus three widenings read off the question through `QueryScopeRouter.asksAboutMedications`/`asksAboutAllergies`/`asksAboutConditions`. Three and not two, and asked per LIST: the recorded side is an allergy OR a condition, and a conditions question must not widen her allergy records as well, or the three collapse into "asks about her chart". **Do not re-widen it to "every active order on every question"** — that was #143's over-reach and a category error: this module answers questions and has no subscription, acknowledgement or unprompted delivery path, so an unconditional finding here is an alert with none of an alerting system's machinery (measured live: four different questions returned the same two chips byte for byte). Do not narrow it either — to the drug side alone loses a chip whose ALLERGY was what was asked about; to a topic-intent gate loses `Can I give her bupivacaine?`. What is deliberately given up is announcing a prescribing error nobody asks a drug-shaped question about; that belongs on a surface with acknowledgement. **Its corpus is the CITED records and must never be the echo test's** (#360): those two were one list until the echo test widened to take in the RECITABLE reference records uncited, and an injected record names the patient's own prescriptions — so a shared list makes her prescription subject matter on a question about her cancer, which is the gate's DRUG side. It exposes the FINDING side too, a note-less rule rendering its token verbatim into the record's clauses, and nothing pins that half. `DrugSafetyValidator.AttributionTexts` allocates them separately for that reason; alias them and read the failure. → `ActiveOrderContraindicationTest.aPrescribedAllergyIsNotRaisedWhereTheResponseIsAboutSomethingElse`, `SubjectMatterScopedContraindicationTest.anUncitedReferenceRecordNamingHerPrescriptionIsNotSubjectMatter`.

## Active orders and co-medications

- **Which reference entries the patient's ACTIVE ORDERS are**: `DrugReferenceService.findForActiveOrders()` — ATC ∪ name, and the one list every consumer takes. `findByActiveOrders` is the ATC-only primitive underneath and answers a different question — *which of those orders did a DICTIONARY map to ATC* — which is not a slightly smaller answer but one that can be **empty**; the sparsity is the dictionary's, never the reference data's. It is package-private for that reason: do not widen it back, and never build a candidate set from it. That admission was #151, and how it failed is the part to remember: the injector resolved the primitive while `validate` screened the union, so the two layers disagreed about which orders the patient HAD — **silently, and in one direction** — and the symptom reaching the clinician was a Major chip whose supporting reference record was simply not in the prompt. **The remedy is not two resolutions that agree**: wherever a caller already holds the resolved list, pass it down rather than resolving again. Since #255 that is taken for the PRE-ANSWER pass too — a PARAMETER and never a memo, so #172's constraint is met by the shape rather than by discipline. What travels is the INPUT and deliberately not the enriched CONTEXT. **The POST-ANSWER resolution stands and is a different question.** The list is **unmodifiable**, and that is a contract rather than caution: since #255 the list one caller holds can be the same object another reasons over. → ADR Decisions 58, 53; ADR Appendix A. (How many lines the widest arity's parameters span is a fact about the current declaration, not a rule — read the needles and its javadoc, not a number.)

- **Whether an order's DISPLAY is a name at all**: `PatientClinicalContext.ActiveDrugOrder.hasKnownName()`, and build the one order for which it is false through `ActiveDrugOrder.namedByCodesOnly()`. An active order the module can read no name for still reaches the per-order list (#290) — skipping it left its ATC codes in the flattened union with no order behind them, so ONE prescription became one duplicate-therapy chip per uncovered code. Its display is its own codes labelled as codes and its `names` set is **empty**, deliberately: that set is matched against chart prose, so a code in it would match free text — the cost being that this order class is uuid-only for the #118 reconciliation. **Ask before letting a display DISPLACE a name another source supplied, never before merely labelling something that has no other name** — and since #292 the question is `DrugSafetyValidator.displayNamesADrug(order)`, **two conditions neither of which is sufficient**: that the order answers `hasKnownName()` AND that its display is non-blank, because a blank display resolves to the bare ATC code, which is the absence of a name displacing one. `nameByOrder` asks it **of itself**, and since #298 the order-rung constructor does too, so no caller supplies the answer; what must not ask it is `recordNameSource`, which derives the name source from the flag. Never re-derive the question as "are its names empty" — a proxy the public constructor lets a caller falsify, silently losing a real drug name. `orderCarrying` prefers a carrier answering true, and falls back to the first only where NO carrier does, because then there is nothing better to pick — so two unnameable orders sharing one unnameable code stay list-order dependent, which no test covers. → ADR Decision 40.
- **Which of an entry's interaction rules the injected record renders, and in what order**: `DrugReferenceInjector.renderTier` — THREE segments, one predicate, and the only expression of that partition. Promoted (the chart names the partner and the rule clears `DrugSafetyValidator.configuredSeverityFloor`), then the rules the chart names that the floor FILTERED, then the dataset tail. `promotedCount` counts the first and `OrderedInteractions.chartNamedCount` the second, so `render` tells all three apart.
  - **Never re-express relevance as the floor.** One predicate answering both questions is what silenced the patient's own drugs while rendering the same "listed but unrated" sentence for strangers (#357). And never promote on relevance alone, which was measured and rejected — the comment in `orderedInteractionNotes` carries that measurement, and says which half of it this change does not cover.
  - **Each segment has its own rendering rule and they are not smaller versions of each other.** A PROMOTED note takes the segment-1 slot the budget yields to, and its full text while the budget allows (one that will not fit has always rendered compact). The FILTERED segment states the source's shared sentence on its first note and names the rest with their ratings, because that sentence does not vary between members and full-for-every-member spends the budget saying one thing. The dataset TAIL keeps its own representative behind both, keyed on "anything patient-specific was shown" and never on the promoted count alone, or the breadth it exists to supply is unreachable for exactly the patients it was written for. **That question has ONE name, `OrderedInteractions.nothingPatientSpecific()`**, read by `render` to decide whether the tail is CAPPED and by `orderedInteractionNotes` to decide whether it is SORTED: never re-derive `promotedCount + chartNamedCount` at either site, or a maintainer changing what `tailStart` counts — as #357 did once — has to remember a condition in another method. Its javadoc carries what that drift actually reddens, which is not nothing.
  - **`onePerPartner` reads the same tier**, so the collapse cannot discard the row that decides which segment a partner lands in — asked at BOTH boundaries, not just promotion's. Across tiers it can elect a LESS severe row, deliberately.
  - **Where NOTHING is patient-specific the tail IS the record, so it names up to `MAX_TAIL_PARTNERS_WHEN_NOTHING_PATIENT_SPECIFIC` partners in the compact `name (Severity)` form, most severe first** (#355) — not in full notes, which is the prose the model recited, and not in dataset order, where the cap evicts the entry's worst partner. `SEVERITY_DESCENDING` asks whether a note NAMES its partner FIRST, so a rule with no name to shorten to cannot take the one slot the budget cannot refuse; `InteractionNote` takes the RULE, never a precomputed flag. **Guard that key over the SHAPES `partnerLabel` distinguishes — the product of {absent, blank, non-blank} over the two fields its `firstNonBlank` reads — never one case per substitution, and assert every cell of that product is FILED rather than that every filed cell is asserted**; `InteractionNote.namesItsPartner`'s javadoc carries why, and what the matrix does not reach. → ADR Decision 66; `InjectedInteractionRelevanceOrderTest`, `InjectedInteractionRelevanceOrderContextTest` (the floor boundary is the CONFIGURED one, which the shipped floor cannot show), `DrugReferenceInjectorTest.aSubFloorInteractionIsNotPromotedEvenWhenThePatientIsOnThatDrug` (whose assertion #357 replaced, deliberately — the decision records it), `.withNoPatientRelevantPartnerTheDatasetTailStatesBreadthCompactlyMostSevereFirst`, `.aTailRuleWithNoPartnerToNameDoesNotDisplaceOneThatDoes`, `.everyRuleShapeThatNamesAPartnerLeadsANamelessParagraphAndEveryOtherShapeTrailsIt` (the shape matrix; the five single-substitution cases beside it are not subsumed by it and one of them, `.aNamelessRuleCarryingASeverityStillDoesNotDisplaceARowThatNamesItsPartner`, is what holds a re-derivation reading the SEVERITY).

## Naming a partner in a response

- **Naming an interaction partner**: `DrugSafetyValidator.partnerLabel()` — the rule's own match token, else its ATC code — is the GROUPING key for every rule chip (`SubjectRule.partnerKey`, `DrugReferenceInjector.onePerPartner`), not for a class-only chip, which is labelled by the ladder and always was. **Since #339 it is no longer what most rule chips SAY.**
  - **A RULE chip's rendered name is `DrugSafetyValidator.reconciledPartnerName`**, for EVERY rule chip in both active-order arms (#292's scope was the folded chip alone). This label survives only where that method declines. `CoMedications.partnerNaming` has three rungs — the ladder's `labelEntry`, `OrderPartner.substances`, and the co-medication this pass attributed a CHART-recorded ATC code to — because ONE prescription can resolve to two reference substances with a partner keyed on only one. The third rung asserts no identity; `unambiguouslyNames` still decides whether the name may be printed.
  - **A CLASS-only chip's name — and the class sentence of a folded chip whose arms did not reconcile — is `DrugSafetyValidator.classPartnerName`**: the ladder's label with ONE thing re-decided. Asking the row question at the rule chip alone was measured to be half a migration.
  - **Which ROW either of them displays is a second question and its answer is `SubstanceSubjects.subjectOf`, never the ladder's own election.** The ladder elects with `canonicalRow` alone; every other name slot elects with `interactionSubject`, and taking the ladder's answer at a chip site is #187. The ELECTION moves only the ENTRY rung — a label an ORDER supplied has no row to elect, and a bare code or `[ATC …]` is the absence of a name (#155/#290).
  - **Nothing else about that label is re-decided, and rounds 5–6 of #339 tried to re-decide one more thing.** On the ORDER rung every name available is a CONSTITUENT of a prescription the dataset cannot fully name, and `classRelationships` cites the shared subgroup over ALL of the partner's codes — so naming a constituent states a class membership false of the drug named, in text `renderFinding` copies verbatim into a citable `safety_finding` with `STRENGTH_WITHHOLD`. **The display stands on that rung.** The residue is the READING: a lead naming a prescription that contains the chip's own subject as well as its partner looks like a self-interaction, asserts nothing false, and is ONE name for one prescription. The refusal also read the QUESTION's drugs, making a prescription's name question-dependent. **Do not re-propose a second conjunct there**, and note the trade's ordering: what the reverted rounds bought was a legibility reading; what they cost was a false clinical claim in citable evidence.
  - **The gate is `unambiguouslyNames` (#296): the rule's token must name the ladder's entry MORE STRONGLY than any other substance** — a ranking, not an existence test, because `ddinter` writes aliases from the name AND the `rxnorm_name`, so "the token names something else too" is the normal state. `DrugReferenceService.uniqueStrongestClaimant` is the one definition of that comparison and the fold calls it rather than spelling it again; a tie still refuses. **Identity alone (`isNamed`) is measured false-permissive here and the first version used it.** Ask it of the `labelEntry` ROW's own claim, never its substance's strongest — and of the row about to be printed, which since #339 is a CHOICE of two: the row this RESPONSE elects, and, where the token does not claim that row, the ladder's own, asked again rather than carried over. That fallback is not cosmetic — electing alone turned a permit into a refusal and printed two names in one folded detail. **A contested token is admissible only at `NAME_IS_THE_DISPLAY_NAME`**, and the alias trim #296 added is load-bearing: untrimmed, `isNamed` and `matchesDrugName` disagree and the fold refuses what its gate admits.
  - **The ORDER path is a GATE, not a refusal.** Where the label came from an ORDER (`namingOrder`) the order's display goes to both sentences **only where the RULE's own token names that very order** (`namesNamingOrder` — `DrugReference.matchesOrderName`, narrowed from the patient's flattened name list to the one NAME about to be printed, `order.getDisplay()`, so it licenses nothing the rule match did not already license of that string). **It was `getNames()` until #293 and the narrowing is that issue's, not a tidy-up**: reading `drugNonCoded` made one order's names no longer provably one drug's, so a scan proved a fact about one name and printed another. What the narrowing gives up is a partner whose token names one of the order's OTHER names but not its display — #136's pre-existing shape, unpinned. Ask it of the one order `OrderPartner.namingOrder` carries, never of every carrier.
  - **`OrderPartner.recordNameSource` is the only writer of `namingOrder` or `namesADrug`, and no constructor takes them as separate arguments.** `reconciledPartnerName` still asks `!namesADrug` FIRST — two INDEPENDENT guards, and a change must keep both. **Nothing behavioural pins the branch order any more** (a consequence of #298, since the pair it protects against is now unconstructible); it survives on this rule and on ADR 40. **Do not reverse those branches to make the field load-bearing**, and do not reintroduce a caller-supplied pair. → `OrderPartnerNameSourceWritePathTest` scans the source for the SHAPE deliberately — its first version asked only that the right-hand side NAMED the flag, and an `&&`/`||` slip was green under it and under the whole behavioural suite.
  - **The chip and the injected `drug_reference` note name one partner one way (#297), WITHOUT sharing a string.** The fold decides BOTH names at once (`ReconciledPartner`) rather than the note asking the gate again — a second copy of those conditions is how the chip's own two sentences came apart. The record's name travels on the `SafetyWarning` (`reconciledPartnerNoteName`) and is never re-derived; a second walk to compare answers is the two-resolutions-that-agree shape #151 forbids. **Only the ENTRY rung moves the note.** Two conditions gate its adoption and neither is decoration: the name is handed out only for the very rule the fold was decided on, and only where the context carries per-order structure. **Not "the order rung has no dataset name to take"** — that premise is false; what `namesNamingOrder` HAS proved is that the token names that display, and handing the note a prescription DISPLAY would put a strength and formulation the KB knows nothing about into a list of that KB's own partners. Do not "restore" #292's state by making the chip re-adopt the token: that silences the #155 and #290 ladder pins. → ADR Decisions 39, 51.
  - **Widening the reconciliation to every rule chip gave one prescription two chips saying the same thing, which `DrugSafetyValidator.StatedInteractionChips` collapses.** This is NOT `InteractionPairs` (whose javadoc says why a repeat must not be recognised by rendered text — it answers the opposite question) and not `SafetyWarning.equals`, which deliberately does not exist so nothing DOWNSTREAM can collapse chips this module meant to keep apart (`InteractionRouteVariantTest`). Key on every field a consumer reads, never the detail alone; keep `InteractionPairs.add` OUTSIDE the collapse; and in the screening arm collapse where the candidate is COLLECTED, not after the cap, or a restatement is counted into `PairChipExtent` as a pair found and withheld. What it gives up is WHICH constituent, on the chip alone. Naming the constituent instead was declined: new clause structure in a sentence `DrugSafetyChipLabelTest` and #108 constrain, conditional on what OTHER chips the response holds.
  - **#121's invariant is scoped to the residue** where the dataset identifies no partner entry: the grouping key is this label case-folded, and the chip renders it only where nothing reconciled. Grouping runs before the reconciliation and is unaffected either way.
  - **Mutate each branch and read the failures rather than trusting a list** — and read them rather than counting them; a count published here was wrong by 5×. **Do not make an exclusivity claim** ("reddens exactly here", "the rest of the suite is green") — one was true when written and false when read, telling a maintainer the failure that mattered most was collateral. Dropping the `labelEntry != null` guard reaches the CODE-ONLY shape and dereferences null, so its failures are NPEs from a chip-naming site and are not confined to naming cases. → ADR Decision 63; `OneOrderNameAcrossOneResponseTest` (`.twoRulesAboutOneCombinationPrescriptionNameItOnce`, `.aPartnerIsNamedByTheRowThisResponseNamesItsSubstanceBy`, `.aClassOnlyChipNamesAPartnerByTheSameRowARuleChipDoes`, `.aPrescriptionNamingTheSubjectAndThePartnerIsStillNamedOnceByItsOwnDisplay`, `.aRuleWhoseTokenNamesTwoSubstancesKeepsItsOwnTokenOnAnUnfoldedChipToo`, `.onAFlattenedChartTheChipIsReconciledAndTheNoteIsNot`, `.aScreenOfACombinationPrescriptionStatesOneRelationshipOnce`); `PartialOrderCoveragePartnerTest.everyClassSentenceAboutAPartlyCoveredOrderNamesADrugThatPublishesTheCitedSubgroup`, `.aFoldedClassSentenceAboutAPartlyCoveredOrderNamesADrugThatPublishesTheCitedSubgroup`, `.theMergedPartnerIsNotNamedAfterHalfOfACombination`; `FoldedChipOnePartnerNameTest` (`.anOrderWithNoMatchTokensIsStillJudgedOnTheNameItIsAboutToPrint`, `.anOrderSuppliedNameTheRulesTokenNamesIsHandedToBothSentences`, `.aRuleTokenTheLaddersRowOnlyTiesKeepsItsOwnToken`, `.aRowTheResponseElectsButTheTokenDoesNotClaimFallsBackToTheLaddersOwn`, `.aRuleAboutAnotherSubstanceSharingTheCodeKeepsItsOwnToken`, `.aBlankDisplayWithNamesNeverHandsItsCodeToBothSentences`, `.aPaddedAliasNamesTheOneOrderOnce`); `ClassChipPartnerLabelTest.anOrderTheDatasetDoesNotCoverIsNamedByItsOwnDisplayName`; `NonCodedDrugOrderNameTest.aRuleNamedOnlyByTheFreeTextIsNotPrintedUnderTheCodedDrugsName`; `OneNameAcrossChipAndInjectedRecordTest.aReconciledNameReachesOnlyTheNoteItWasDecidedFor`, `.anOrderRungFoldStillLeavesTheNoteOnTheRulesOwnToken`.

## Chart assembly

- **Chart assembly**: Use `ChartBuildingStrategy.buildChart()` → `QueryStoreChartBuilder.build()`. Never fetch or serialize a patient chart by another path; querystore owns retrieval.
- **Which chart-assembly mode produced an answer**: `ChartBuildingStrategy.searchModeLabel(chart)`, read off the answer as `ChartAnswer.getSearchMode()`. Never re-derive it at a consumer from `chartsearchai.chartMode` or `chartsearchai.embedding.preFilter` — that was #178, where both audit-write sites branched on preFilter alone, so the shipped `CHART_MODE_DEFAULT` could not reach the `search_mode` column at all and a maintainer reading those rows was reading a constant. The label is computed from `PatientChart`'s own stamps (`isQueryScoped()`, `isPreFiltered()`), never a fresh GP read, which also means labelling needs no `Context`. Two consequences: every stamp must be carried across `DrugReferenceInjector.injectRecords`, which rebuilds the chart from scratch — a dropped stamp is lost silently and **fail-open**, which has happened twice; and `SEARCH_MODE_QUERY_SCOPED` is defined AS `CHART_MODE_QUERY_SCOPED`, so renaming that GP token silently rewrites every subsequent row for readers outside this module. → `ChartSearchAiAuditSearchModeTest` pins the four spellings as literals, because every other assertion compares a constant to itself.
- **Whether a chart record's drug order is still in force**: `SerializedRecord.getOrderActive()` — and `PatientChartSerializer.RecordMapping.getOrderActive()` where a consumer reads a built chart. Written in exactly ONE place, `QueryStoreChartBuilder.toSerializedRecords`, the funnel all three build paths share; never re-derive it, and in particular never from the rendered text. That was #317: `describesEndedOrder` read querystore's prose, which renders nothing for `auto_expire_date`, so an order that lapsed by its duration was invisible as ended. **It is three-valued and the third value is the guard** — `TRUE` in force, `FALSE` this patient's order and not in force, `null` the module cannot say. **The situations `null` covers are enumerated in exactly ONE place — the `SerializedRecord.orderActive` field javadoc — and every other site, this one included, points at it rather than restating it.** That list grew from three to four when the per-order guard was added, and three successive review passes each found further sites still saying three. Do not copy it here or into a decision; a second copy is a second thing to forget to update. Never collapse it to a boolean, and never read `isEmpty()` on an active-order set as "could not read" — an empty active set is a real and common state, and exactly the one the mark must fire on. It reads the patient's orders ONCE and keeps TWO sets out of that read: "absent from the active set" alone cannot tell an ended order from a record whose order the module cannot identify. **Evaluate each order in its own try** — `Order.isActive()` THROWS where `dateStopped` is after `autoExpireDate`, and core neither validates nor refuses to write that pair, so one such row inside a chart-wide try silently takes the mark off every record for that patient. **`describesEndedOrder` is now AND-ed with this, never ranked against it** — neither overrules the other and each can only exclude more, which is what keeps the #118 name fallback intact. Do not "simplify" it into a precedence rule: three separate texts said precedence before review read the condition. Scoped to `drug_order` deliberately. Mutate the guards and read the failures — but do not read a surviving mutation as proof the suite is weak: some are pinned only structurally, and the null-patient and null-uuid checks are unreachable and defensive only. → ADR Decisions 46, 47.
