# Rules

- When a test fails, fix the pipeline/production code — never weaken assertions, revert test data, or change expected values to match wrong behavior.
- Prefer root-cause fixes over incremental symptom patches. Diagnose *why* something is broken before proposing a fix. Start with the best solution, not the quickest.
- Before claiming the filter is correct, verify what it actually returns — check the records, not just the count or the final answer. A filter returning 32 irrelevant records is not correct even if the LLM produces the right answer from them.
- Do not go in circles analyzing a problem without fixing it.
- Tests must call the actual production pipeline — no simulations, mocks, or reimplementations of pipeline logic in test code. This includes unit tests for internal methods: do not call internal methods directly with hand-crafted inputs. Every test must exercise the full production code path using real data (e.g. the patient test datasets and the real querystore-backed retrieval path).
- The same rule applies to any script that **measures** the knowledge base for a figure you will quote in javadoc, a PR body or an issue: call the production predicate, do not re-express it. Measured 2026-08-07: a Python reimplementation of `substanceKey` disagreed with production on family counts (126/119/6 against the true 129/119/7), and two issues still carry unreconciled KB-wide figures because of it. The predicates here (`substanceKey`, `normalizeAtcToken`, `isLocallyAppliedAtcCode`, `containsBoundedToken`, `canonicalRow`) carry accumulated special cases that a fresh implementation quietly drops, so a script that is 98% right produces plausible numbers that are wrong in exactly the tail being investigated. Compile against the built jar or drive the real code through a throwaway test, and say which method produced any figure you record.
- When a multi-step pipeline exists (e.g. normalize → transform → embed), tests must call the composed production method, not manually chain the individual steps. Manually chaining steps in tests can mask bugs where the production code assembles the pipeline differently. If no composed method exists, extract one and use it from both production and test code.
- Tests are the specification. Modifying tests to make them pass is changing the spec — only fix the production code to satisfy the existing tests.
- Before presenting changes, review your own diff multiple times. On each pass, check every item below. Keep reviewing until a pass finds nothing to fix.
  1. Does the change match the plan?
  2. Is the logic correct — edge cases, off-by-one errors, null/empty handling?
  3. Are there any regressions — does existing behavior stay intact?
  4. Is anything missing — incomplete implementation, forgotten call sites?
  5. Does it use the real production pipeline, not a simulation or mock?
  6. Were any tests modified? If so, that's a rule violation — revert and fix the production code instead.
  7. Were all rules in this file followed?
- Follow test-driven development: for every bug fix or new feature, first write a failing test that defines the expected behavior, then write production code to make it pass. Write the strictest assertion — if it doesn't fail, tighten it until it does.
- Always create a plan before writing code. Read the relevant code, outline the approach, then implement.
- Never commit code with known regressions. When a change fixes one case but breaks another, the root cause is usually in shared infrastructure, not the individual call site — diagnose the shared problem before patching stages.
- Retrieval is owned by openmrs-module-querystore (issue #51). chartsearchai no longer has an in-process embedding/Lucene/Elasticsearch pipeline, scoring/ranking code, an embedding store, or a retrieval eval harness — do not reintroduce them. Retrieval changes *and retrieval-quality evaluation* belong in the querystore module (it owns the index and the e5-base-v2 embedder), not here.
- **Keep Bash output scoped — it is context, and the tail dominates.** Measured over one full `resolve-ticket` run: 329 Bash calls produced ~460k characters (~115k tokens, 22% of the window), and **33 of those calls produced 52% of it**. Three habits cost most of it and none of them bought anything. Never `cat` a file you are about to grep — one call printed two state files whole, 11k characters, to read four fields. Scope every recursive grep to `api/src`/`omod/src` and never to `.` — an unscoped one returned 9k characters of `.claude/worktrees/` hits and had to be re-run scoped anyway. And report a build as its FAILURES plus a computed total rather than every `Tests run:` line: that was 12% of all output across ~15 builds, and no finding in that run ever came from a passing line. **This rule does not reach reading production code.** File-region reads were the single largest category (38%) and are where the change itself came from — the same-substance gate, the invariants the change falsified in unchanged neighbours, and every citation checked rather than trusted. Trim the overhead, never the reading.

# API surface rules — do not bypass these methods

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values.

- **Prefixed text**: Use `ChartSearchAiUtils.buildPrefixedText(resourceType, text)`. Never call `getEmbeddingPrefix()` directly (it is private) or hardcode prefix strings like `"Clinical observation: "`.
- **Cosine similarity**: Use `ChartSearchAiUtils.cosineSimilarity()`. Never reimplement the formula.
- **Diacritic folding**: Use `DrugReference.foldDiacritics()`. Never call `java.text.Normalizer` or hand-roll a character map for this — the NFD-decompose-and-strip rule and its documented limits live in one place.
- **Matching a drug name**: three shapes, three accessors, and the choice is deliberate — do not swap one for another or widen one to serve another (#86, #128, #147). `DrugReference.matchesText()` for PROSE (a question, an answer, a rendered record: symmetric word boundaries), and `DrugReference.namedOccurrences()` when a caller needs WHERE a prose match sits rather than whether it occurs — every occurrence with its span, because since #270 the dose arm has to ask whether an occurrence is merely a sub-span of a rival's longer name, and one reported occurrence cannot answer that for a substance the clause names twice — never `String.indexOf` beside a `matchesText` gate, which was #260: the two disagreed in both directions and both silently, so a name the prose rule does not find (`penicillin` inside `penicillins`) vetoed a real dose and a name it does find (`paracetamol` written `paracétamol`) could not locate itself. `DrugReference.matchesDrugName()` / `DrugReferenceService.findByDrugName()` / `lookupByToken()` for a clinician-entered drug NAME (an order's display name, an allergen: left boundary plus up to two inflection letters). `DrugReference.isNamed()` / `normalizeName()` for IDENTITY between two reference strings (a rule token against an entry's aliases). This bullet settles only which BOUNDARY RULE a string shape gets — "does this string match this entry". For which CANDIDATES the string puts in play, that answer is a superset and the next bullet governs.
- **Which candidates a recorded string puts IN PLAY**: Use `DrugReferenceService.findImpliedByQuery(text)` for PROSE (a question, an answer) and `findImpliedByDrugName(name)` for a recorded drug NAME (an order's display name). `findByQuery`/`findByDrugName` are the unranked primitives underneath them and answer a different question — "does this string MATCH this entry", which is a strict superset of "which substances does it NAME" wherever one alias is shared by two substances. Never build a chip arm's or the injector's candidate set by iterating `matchesText`/`matchesDrugName` yourself: that was issue #209, where a name admitted a superset and a chip named a substance the patient was not prescribed (`Hydrocortisone butyrate` for a patient on `Hydrocortisone Injection vial 100mg`). The narrowing ranks the name an entry matched BY, never the whole string — `DrugReference.aliasesIn()`/`aliasesNaming()` are each their own boolean's witness and exist for this and nothing else, because prose has no claim strength and a recorded display name's strongest claim is usually mere containment. Both legs are needed together: the drug-in-play arm and the order-driven arm each skip what the other covered, so narrowing one alone leaves the chip standing.
- **Which substances a recorded drug name implies**: Use `DrugReferenceService.findImpliedSubstances(name)`. `lookupByToken()` answers exactly **one** row and is the primitive underneath it — reaching for it directly is how a combination allergen ends up checked against a single constituent (#193) and how a presentation filed apart from its parent moiety produces no chip at all (#195). Both failed **silently and closed**, which is the failure mode this feature exists to prevent. The widening lives here deliberately, in what the recorded *string* is read to name — not in `substanceKey` (identity) and not in `nameMatchStrength` (ranking); keep those three concerns apart.
- **Which of the substances a recorded name implies it actually NAMES**: Use `DrugReferenceService.findNamedSubstances(drugName, implied)`, and ask it before PRINTING a substance's own label in a sentence that reports the patient's record. It is a strict subset of `findImpliedSubstances` and answers a different question — that one is additive on purpose (#193/#195), because every substance a recorded name could denote must reach the class and cross-reactivity comparisons, while a sentence saying "the patient has a recorded allergy to X" may only name what the record names. Its equal-claimant leg admits a row on a rank TIE, and a tie is satisfied both by a combination the KB spells without a separator (`amoxicillin and clavulanic acid`, that leg's own reason for existing) and by two substances sharing one name that is neither's display name — and the second is a row the chart never mentions. That was #268: `findImpliedSubstances("ado-trastuzumab emtansine")` returns `[Trastuzumab, Trastuzumab deruxtecan, Trastuzumab emtansine]` over the shipped KB, so a Kadcyla allergy asked about Enhertu was told *"The patient has a recorded allergy to Trastuzumab deruxtecan."* **Never build a candidate set from it** — package-private for that reason, like `findByActiveOrders`, and the failure is fail-CLOSED and silent: a caller resolving with it drops every substance a name implies without naming, i.e. every class comparison the module makes. The narrowing is in what a sentence may SAY, never in what the arms may reason over. `DrugSafetyValidator.addAllergyContraindications` is the only caller; where a name does not name the row, its three sentences state the relationship instead of asserting the allergy (`X is contraindicated by a recorded allergy to "<charted token>"`), which also keeps `README`'s rule that a `detail` names its own drug and tells one finding from another (#238).
- **How strongly an entry claims a recorded name**: Use `DrugReference.nameMatchStrength()`. Resolution ranks the *claim* — an entry whose display name **is** the recorded name, then one of whose other names **is** it, then the earliest entry the name merely occurs **inside** — and earliest-match survives only as that last rank. Never re-rank by alias length or by preferring `canonicalRow`: both were measured and are worse (longest-alias repairs 43 of 54 mis-resolutions and breaks 34 that earliest-match gets right; `canonicalRow` renames a charted `Ketorolac (ophthalmic)` allergy and regresses #187). #192 deliberately left the candidate set identical and moved only the choice; since #209 this ranking also DECIDES the set, through `findImpliedSubstances` under `findImpliedByQuery`/`findImpliedByDrugName` — so it is no longer true that widening the set is `matchesDrugName`'s job alone. `matchesDrugName` still bounds which entries a name can reach at all; this ranks which of them the name NAMES.
- **Substance identity, and which row represents a substance**: Use `DrugReference.substanceKey()` / `substanceGroupKey()` to ask "are these rows one substance?", and `DrugReference.canonicalRow()` / `namesNoRoute()` / `namesItsSubstance()` to pick the row that names it. A substance has N rows in DDInter (route and formulation variants sharing one `rxnorm_name`), so anything that enumerates matching entries produces N of something unless it goes through these — that was #145, #162, #163, #174 and #186, one defect in seven places. Identity is decided by `drugbank_id` resolved **per substance-name family**, deliberately not by `rxcui` or `rxnorm_name` (both are shared by `Omeprazole` and `Esomeprazole`, which are different substances) and not by the display stem alone (#187). Several call sites now depend on these agreeing with each other; do not compute a local variant. **`canonicalRow` has TWO rungs, and their ORDER and the second one's GATE are both measured decisions rather than preferences (#250)**: route-qualification first (`namesNoRoute`), then — for two rows of ONE substance tied on that — the row the data files the family under (`namesItsSubstance`), and only for two rows of one substance because this fold is also applied to sets that are not. Do not move the second above the first, which is what #250's own "add a third rung" wording invites, and do not compare display STEMS instead of whole names. **ADR Decision 43 is canonical for what each of those three costs**, and it is not restated here for the reason the `foldedPartnerLabel` bullet gives: three copies of a rejected-alternative argument is how this file has come to contradict itself before. What belongs here is where each is pinned, because none of them was pinned before it was asked for: the reorder by `SubstanceNameRowTest.routeQualificationStillOutranksNamingTheSubstance`, the stem weakening by `theSubstanceNameIsMatchedAgainstTheWholeDisplayNameAndNotItsStem` and `noRouteQualifiedPresentationIsElectedToSpeakForItsSubstance` (it reddened NOTHING in the api suite before those existed), and the gate by `DuplicateTherapySelfChipTest.anOrderKnownOnlyByACodeTheRowItselfPublishesIsStillSkipped`. Mutate each and read the failures rather than trusting that list. For a chip's SUBJECT the two rankings compose in a fixed order and `DrugSafetyValidator.interactionSubject()` is where that composition lives: the row the patient's own record claims most strongly (`nameMatchStrength`) first, then `canonicalRow` among the rows tied on that (#194 — before #250, `canonicalRow` alone subjected a `Botulinum toxin type A` order on `Daxibotulinumtoxina`; the fold now reaches that row itself, and where the ordering is still pinned moved with the example, to the COVID pair in `OrderedSubjectRowTest.theOrderNamedRowIsNamedWhereTheFoldCannotReachIt`, whose rows tie on both rungs). Do not reverse the order (the fold first renames a charted presentation, which is #187) and do not call `canonicalRow` directly at a chip-subject site, including the dose arm's — one substance must not be named two ways in one response.
- **Whether an ATC subgroup may justify a clinical claim**: THREE predicates, and which one you want is decided by **the claim you are about to make**. `DrugReference.isLocallyAppliedAtcCode()` separates the code that classifies a SUBSTANCE from the ones that classify a locally applied presentation of it — **a preference between candidates wherever the caller holds no evidence about which presentation the patient was given, which is every caller but one.** `DrugSafetyValidator.sharedClass` is that rule and is unchanged: it still returns a locally applied subgroup where that is all a pair shares. Since #234 there is a second caller, `DrugReference.codesAtSites`, and it may DROP a code — a `D01B` systemic antifungal is not a skin presentation however plainly it sits under `D`. That is not a change of mind about the predicate and it is not a licence to veto elsewhere: what decides the dropping is `ATC_GROUPS_BY_SITE` against the order's own recorded route or dose form (`ActiveDrugOrder.getAdministrationTerms()`), and this predicate only refuses the `SYSTEMIC_USE_EXCEPTIONS` nested inside a site the chart already named. A caller with no such evidence gets the preference and never the veto — and adding a third caller means saying which of the two it is. `isUnclassifyingAtcCode()` is the DUPLICATE-THERAPY bar: a group that asserts nothing at all. `isPurposeOnlyAtcCode()` is the CROSS-REACTIVITY bar and **subsumes** it: a group that asserts a purpose but no chemistry. That ordering is what makes three lists composable rather than three overlapping ones — a group asserting nothing cannot assert a purpose either, so refusing it for duplicate therapy while admitting it for cross-reactivity would have the arms disagree about which claim is the stronger. `DrugSafetyValidator.sharedClass` takes the arm as a parameter and is the only caller of the latter two; **never ask one arm's question with the other's predicate** — routing a cross-reactivity question to `isUnclassifyingAtcCode` is exactly the conflation #183 exists to remove.
  **The two arms may legitimately name DIFFERENT classes for one pair. That is the settlement, not a defect** (#183/#184), and it is the part nobody expected going in. The preference among surviving candidates is still one method — that is #171 and it still holds — but the candidate SETS now differ, so where a pair shares a purpose-named subgroup and a chemically named one, duplicate therapy is honestly about the first and cross-reactivity about the second; naming them alike would make one of the two sentences false. Measured: 4 of the 3693 shipped-KB pairs that answer on both arms.
  **The criterion, stated so it can be re-applied.** A subgroup licenses only the claim its own published NAME asserts, and a residue ("Other …"/"Various …") inherits its parent's assertion recursively — *unless it contributes a term none of its ancestors' names carry*, which is what stops `J01DI` "Other cephalosporins and penems" inheriting a bare therapeutic tier and losing the chemical family that makes a cephalosporin allergy mean anything. A name stating a chemical family, a derivative class or a molecular TARGET licenses both claims (`R06AX` antihistamines is a receptor, `C01BD` a channel, `N01B` a sodium-channel action); one stating only an indication, an organism acted against, a therapeutic area or a diagnostic use licenses duplicate therapy alone (`S01AA` "Antibiotics"); one whose ancestry is residue all the way up to a bare LEVEL-1 anatomical main group licenses neither (`A16AX`). Level 1 and not level 2 — ATC's level 2 is its THERAPEUTIC tier, so a residue inheriting "ANTINEOPLASTIC AGENTS" does assert a purpose and two drugs sharing it are duplicate therapy.
  **Derived from the index, never from the reported cases.** All 939 level-4 names in the WHO ATC/DDD index were read and the criterion applied to each; it independently reproduces every decision `isUnclassifyingAtcCode`'s javadoc states (`R06AX`, `J01GB`, `N02AX` keep; `A01AD`, `D11AX`, `S01XA`, `D06AX` vetoed), differing only where #182 declares its own deliberate over-reach. That matters: #161's list was hand-picked, and its hardening found it incomplete in a way that **reproduced the defect it was fixing** (46 of 1090 pairs named a missing group, 21 of them moved there by the fix). Add a member only by re-deriving the criterion, and record the measured KB impact.
  **Do not re-propose a uniform ATC veto.** It was measured and rejected: of the 5266 cross-reactivity claims ATC licenses over the shipped KB, **3701 rest on a subgroup that names chemistry or a molecular target and only 1565 on purpose or on nothing**, so a blanket rule loses real signal **2.4× faster than it removes false claims** — the penicillins, cephalosporins, aminoglycosides, benzodiazepines and statins are all on the losing side — and the one curated cross-reactivity group the module ships replaces just 24 of the 5266. That trade is the whole reason the arms differ; without it the simpler uniform rule looks obviously right and is not.
- **Which of a substance's codes describe the presentation the patient was GIVEN**: Use `DrugReference.codesForRecordedAdministration(codes, recordedTerms)`, and read the terms off the order — `PatientClinicalContext.ActiveDrugOrder.getAdministrationTerms()`, every name the order's route concept and its drug's dosage-form concept PUBLISH, never the drug's NAME. Every name and not the elected one, through `PatientClinicalContextBuilder.addConceptNames` and never `addConceptName`, which the order-NAME path shares: `Concept.getName()` returns the locale-PREFERRED spelling ahead of the fully specified one, and on the 3.7.1 reference dictionary three of the nine site-naming routes are preferred under a spelling no term matches — 874 `In both eyes` against the FSN `Bilateral eye administration`, 877 `In both ears`, and 872 `Vaginally`, the only vaginal route there is. `containsWord` takes no trailing letters, so `eyes` misses `eye` and `Vaginally` misses `vaginal`, and reading one name left #234's own defect standing — silently, with a chip identical to the pre-fix one — for three of that dictionary's nine site-naming routes. Reading every name is the root-cause fix and a term list is not a substitute for it, because a vocabulary of site WORDS cannot reach a spelling that is not one — that dictionary also elects `OU`, `OD` and `OS` for its three eye routes. Do not widen `addConceptName` to do it, which would change which reference entries an ORDER's name reaches (`findImpliedByDrugName`). `SITE_TERMS` does carry the words those three elected names are built on, BESIDE the read — `eyes`, `ears`, `vaginally`, each an inflection of a term already in the list — so a dictionary publishing one of the two spellings and not the other still narrows. Two independent mechanisms, either of which reaches those three routes on the 3.7.1 dictionary: `UnmappedOrderAdministrationSiteTest.aRouteSpelledAsAnInflectionOfItsTermStillSelectsItsSite` pins the terms, each leg reddening alone when its own term is removed, and `ActiveOrderAdministrationTermsTest.everySpellingTheRouteConceptPublishesIsCarried` pins the read through its assertion on the TERMS — the one of its three that mutating `addAdministration` back to `addConceptName` reddens, its assertion on the CODES having stopped discriminating once `eyes` became a term. The widening cuts both ways rather than only towards narrowing: the same dictionary prefers `Rectally` and `Per NG tube`, whose FSNs are what `ROUTES_OF_ENTRY`'s refusal is spelled for. `DrugSafetyValidator.codesForThisSubstancesPresentations` — reached from `addPartnersForUnmappedOrders` — is the single production caller of it and of `narrowsAnyCode`, the only other thing that reads a recorded term against a code list, and that is the only place either belongs: a partner reached by NAME holds the dataset's codes for a whole substance, which cover every route it is marketed as, and `sharedClass` prefers the systemic one among them — so an unmapped `Hydrocortisone cream 1%` was named in a systemic `H02AB` chip the same order mapped to `D07AA02` does not raise (#234). Do not apply it inside `sharedClass`: that method compares two code sets for four callers, and the narrowing belongs where an order becomes codes, not where codes are compared. **The site table is a PARTITION of `LOCALLY_APPLIED_ATC_GROUPS`, not a list beside it** — `ATC_GROUPS_BY_SITE` plus `LOCALLY_APPLIED_GROUPS_NAMING_NO_SITE` account for all 17 of its prefixes, and `S` is expanded into ATC's own `S01`/`S02`/`S03` because "Sensory organs" names two sites at once. Written freehand it dropped `S03` "Ophthalmological and otological preparations", which the shipped KB uses (neomycin's ear codes are `{S02AA07, S03AA01}`), i.e. it discarded a site's own code — #161's hand-picked-list failure one level along; `UnmappedOrderAdministrationSiteTest.everyLocallyAppliedCodeInTheShippedKnowledgeBaseIsAccountedFor` is what fails on it, and it is a DATA guard over the shipped KB rather than a structural one, so a group absent from that KB still escapes. **A term must name ONE site**: `cream`/`ointment`/`lotion` are deliberately absent, because a cream serves skin, vagina and anorectum alike and the union reading is WORSE than none — hydrocortisone's `C05AA01` survives it and a chip that said `H02AB` says `C05AA`, a haemorrhoid preparation, instead. A form word is admitted only where the form serves one site and no other (`inhaler`). **`topical` is absent for that same reason and it is the removal that costs most** — ATC uses the word for the anorectum too (`C05A` "Antihemorrhoidals for topical use", quoted in `LOCALLY_APPLIED_ATC_GROUPS`'s own javadoc), and read as the skin it SILENCES a real claim: measured, an unmapped `Hydrocortisone eye ointment` recorded route `Topical` produced no chip where the same order recorded `Bilateral eye administration` produced the true `S01BA` one. And a term naming a route of ENTRY (`ROUTES_OF_ENTRY`) REFUSES the site walk rather than merely failing to match it, because a systemic route's recorded name can CONTAIN a site word — measured, `transdermal skin patch` matched `skin` and silenced a chip; the residue it does not reach is the spaced `sub cutaneous`. Mouth, gut and anorectal have groups and no terms, because `Oral`/`Rectal administration` are the systemic routes AND the way an `A01`/`A07`/`C05A` presentation is given. It **declines** — returning the codes untouched — where no term names a site and where the substance is filed under none at that site; and for SEVERAL orders of one substance the question is asked per order and of what the data can EXPRESS (`narrowsAnyCode`), never of what the terms merely NAME — the weaker reading shipped once, and a cutaneous cream then carried a nasal order of the same substance into the skin because the empty-set fallback is evaluated over the union; it can remove CODES and never a partner, because the alternative silences every unmapped order of the 157 shipped-KB substances filed on both sides of `isLocallyAppliedAtcCode` on no positive evidence. Measured 2026-08-28 through the real parser and predicates: all 46 active drug orders on the 3.7.1 demo record `Oral administration` or nothing, so it is inert there; ADR Decision 50 carries the per-site impact and the rejected alternatives.
- **Whether a citation may be grounding-verified**: Use `ChartSearchAiUtils.isGroundingDemoteOnly(type)`, a named view of `referenceGroup()`. **Never test `resourceType` against `drug_reference`** — that is how `safety_finding` was graded as chart evidence for two releases (#122), and the derived form exists so a new reference type gets the right treatment automatically instead of silently getting the wrong one. Measured 2026-08-09, and this measurement is about **this** site — a re-hardcode inside `referenceGroup`/`isGroundingDemoteOnly` themselves, or at the verifier's call site: it **survives all 1058 tests**, and only fails once a *fourth* injected type exists, so the test suite will not catch that regression when it is made. **That warning still holds here.** It no longer holds at the wire serializer, which is guarded — see the next bullet, and do not read that guard as covering this site. The same rule binds consumers of the wire format: `README:403` requires a client to treat every `group=reference` citation alike, and the reference frontend does not — since #201 it can no longer misread the grounding verdict (the wire withholds it), but it still keys its badge, its label and its chart-tab route off `resourceType`, so that half of #201 is a change in `openmrs-esm-chartsearchai`.
- **Whether a grounding verdict may be PUBLISHED**: the second consequence of that same classification, and `ChartSearchAiRestController.groundedForWire()` is the ONLY place a `grounded` value reaches the wire. A `reference`-group citation always serializes `null` there — never `true`, never `false` (#201) — because the verdict means "this citation is not about that record", only `group` tells that apart from a chart citation's "this claim may not be supported", and a client reading it as the latter rendered the module's own deterministic Major-interaction finding as *Unsupported*, in red. Never publish `ref.getGrounded()` directly, and never re-derive the carve-out from a type name here. Unlike the bullet above, this site **is** guarded: `ChartSearchAiReferenceGroundingWithholdingTest.theWireSerializerMustNotNameAReferenceGroupResourceType` reads every class file the controller compiles to and fails if any names a reference-group type, which works because `RESOURCE_TYPE_*` are compile-time constants javac inlines into the using class's pool. Measured 2026-08-13: it is the ONLY test that fails on a hardcoded pair in `groundedForWire` — the behavioural sweep beside it passes — and it fails again when that hardcode is moved into the nested `PatientResolution` class, which the guard's first version missed because it read only the outer class file. Its scope is exactly the controller's own class files; a hardcode anywhere else is still invisible to the suite.
- **What reference dataset is actually loaded**: Use `DrugReferenceService.getLoadStatus()` (or `GET /chartsearchai/drugreferencestatus`). Never re-read the global properties to infer it — the load is **lazy**, so a check made right after flipping a GP reads the *previous* source, which is exactly how a verification pass was fooled before #149/#154 existed.
- **Memoising anything derived from `getAll()`**: hold it in a **per-call local, never in a field** — #172's rule, binding `DrugSafetyValidator`, `DrugReferenceInjector` and `DrugReferenceService` alike. The reason **nine** comments across those three classes gave for it is **measured false**: they said `getAll()` is hot-reloadable and that a memoised entry outliving a reload fails the identity comparisons the safety arms make. Measured 2026-08-14, two ways. Statically, `DrugReferenceService.dataset` is written only by `ensureLoaded()` when it is null and by the package-private `setEntries` test seam, which has no production caller — the module registers no `GlobalPropertyListener` and exposes no reload endpoint; the service's own class javadoc has said "held for the life of the bean … requires a module restart" since the commit that added it. **Prefer the test to the date**: the static half is already pinned in-suite by `DrugReferenceLoadContextTest.loadStatusDoesNotDriftFromTheCachedEntriesWhenTheGlobalPropertiesChange` (there since #154), so read that rather than re-measuring by hand — and read it rather than a paraphrase, including this one. Live, flipping `chartsearchai.drugReference.sourceFormat` from `ddinter` to `atc` on a running server left `GET /chartsearchai/drugreferencestatus` reporting the DDInter entries it already had and a real `/search` still raising its chip — where a reload would have re-parsed the DDInter file with the ATC parser, loaded 0 entries and dropped the chip. `getCrossReactivityGroups()` is the same shape — written once by its own lazy guard, otherwise only by test seams. Do **not** extend that to one group's PREFIXES: `CrossReactivityGroup.setAtcPrefixes` is a production write path and must stay authoritative after a read, which is the separate reason stated on `containsAnyCode` itself. Same rule, different mechanism. **Keep the rule; replace the reason.** Two hold today: these beans are Spring singletons, so a field memo is one unsynchronized `HashMap` shared by every concurrent request — stale reads and lost updates possible, structural corruption possible — and SOME of these memos are keyed on something unbounded, so as fields they grow for the life of the JVM or answer for whoever asked first. Say which applies at a given site rather than reciting both, because the second does not bind every site: two of `orderPartners`' four memos are keyed on a per-request `ActiveDrugOrder` and `validate`'s recorded-allergen list has no key at all (a field version would key on the allergy tokens — patient free text), while `entryByCode` is bounded by the ATC code space and `findImpliedByDrugName`'s cache by the loaded entries' own aliases, so those two take only the singleton reason. The third is why the discipline is worth keeping rather than merely defensible: a module whose memos are all per call is one a reload path can be **added to later** without re-auditing every one of them, which is the honest version of the reload reason and the one that cannot rot. Never collapse it to a boolean, and never read `isEmpty()` on an active-order set as "could not read": an empty active set is a real and common state (one ended prescription, nothing active) and is exactly the state the mark must fire on. It reads the patient's orders ONCE (`getAllOrdersByPatient`) and splits them here with `Order.isActive()`, and it keeps TWO sets out of that one read, the second of which is not redundant: "absent from the active set" alone cannot tell an ended order from a record whose order the module cannot identify, and since the mark is keyed on querystore's `resourceUuid` contract, a drift there would otherwise make absence true of EVERY record and tell a clinician that every one of this patient's prescriptions had ended. Requiring the uuid to be one of the patient's own orders makes the mark a positive fact rather than an inference from absence. **Evaluate each order in its own try**: `Order.isActive()` agrees with `getActiveOrders` on every leg checked but THROWS where `dateStopped` is after `autoExpireDate` (the SQL just answers), and core neither validates that pair nor refuses to write it — so one such row, evaluated inside a chart-wide try, silently takes the mark off every record for that patient. **`describesEndedOrder` is now AND-ed with this, never ranked against it** — `DrugReferenceInjector.unrepresentedActiveOrders` admits a record to its substantiation corpus only where both leave it live, so neither overrules the other and each can only exclude more; that is what makes adding the second safe (it re-admits nothing prose refused) and what keeps the #118 name fallback intact for the drifted-uuid record it exists for. Do not "simplify" it into a precedence rule: three separate texts said precedence before review read the condition. Scoped to `drug_order`, deliberately — the read returns every order type, so widening to `test_order`/`referral_order` is a decision, not a gap in the data. Mutate the guards and read the failures rather than trusting a list — but do not expect every one of them to redden something, and do not read a surviving mutation as proof the suite is weak. Two were pinned by cases that passed for the wrong reason until a mutation said so; one is pinned only structurally, because a failed read and an empty reading are indistinguishable in output; and the null-patient and null-uuid checks are unreachable from the three callers and defensive only, so deleting them changes nothing and no test can say otherwise.
- **Which chart-assembly mode produced an answer**: Use `ChartBuildingStrategy.searchModeLabel(chart)`, and read it off the answer as `ChartAnswer.getSearchMode()`. Never re-derive it at a consumer from `chartsearchai.chartMode` or `chartsearchai.embedding.preFilter` — that was #178, where both audit-write sites branched on preFilter alone, so `queryScoped` (the shipped `CHART_MODE_DEFAULT`) could not reach the `search_mode` column at all. Measured on the standalone before the fix: **6036 rows, every one `full-chart`, no other value ever written** — a maintainer reading them to reconstruct what a clinician was shown was reading a constant. The label is computed from `PatientChart`'s own stamps (`isQueryScoped()`, `isPreFiltered()`), never a fresh GP read, for the reason `markQueryScoped` exists: a re-read can disagree with the read that built the chart, and it also means labelling needs no `Context`. Two consequences bind anything added here. Every stamp must be carried across `DrugReferenceInjector.injectRecords`, which rebuilds the chart from scratch — a dropped stamp is lost silently and **fail-open** (it reads as unstamped), which has happened twice. And `SEARCH_MODE_QUERY_SCOPED` is defined AS `CHART_MODE_QUERY_SCOPED`, so renaming that GP token silently rewrites every subsequent row for readers outside this module; the four spellings are pinned as literals in `ChartSearchAiAuditSearchModeTest` precisely because every other assertion compares a constant to itself and cannot see a rename.
- **Test datasets**: Use `TestDatasetHelper.FULL_PATIENT_DATASET`, `TestDatasetHelper.SECOND_PATIENT_DATASET`, `TestDatasetHelper.toSerializedRecords()`, `TestDatasetHelper.inferResourceType()`, `TestDatasetHelper.stripDatasetPrefixAndDate()`. Never duplicate these helpers in individual test files.
- **Category hints in tests**: Use `TestDatasetHelper.FULL_DATASET_CATEGORY_HINTS` (and per-dataset variants). Never duplicate hints maps in individual test files.
- **Stripping category hints**: Use `ChartSearchAiUtils.stripCategoryHints()`. Never reimplement the hint-detection pattern.
- **Saying an absent-data answer may name its topic two ways**: put the alternatives in `expectedAnswerContainsAny` (OR). **Never add a second element to `expectedAnswerContains` for that** — it is AND, so a second element makes the case stricter, which is the opposite of what a second correct name needs (#216). Neither list is the place to accommodate a wording you have not measured: an OR element is a new way to pass, and `AbsentDataEvalTest.anAnswerNamingNoTopicFailsEveryCaseThatNamesOne` reddens if one is loose enough to match an answer that names nothing. Where a single stem covers the variants (`smok`, `vaccin`) that stem in the AND list is the narrower expression and stays.
- **Inline citation markers**: `ChartSearchAiUtils.INLINE_CITATION` is the single parsing pattern and is deliberately single-index. Compact shorthand (`[6, 7]`, `[6/7]`) is normalized upstream by `LlmAnswerExtractor.normalizeSlashCitations(text, citations)` and ONLY when the structured citations array corroborates the group — never loosen the pattern or split bracket groups elsewhere; uncorroborated numeric brackets are clinical values (`[120, 80]`) and splitting them fabricates references.
- **Reading an index out of the structured `citations` field**: a different question from the one above, answered by `LlmAnswerExtractor.citationIndex()` — an integral JSON number, or a string that is entirely one integer (#219: the json_schema is enforced by the server, so a remote that approximates it can send `["9","10"]`, and an `isInt()` check dropped that in silence). The asymmetry with prose is deliberate and neither side may cite the other to widen itself: an array entry has no competing reading, so its TYPE is coerced and the coercion is reported at WARN, while a bracket in answer text can always be a clinical value, so it is not re-read. The widening is over types only — which VALUES are admitted is unchanged, and `LlmInferenceService.extractCitedReferences` remains the only thing that decides which indices become references. **The same accessor also reads the whole field when it is not an array** (#221, via `readNonArrayCitations`): that is deliberate, and the point of it — container and entries must admit exactly the same JSON types, and routing both through one reader is what stops them drifting apart. Do not give the container a rule of its own.
- **Whether a non-conformant `citations` field is reported**: it is, at WARN, in both shapes — an array whose entries misbehave (`reportNonConformantCitations`) and a container that is not an array at all (`readNonArrayCitations`). Two channels for one failure was the inconsistency, not the warning; #221's first draft logged the container at DEBUG on an "unobserved shape" argument that does not apply, since the branch cannot run unless a provider really did send an unusable field, and the default `org.openmrs.*` level is WARN so DEBUG is evidence for someone already looking rather than a signal that arrives. **The one silent case is an explicit `null`, and the reason is not "it is not an array".** It is what the container ASSERTS: `null` asserts ABSENCE — the same statement as an omitted field, from a provider whose answer cites nothing — so nothing is lost and nothing is guessed. Everything reaching `readNonArrayCitations` asserts PRESENCE of something unusable. Absence honoured is not a defect; presence discarded is. Do not fold the two on the strength of both being non-arrays.
