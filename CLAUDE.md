# Rules

- When a test fails, fix the pipeline/production code — never weaken assertions, revert test data, or change expected values to match wrong behavior.
- Prefer root-cause fixes over incremental symptom patches. Diagnose *why* something is broken before proposing a fix. Start with the best solution, not the quickest.
- Before claiming the filter is correct, verify what it actually returns — check the records, not just the count or the final answer. A filter returning 32 irrelevant records is not correct even if the LLM produces the right answer from them.
- Do not go in circles analyzing a problem without fixing it.
- Tests must call the actual production pipeline — no simulations, mocks, or reimplementations of pipeline logic in test code. This includes unit tests for internal methods: do not call internal methods directly with hand-crafted inputs. Every test must exercise the full production code path using real data (e.g. the patient test datasets and the real querystore-backed retrieval path).
- The same rule applies to any script that **measures** the knowledge base for a figure you will quote in javadoc, a PR body or an issue: call the production predicate, do not re-express it. Measured 2026-08-07: a Python reimplementation of `substanceKey` disagreed with production on family counts (126/119/6 against the true 129/119/7), and two issues still carry unreconciled KB-wide figures because of it. The predicates here (`substanceKey`, `normalizeAtcToken`, `isLocallyAppliedAtcCode`, `containsBoundedToken`, `canonicalRow`) carry accumulated special cases that a fresh implementation quietly drops, so a script that is 98% right produces plausible numbers that are wrong in exactly the tail being investigated. Compile against the built jar or drive the real code through a throwaway test, and say which method produced any figure you record.
- When a multi-step pipeline exists (e.g. normalize → transform → embed), tests must call the composed production method, not manually chain the individual steps. Manually chaining steps in tests can mask bugs where the production code assembles the pipeline differently. If no composed method exists, extract one and use it from both production and test code.
- Tests are the specification. Modifying tests to make them pass is changing the spec — only fix the production code to satisfy the existing tests.
- Before presenting changes, review your own diff multiple times. On each pass, check every item below. Keep reviewing until a pass finds nothing to fix.
  1. Does the change match the plan?
  2. Is the logic correct — edge cases, off-by-one errors, null/empty handling?
  3. Are there any regressions — does existing behavior stay intact?
  4. Is anything missing — incomplete implementation, forgotten call sites?
  5. Does it use the real production pipeline, not a simulation or mock?
  6. Were any tests modified? If so, that's a rule violation — revert and fix the production code instead.
  7. Were all rules in this file followed?
- Follow test-driven development: for every bug fix or new feature, first write a failing test that defines the expected behavior, then write production code to make it pass. Write the strictest assertion — if it doesn't fail, tighten it until it does.
- Always create a plan before writing code. Read the relevant code, outline the approach, then implement.
- Never commit code with known regressions. When a change fixes one case but breaks another, the root cause is usually in shared infrastructure, not the individual call site — diagnose the shared problem before patching stages.
- Retrieval is owned by openmrs-module-querystore (issue #51). chartsearchai no longer has an in-process embedding/Lucene/Elasticsearch pipeline, scoring/ranking code, an embedding store, or a retrieval eval harness — do not reintroduce them. Retrieval changes *and retrieval-quality evaluation* belong in the querystore module (it owns the index and the e5-base-v2 embedder), not here.

# API surface rules — do not bypass these methods

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values.

- **Prefixed text**: Use `ChartSearchAiUtils.buildPrefixedText(resourceType, text)`. Never call `getEmbeddingPrefix()` directly (it is private) or hardcode prefix strings like `"Clinical observation: "`.
- **Cosine similarity**: Use `ChartSearchAiUtils.cosineSimilarity()`. Never reimplement the formula.
- **Diacritic folding**: Use `DrugReference.foldDiacritics()`. Never call `java.text.Normalizer` or hand-roll a character map for this — the NFD-decompose-and-strip rule and its documented limits live in one place.
- **Matching a drug name**: three shapes, three accessors, and the choice is deliberate — do not swap one for another or widen one to serve another (#86, #128, #147). `DrugReference.matchesText()` for PROSE (a question, an answer, a rendered record: symmetric word boundaries). `DrugReference.matchesDrugName()` / `DrugReferenceService.findByDrugName()` / `lookupByToken()` for a clinician-entered drug NAME (an order's display name, an allergen: left boundary plus up to two inflection letters). `DrugReference.isNamed()` / `normalizeName()` for IDENTITY between two reference strings (a rule token against an entry's aliases). This bullet settles only which BOUNDARY RULE a string shape gets — "does this string match this entry". For which CANDIDATES the string puts in play, that answer is a superset and the next bullet governs.
- **Which candidates a recorded string puts IN PLAY**: Use `DrugReferenceService.findImpliedByQuery(text)` for PROSE (a question, an answer) and `findImpliedByDrugName(name)` for a recorded drug NAME (an order's display name). `findByQuery`/`findByDrugName` are the unranked primitives underneath them and answer a different question — "does this string MATCH this entry", which is a strict superset of "which substances does it NAME" wherever one alias is shared by two substances. Never build a chip arm's or the injector's candidate set by iterating `matchesText`/`matchesDrugName` yourself: that was issue #209, where a name admitted a superset and a chip named a substance the patient was not prescribed (`Hydrocortisone butyrate` for a patient on `Hydrocortisone Injection vial 100mg`). The narrowing ranks the name an entry matched BY, never the whole string — `DrugReference.aliasesIn()`/`aliasesNaming()` are each their own boolean's witness and exist for this and nothing else, because prose has no claim strength and a recorded display name's strongest claim is usually mere containment. Both legs are needed together: the drug-in-play arm and the order-driven arm each skip what the other covered, so narrowing one alone leaves the chip standing.
- **Which substances a recorded drug name implies**: Use `DrugReferenceService.findImpliedSubstances(name)`. `lookupByToken()` answers exactly **one** row and is the primitive underneath it — reaching for it directly is how a combination allergen ends up checked against a single constituent (#193) and how a presentation filed apart from its parent moiety produces no chip at all (#195). Both failed **silently and closed**, which is the failure mode this feature exists to prevent. The widening lives here deliberately, in what the recorded *string* is read to name — not in `substanceKey` (identity) and not in `nameMatchStrength` (ranking); keep those three concerns apart.
- **How strongly an entry claims a recorded name**: Use `DrugReference.nameMatchStrength()`. Resolution ranks the *claim* — an entry whose display name **is** the recorded name, then one of whose other names **is** it, then the earliest entry the name merely occurs **inside** — and earliest-match survives only as that last rank. Never re-rank by alias length or by preferring `canonicalRow`: both were measured and are worse (longest-alias repairs 43 of 54 mis-resolutions and breaks 34 that earliest-match gets right; `canonicalRow` renames a charted `Ketorolac (ophthalmic)` allergy and regresses #187). #192 deliberately left the candidate set identical and moved only the choice; since #209 this ranking also DECIDES the set, through `findImpliedSubstances` under `findImpliedByQuery`/`findImpliedByDrugName` — so it is no longer true that widening the set is `matchesDrugName`'s job alone. `matchesDrugName` still bounds which entries a name can reach at all; this ranks which of them the name NAMES.
- **Substance identity, and which row represents a substance**: Use `DrugReference.substanceKey()` / `substanceGroupKey()` to ask "are these rows one substance?", and `DrugReference.canonicalRow()` / `namesNoRoute()` to pick the row that names it. A substance has N rows in DDInter (route and formulation variants sharing one `rxnorm_name`), so anything that enumerates matching entries produces N of something unless it goes through these — that was #145, #162, #163, #174 and #186, one defect in seven places. Identity is decided by `drugbank_id` resolved **per substance-name family**, deliberately not by `rxcui` or `rxnorm_name` (both are shared by `Omeprazole` and `Esomeprazole`, which are different substances) and not by the display stem alone (#187). Several call sites now depend on these agreeing with each other; do not compute a local variant. For a chip's SUBJECT the two rankings compose in a fixed order and `DrugSafetyValidator.interactionSubject()` is where that composition lives: the row the patient's own record claims most strongly (`nameMatchStrength`) first, then `canonicalRow` among the rows tied on that (#194 — `canonicalRow` alone subjected a `Botulinum toxin type A` order on `Daxibotulinumtoxina`). Do not reverse the order (the fold first renames a charted presentation, which is #187) and do not call `canonicalRow` directly at a chip-subject site, including the dose arm's — one substance must not be named two ways in one response.
- **Whether an ATC subgroup may justify a clinical claim**: THREE predicates, and which one you want is decided by **the claim you are about to make**. `DrugReference.isLocallyAppliedAtcCode()` separates the code that classifies a SUBSTANCE from the ones that classify a locally applied presentation of it — a preference between candidates, never a veto. `isUnclassifyingAtcCode()` is the DUPLICATE-THERAPY bar: a group that asserts nothing at all. `isPurposeOnlyAtcCode()` is the CROSS-REACTIVITY bar and **subsumes** it: a group that asserts a purpose but no chemistry. That ordering is what makes three lists composable rather than three overlapping ones — a group asserting nothing cannot assert a purpose either, so refusing it for duplicate therapy while admitting it for cross-reactivity would have the arms disagree about which claim is the stronger. `DrugSafetyValidator.sharedClass` takes the arm as a parameter and is the only caller of the latter two; **never ask one arm's question with the other's predicate** — routing a cross-reactivity question to `isUnclassifyingAtcCode` is exactly the conflation #183 exists to remove.
  **The two arms may legitimately name DIFFERENT classes for one pair. That is the settlement, not a defect** (#183/#184), and it is the part nobody expected going in. The preference among surviving candidates is still one method — that is #171 and it still holds — but the candidate SETS now differ, so where a pair shares a purpose-named subgroup and a chemically named one, duplicate therapy is honestly about the first and cross-reactivity about the second; naming them alike would make one of the two sentences false. Measured: 4 of the 3693 shipped-KB pairs that answer on both arms.
  **The criterion, stated so it can be re-applied.** A subgroup licenses only the claim its own published NAME asserts, and a residue ("Other …"/"Various …") inherits its parent's assertion recursively — *unless it contributes a term none of its ancestors' names carry*, which is what stops `J01DI` "Other cephalosporins and penems" inheriting a bare therapeutic tier and losing the chemical family that makes a cephalosporin allergy mean anything. A name stating a chemical family, a derivative class or a molecular TARGET licenses both claims (`R06AX` antihistamines is a receptor, `C01BD` a channel, `N01B` a sodium-channel action); one stating only an indication, an organism acted against, a therapeutic area or a diagnostic use licenses duplicate therapy alone (`S01AA` "Antibiotics"); one whose ancestry is residue all the way up to a bare LEVEL-1 anatomical main group licenses neither (`A16AX`). Level 1 and not level 2 — ATC's level 2 is its THERAPEUTIC tier, so a residue inheriting "ANTINEOPLASTIC AGENTS" does assert a purpose and two drugs sharing it are duplicate therapy.
  **Derived from the index, never from the reported cases.** All 939 level-4 names in the WHO ATC/DDD index were read and the criterion applied to each; it independently reproduces every decision `isUnclassifyingAtcCode`'s javadoc states (`R06AX`, `J01GB`, `N02AX` keep; `A01AD`, `D11AX`, `S01XA`, `D06AX` vetoed), differing only where #182 declares its own deliberate over-reach. That matters: #161's list was hand-picked, and its hardening found it incomplete in a way that **reproduced the defect it was fixing** (46 of 1090 pairs named a missing group, 21 of them moved there by the fix). Add a member only by re-deriving the criterion, and record the measured KB impact.
  **Do not re-propose a uniform ATC veto.** It was measured and rejected: of the 5266 cross-reactivity claims ATC licenses over the shipped KB, **3701 rest on a subgroup that names chemistry or a molecular target and only 1565 on purpose or on nothing**, so a blanket rule loses real signal **2.4× faster than it removes false claims** — the penicillins, cephalosporins, aminoglycosides, benzodiazepines and statins are all on the losing side — and the one curated cross-reactivity group the module ships replaces just 24 of the 5266. That trade is the whole reason the arms differ; without it the simpler uniform rule looks obviously right and is not.
- **Whether a citation may be grounding-verified**: Use `ChartSearchAiUtils.isGroundingDemoteOnly(type)`, a named view of `referenceGroup()`. **Never test `resourceType` against `drug_reference`** — that is how `safety_finding` was graded as chart evidence for two releases (#122), and the derived form exists so a new reference type gets the right treatment automatically instead of silently getting the wrong one. Measured 2026-08-09, and this measurement is about **this** site — a re-hardcode inside `referenceGroup`/`isGroundingDemoteOnly` themselves, or at the verifier's call site: it **survives all 1058 tests**, and only fails once a *fourth* injected type exists, so the test suite will not catch that regression when it is made. **That warning still holds here.** It no longer holds at the wire serializer, which is guarded — see the next bullet, and do not read that guard as covering this site. The same rule binds consumers of the wire format: `README:403` requires a client to treat every `group=reference` citation alike, and the reference frontend does not — since #201 it can no longer misread the grounding verdict (the wire withholds it), but it still keys its badge, its label and its chart-tab route off `resourceType`, so that half of #201 is a change in `openmrs-esm-chartsearchai`.
- **Whether a grounding verdict may be PUBLISHED**: the second consequence of that same classification, and `ChartSearchAiRestController.groundedForWire()` is the ONLY place a `grounded` value reaches the wire. A `reference`-group citation always serializes `null` there — never `true`, never `false` (#201) — because the verdict means "this citation is not about that record", only `group` tells that apart from a chart citation's "this claim may not be supported", and a client reading it as the latter rendered the module's own deterministic Major-interaction finding as *Unsupported*, in red. Never publish `ref.getGrounded()` directly, and never re-derive the carve-out from a type name here. Unlike the bullet above, this site **is** guarded: `ChartSearchAiReferenceGroundingWithholdingTest.theWireSerializerMustNotNameAReferenceGroupResourceType` reads every class file the controller compiles to and fails if any names a reference-group type, which works because `RESOURCE_TYPE_*` are compile-time constants javac inlines into the using class's pool. Measured 2026-08-13: it is the ONLY test that fails on a hardcoded pair in `groundedForWire` — the behavioural sweep beside it passes — and it fails again when that hardcode is moved into the nested `PatientResolution` class, which the guard's first version missed because it read only the outer class file. Its scope is exactly the controller's own class files; a hardcode anywhere else is still invisible to the suite.
- **What reference dataset is actually loaded**: Use `DrugReferenceService.getLoadStatus()` (or `GET /chartsearchai/drugreferencestatus`). Never re-read the global properties to infer it — the load is **lazy**, so a check made right after flipping a GP reads the *previous* source, which is exactly how a verification pass was fooled before #149/#154 existed.
- **Whether a loaded dataset is VALID, and what the loader did about it**: Use `DrugReferenceValidity`, reported through `DrugReferenceLoad.getFindings()`. Never add a guard for one bad-data shape at its own call site. #150, #156, #196 and #211 were four such shapes in one code path — a blank alias that makes an entry contraindicate its drug for every patient with any allergy, two fallbacks that load a dataset nobody configured, a KB row publishing another substance's own name, and rows of one substance disagreeing about which carries the rules — and five separate guards would give five answers to what this loader considers valid. Two rules bind anything added here. **The remedy is decided per rule and never uniform by default**: drop the offending VALUE where the rest of the entry is usable (dropping more trades a fail-open for a silent fail-closed), repair only what the data already says (the display name an entry omits from its own aliases, which the `ddinter` and `atc` parsers add as they build theirs), and otherwise report — no rule refuses a file, because an additive net that refuses its dataset produces the inert safety layer #149 exists to flag. **A rule must stay silent on an untouched default**: both path GPs default to files the module never creates, so a rule keyed on "a path is configured and we fell back" fires on every install and is filtered within a week. Compare against `ChartSearchAiConstants.DEFAULT_DRUG_REFERENCE_DATA_FILE_PATH` / `..._CROSS_REACTIVITY_FILE_PATH`, which `GlobalPropertyDefaultsTest` pins to `config.xml`. Silence is the ABSENCE of a finding, never a muted one: every finding reaches both channels — WARN at the moment it happens, and `toMap()` (so `GET /chartsearchai/drugreferencestatus`) afterwards, carrying its rule, remedy and count. "Observable but not loud" was tried for the mistyped-`sourceFormat` case and ruled wrong: #154 built that endpoint because an operator cannot be expected to poll it, and #149 exists because a wrong load logged at INFO reads like a right one.
- **Which reference entries the patient's ACTIVE ORDERS are**: Use `DrugReferenceService.findForActiveOrders()` — ATC ∪ name, and the one list every consumer takes: the two order-driven chip arms, the subject rows `resolvedSubstanceRows` widens with, the names `withReferenceNames` attaches, and since #151 the candidate set `DrugReferenceInjector.matchingEntries` scopes order-driven injection over. `findByActiveOrders` is the ATC-only primitive underneath it and answers a different question — *which of those orders did a DICTIONARY map to ATC* — and that is not a slightly smaller answer, it is one that can be **empty**. Measured 2026-08-13 by the predicate `PatientClinicalContextBuilder.addAtcCodes` applies (a concept-reference-source name containing `ATC`), **27 of the 43 active drug orders on the 3.7.1 demo instance carry no ATC code at all**, while `DrugReference.normalizedAtcCodes()` over the real `DdiDrugReferenceSource.parse` of the 19 MB KB publishes codes for 1839 of its 2283 entries — the sparsity is the dictionary's, never the reference data's, so a rule that reads the ENTRY's codes and a set that reads the ORDER's codes are answering off different keys. It is package-private for that reason: do not widen it back, and never build a candidate set from it. That admission was #151, and how it failed is the part to remember: `matchingEntries` resolved the primitive while `DrugSafetyValidator.validate` screened the union, so the two layers disagreed about which orders the patient HAD — **silently, and in one direction**, the injector's answer always the smaller — so nothing errored, no count looked wrong, and the symptom reaching the clinician was a Major chip whose supporting reference record was simply not in the prompt. **The remedy is not two resolutions that agree.** `injectRecords` already resolves this once for its own promotion predicate and hands that list to `matchingEntries`, so the injector has no opinion left to keep in step; wherever a caller already holds the resolved list, pass it down rather than resolving again.
- **Naming an interaction partner**: Use `DrugSafetyValidator.partnerLabel()`. The chip and the injected record share it precisely so they cannot name one partner two ways.
- **Which partner a rule is about**: Use `DrugSafetyValidator.activeOrderEntryFor()`. Both surfaces that group per partner — `bestRulePerPartner` for the chip and `DrugReferenceInjector.onePerPartner` for the record — key on the ACTIVE-ORDER entry it resolves, falling back to the case-folded `partnerLabel` for the dataset tail (#190 item 2). Do not key either of them on the label alone (two names of one order become two notes beside one chip — `warfarin`/`coumadin`, #136) and do not resolve a partner across the whole dataset instead: that merges genuinely distinct partners on 397 of the 2283 entries (`trastuzumab` with `trastuzumab deruxtecan`), which in a record costs a partner its name (#188). The bound is what makes this safe — resolution is against the patient's own orders, so wherever it merges two labels the chip merged them first.
- **Which collapse unit a contraindication rule is on**: Use `DrugSafetyValidator.contraindicationFinding()`, and `selfNamedAllergyRule()` for the one question it turns on. The chip ledger (`ContraindicationChips`) and `DrugReferenceInjector.contraindicationSections` key on it precisely so one recorded allergy cannot be one chip and two clauses (#190 item 1). A rule's key is its normalized `(type, token)` — **except** an ALLERGY rule whose token is one of the subject entry's own names, which reports the allergen arm's fact and is keyed on the SUBSTANCE so the two fold into one chip (#146; 3 of the 4 entries in the shipped curated file have that shape and every one of them double-reported a single allergy on the default `sourceFormat=json`). Which of the two wordings survives is decided by CONTENT and never by arm — a rule carrying an operator-authored note outranks identity, a rule carrying none renders its own token back and is outranked by every relationship — because #88 settled that "arm X yields to arm Y" is the wrong dedup whenever the yielding arm can be the one carrying the content. **The self-naming test is `DrugReference.isNamed`, never `findImpliedSubstances`.** Both operands are canonical REFERENCE strings (a curated token against an entry's own alias list), so the question is name identity, and the widening the bullets above make deliberate for a RECORDED name is exactly what must not reach here: a curated token may name a CLASS (`nsaid`, `aminoglycoside`), and resolving tokens to entries wholesale collapses a class-level rule into an identity chip — a different and worse defect, which is why #160 declined to introduce it. What bounds the fold to its own subject is not the predicate (`isNamed` is true of every entry aliasing the token) but that it is asked OF the entry the rule is filed on. Never re-derive either method at a call site: a second copy is how the chip and the record came apart the first time this key moved, and they did so silently — the model simply reads one contraindication more than the deterministic layer found.
- **Whether an injected record may state what THIS patient's chart records**: three questions, three predicates, and the whole entry exists because conflating any two of them produces a confident false statement in citable evidence (#208 item 2 — three of the four defects a review pass found in that change were this one shape). **Does the chart record it?** `DrugSafetyValidator.recordedContraindicationKind()`, the chip arm's own match, shared and never copied for the reason `contraindicationFinding` is. **Could the module even ask?** `DrugSafetyValidator.evaluatesAgainstTheChart()` — a rule typed neither `allergy` nor `condition`, or carrying no token, is unaskable, and its token half is the matcher's own emptiness rule (`PatientClinicalContext.matchableToken`, extracted from `containsToken` so "not matchable" and "did not match" cannot drift). **Was the chart read at all?** `PatientClinicalContext.contraindicationRecordsRead()`, set false by `PatientClinicalContextBuilder`'s own catch blocks: **a chart the module could not read is not a chart that records nothing.** That last one is the same failure class as #178's constant log and #242's silent zero-entry parse, and it is the one that bites hardest here, because the builder swallows a failed allergy or condition read into an EMPTY set — right for a chip, which must not raise what it cannot substantiate, and wrong for a record that would then tell the model this patient records none of a drug's contraindications *because nobody looked*. The composed gate is `DrugReferenceInjector.statesTheChartsContraindicationReading`, which also requires `DrugSafetyValidator.reportsContraindications()` (both `drugSafety` toggles) because the reading is the record's half of a chip and must not outlive one, and it is decided ONCE per injection so two records of one chart cannot disagree. **The rule under all of it: never render silence as denial.** A negative claim needs all three answers; a chip needs only the first, which is why the chip arm can treat one null as "stay silent" and a record cannot.
- **Which co-medications the class arm reasons about**: `DrugSafetyValidator.orderPartners()`, and its answer is the patient's **whole** active-order list — never the subset a concept dictionary happened to classify. It walks `getActiveDrugAtcCodes()`, and then `addPartnersForUnmappedOrders` takes the orders no walked code reached and resolves them by NAME through `findImpliedByDrugName` (the ranked accessor: unranked, one `Hydrocortisone Injection vial 100mg` becomes TWO co-medications, the second an ester the patient is not on). That second leg is #228, and it is not optional because the sparsity is the DICTIONARY's and never the reference data's — measured 2026-08-13 by SQL applying `PatientClinicalContextBuilder.addAtcCodes`' own predicate, **27 of the 43 active drug orders on the 3.7.1 standalone carry no ATC code**, while `DrugReference.normalizedAtcCodes()` over the real `DdiDrugReferenceSource.parse` of the 19 MB KB publishes codes for 1839 of its 2283 entries. The arm was therefore blind on the MAJORITY of prescriptions, silently: no chip, no log line, nothing separating "no duplicate therapy" from "could not look". Through the real `validate` over that KB and the standalone's own order sets, **14 partners → 42, and patients with at least one partner 12 of 24 → 24 of 24**. Two rules bind anything added here and **each was a defect that shipped green** — the suite caught neither until a mutation did. **The exact-code leg of the restating-existing-therapy skip applies ONLY where the partner's codes are the CHART's** (`OrderPartner.codesFromDataset`): that leg is a PROXY for identity kept for the case identity cannot reach, and on a partner reached by NAME the codes are the DATASET's, so it would be asking whether two reference rows share a code — which this KB says is not identity, and is the reason `substanceKey` exists. `Omeprazole` and `Esomeprazole` publish one `A02BC05` between them, so unscoped the leg silences exactly the chip #228 adds: a patient on omeprazole, asked about a genuinely different PPI, hears nothing. Scoping it is also what makes the partner's own-substance key load-bearing — before, deleting that line left every test green. **And the cross-leg dedup is `alreadyACoMedication`, never a map lookup**: the walk keys some partners on the ORDER and some on the SUBSTANCE, so a substance-key lookup cannot see the first kind, and a mapped `Omeprazole 20mg` beside an unmapped `Omeprazole capsule` became two co-medications under two names — the one-substance-named-two-ways failure #145/#162/#174 keep having to remove.
- **Whether a co-medication IS the drug being asked about**: the restating-existing-therapy skip in `DrugSafetyValidator.classRelationships`, and it is TWO tests OR-ed with neither removable. Substance identity is the question — `DrugReference.substanceGroupKey()` against `OrderPartner.substances` — because deciding it by codes alone was #185: the KB's `Omeprazole` row publishes only esomeprazole's `A02BC05` and omeprazole's own `A02BC01` appears nowhere, so an omeprazole order was reported as duplicating itself. The shared-exact-code leg stays beside it for the case identity cannot reach, and since #228 applies ONLY there (`OrderPartner.codesFromDataset` — see the bullet above for why a name-reached partner is not that case) — a context carrying only the flattened code set (#118) has no order to name the partner, so the code is all there is; **six pre-existing tests go red without it**, because an order known only as `A02BC05` resolves to `Omeprazole`, whose substance is not `Esomeprazole`'s, and dropping the leg raises a chip this arm has never raised. `resolvesFrom`'s javadoc explains why that same over-skip is safe THERE and does not transfer here.
- **What a co-medication is known to contain**: `OrderPartner.substances`, populated on exactly ONE rung — inside `orderPartners`' `unnameableCode && order != null` branch, beside `nameByOrder`, and over EVERY order `ordersCarrying` returns rather than the first. Both halves of that scoping were got wrong once each while writing #185 and **both mistakes passed the entire suite**, which is why this is here. Widening it to every partner an order produced silences a chip that NAMES one: an order mapped to two covered codes is two partners, and a question about the first constituent then loses the second (`Metronidazole and secnidazole`) — the inverse of the defect. Narrowing the read to the partner's `namedByOrder` flag, or to the first carrier only, makes a suppression depend on the sequence `OrderService` returned the prescriptions in. The names are read through `DrugReferenceService.findImpliedByDrugName` and never the unranked matcher underneath it: this decides which chips are SILENCED, and unranked it reaches a second substance (#209's `Hydrocortisone Injection vial 100mg` reaching `Hydrocortisone butyrate`) whose own duplicate-therapy chip must survive.
- **Chart assembly**: Use `ChartBuildingStrategy.buildChart()` → `QueryStoreChartBuilder.build()`. Never fetch or serialize a patient chart by another path; querystore owns retrieval.
- **Which chart-assembly mode produced an answer**: Use `ChartBuildingStrategy.searchModeLabel(chart)`, and read it off the answer as `ChartAnswer.getSearchMode()`. Never re-derive it at a consumer from `chartsearchai.chartMode` or `chartsearchai.embedding.preFilter` — that was #178, where both audit-write sites branched on preFilter alone, so `queryScoped` (the shipped `CHART_MODE_DEFAULT`) could not reach the `search_mode` column at all. Measured on the standalone before the fix: **6036 rows, every one `full-chart`, no other value ever written** — a maintainer reading them to reconstruct what a clinician was shown was reading a constant. The label is computed from `PatientChart`'s own stamps (`isQueryScoped()`, `isPreFiltered()`), never a fresh GP read, for the reason `markQueryScoped` exists: a re-read can disagree with the read that built the chart, and it also means labelling needs no `Context`. Two consequences bind anything added here. Every stamp must be carried across `DrugReferenceInjector.injectRecords`, which rebuilds the chart from scratch — a dropped stamp is lost silently and **fail-open** (it reads as unstamped), which has happened twice. And `SEARCH_MODE_QUERY_SCOPED` is defined AS `CHART_MODE_QUERY_SCOPED`, so renaming that GP token silently rewrites every subsequent row for readers outside this module; the four spellings are pinned as literals in `ChartSearchAiAuditSearchModeTest` precisely because every other assertion compares a constant to itself and cannot see a rename.
- **Test datasets**: Use `TestDatasetHelper.FULL_PATIENT_DATASET`, `TestDatasetHelper.SECOND_PATIENT_DATASET`, `TestDatasetHelper.toSerializedRecords()`, `TestDatasetHelper.inferResourceType()`, `TestDatasetHelper.stripDatasetPrefixAndDate()`. Never duplicate these helpers in individual test files.
- **Category hints in tests**: Use `TestDatasetHelper.FULL_DATASET_CATEGORY_HINTS` (and per-dataset variants). Never duplicate hints maps in individual test files.
- **Stripping category hints**: Use `ChartSearchAiUtils.stripCategoryHints()`. Never reimplement the hint-detection pattern.
- **Saying an absent-data answer may name its topic two ways**: put the alternatives in `expectedAnswerContainsAny` (OR). **Never add a second element to `expectedAnswerContains` for that** — it is AND, so a second element makes the case stricter, which is the opposite of what a second correct name needs (#216). Neither list is the place to accommodate a wording you have not measured: an OR element is a new way to pass, and `AbsentDataEvalTest.anAnswerNamingNoTopicFailsEveryCaseThatNamesOne` reddens if one is loose enough to match an answer that names nothing. Where a single stem covers the variants (`smok`, `vaccin`) that stem in the AND list is the narrower expression and stays.
- **Inline citation markers**: `ChartSearchAiUtils.INLINE_CITATION` is the single parsing pattern and is deliberately single-index. Compact shorthand (`[6, 7]`, `[6/7]`) is normalized upstream by `LlmAnswerExtractor.normalizeSlashCitations(text, citations)` and ONLY when the structured citations array corroborates the group — never loosen the pattern or split bracket groups elsewhere; uncorroborated numeric brackets are clinical values (`[120, 80]`) and splitting them fabricates references.
- **Reading an index out of the structured `citations` field**: a different question from the one above, answered by `LlmAnswerExtractor.citationIndex()` — an integral JSON number, or a string that is entirely one integer (#219: the json_schema is enforced by the server, so a remote that approximates it can send `["9","10"]`, and an `isInt()` check dropped that in silence). The asymmetry with prose is deliberate and neither side may cite the other to widen itself: an array entry has no competing reading, so its TYPE is coerced and the coercion is reported at WARN, while a bracket in answer text can always be a clinical value, so it is not re-read. The widening is over types only — which VALUES are admitted is unchanged, and `LlmInferenceService.extractCitedReferences` remains the only thing that decides which indices become references. **The same accessor also reads the whole field when it is not an array** (#221, via `readNonArrayCitations`): that is deliberate, and the point of it — container and entries must admit exactly the same JSON types, and routing both through one reader is what stops them drifting apart. Do not give the container a rule of its own.
- **Whether a non-conformant `citations` field is reported**: it is, at WARN, in both shapes — an array whose entries misbehave (`reportNonConformantCitations`) and a container that is not an array at all (`readNonArrayCitations`). Two channels for one failure was the inconsistency, not the warning; #221's first draft logged the container at DEBUG on an "unobserved shape" argument that does not apply, since the branch cannot run unless a provider really did send an unusable field, and the default `org.openmrs.*` level is WARN so DEBUG is evidence for someone already looking rather than a signal that arrives. **The one silent case is an explicit `null`, and the reason is not "it is not an array".** It is what the container ASSERTS: `null` asserts ABSENCE — the same statement as an omitted field, from a provider whose answer cites nothing — so nothing is lost and nothing is guessed. Everything reaching `readNonArrayCitations` asserts PRESENCE of something unusable. Absence honoured is not a defect; presence discarded is. Do not fold the two on the strength of both being non-arrays.
