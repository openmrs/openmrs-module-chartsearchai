# Rules

- When a test fails, fix the pipeline/production code — never weaken assertions, revert test data, or change expected values to match wrong behavior.
- Prefer root-cause fixes over incremental symptom patches. Diagnose *why* something is broken before proposing a fix. Start with the best solution, not the quickest.
- Before claiming the filter is correct, verify what it actually returns — check the records, not just the count or the final answer. A filter returning 32 irrelevant records is not correct even if the LLM produces the right answer from them.
- Do not go in circles analyzing a problem without fixing it.
- Tests must call the actual production pipeline — no simulations, mocks, or reimplementations of pipeline logic in test code. This includes unit tests for internal methods: do not call internal methods directly with hand-crafted inputs. Every test must exercise the full production code path using real data (e.g. the patient test datasets and the real querystore-backed retrieval path).
- **Never re-express a production predicate in a script that measures the knowledge base for a figure you will quote** in javadoc, a PR body or an issue. Compile against the built jar or drive the real code through a throwaway test, and say which method produced any figure you record. `substanceKey`, `normalizeAtcToken`, `isLocallyAppliedAtcCode`, `containsBoundedToken` and `canonicalRow` carry accumulated special cases a fresh implementation quietly drops, so a script that is 98% right produces plausible numbers that are wrong in exactly the tail being investigated (measured 2026-08-07 — a Python reimplementation of `substanceKey` disagreed with production on family counts; #191).
- **Quote the figure the system already recorded, and where you must derive one, say what produced it and what it is a share OF — wherever it is published, a page or a report included.** #243 records the knowledge-base form of this; the same error reached a measurement of the pipeline's own transcripts on 2026-09-02, where a cost recomputed from published per-token rates was published beside the value the sessions themselves record, and its gap was then stated over the derived base rather than the recorded one.
- When a multi-step pipeline exists (e.g. normalize → transform → embed), tests must call the composed production method, not manually chain the individual steps. Manually chaining steps in tests can mask bugs where the production code assembles the pipeline differently. If no composed method exists, extract one and use it from both production and test code.
- Tests are the specification. Modifying tests to make them pass is changing the spec — only fix the production code to satisfy the existing tests.
- Before presenting changes, review your own diff multiple times. On each pass, check every item below. Keep reviewing until a pass finds nothing to fix.
  1. Does the change match the plan?
  2. Is the logic correct — edge cases, off-by-one errors, null/empty handling?
  3. Are there any regressions — does existing behavior stay intact?
  4. Is anything missing — incomplete implementation, forgotten call sites?
  5. Does it use the real production pipeline, not a simulation or mock?
  6. Were any tests modified? If so, that's a rule violation — revert and fix the production code instead.
  7. Were all rules followed — this file's, and those of every nested instruction file
     covering code the change touches?
- Follow test-driven development: for every bug fix or new feature, first write a failing test that defines the expected behavior, then write production code to make it pass. Write the strictest assertion — if it doesn't fail, tighten it until it does.
- Always create a plan before writing code. Read the relevant code, outline the approach, then implement.
- Never commit code with known regressions. When a change fixes one case but breaks another, the root cause is usually in shared infrastructure, not the individual call site — diagnose the shared problem before patching stages.
- Retrieval is owned by openmrs-module-querystore (issue #51). chartsearchai no longer has an in-process embedding/Lucene/Elasticsearch pipeline, scoring/ranking code, an embedding store, or a retrieval eval harness — do not reintroduce them. Retrieval changes *and retrieval-quality evaluation* belong in the querystore module (it owns the index and the e5-base-v2 embedder), not here.
- **Keep Bash output scoped — it is context, and the tail dominates.** Measured over one full `resolve-ticket` run, 33 of 329 Bash calls produced 52% of all output. Never `cat` a file you are about to grep; scope every recursive grep to `api/src`/`omod/src` and never to `.`; report a build as its FAILURES plus a computed total rather than every `Tests run:` line. **This rule does not reach reading production code** — file-region reads were the largest category and are where the findings came from. Trim the overhead, never the reading.
- **The drug-reference and drug-safety rules are NOT in this file.** They are in `api/src/main/java/org/openmrs/module/chartsearchai/reference/CLAUDE.md`, beside the code they bind. Read that file in full before changing anything in that directory. Do not wait to be handed it: whether a tool loads a nested instruction file on its own varies by tool and by how the files are reached, and a session that greps and edits through shell commands may never open that directory at all — so this is the instruction, not a convenience. Some of those rules also bind code OUTSIDE that directory: how a safety finding, a chip, an interaction-pair extent or the reference slice reaches the answer and the wire is decided in `LlmInferenceService` and `ChartSearchAiRestController`, so read it before changing those too.

# Documenting a decision

**This file is directives and pointers. The evidence lives in `docs/adr.md` and in javadoc.** It
was cut to that shape on 2026-08-31, because three copies of one argument is how this file came
to contradict itself, repeatedly, and how quoted figures went stale unnoticed. What that cut
measured, and where the reasoning it carried went, is `docs/adr.md` Appendix A.

So when you learn something worth keeping:

- **A rule someone must obey** — "use X, never Y" — belongs in the instructions: the directive,
  its issue number, and a pointer to the test that pins it.
  **The file is decided by the code the rule binds** — beside that code where it all sits in one
  directory, in this file where it binds several packages at once. One sentence per rule wherever a
  rule fits in one; where an entry point carries several, give each its own sub-bullet rather than
  a paragraph.
- **Why the rule is that way**, what was measured, what was tried and reverted, what a mutation
  reddens — belongs in the ADR decision, or in the javadoc of the method it constrains. Not here.
- **Do not publish a count that tracks the code.** A test-suite total, a per-mutation tally
  ("reddens exactly these N cases"), an exclusivity claim ("the rest of the suite is green") —
  every one of those has gone stale here, some within a single commit, and a stale one tells a
  maintainer the failure that mattered was collateral. State which named test a mutation reddens,
  name the residue, and stop. A figure that does NOT move with the code — an external fact, a
  past run's measurement, a structural partition — may stay, provided it carries what it is a
  count OF; where its force depends on a denominator, put it in the ADR with its date instead.
- **Do not restate an argument that already has a home.** Link the decision instead.

Most of that is enforced, over this file and every nested one: `ProjectInstructionsGuardTest`
fails the build on a suite total, an elided identifier, a cited symbol, path or ADR decision that
does not resolve, an unclosed code span or bold run, a nested instruction file this file does not name, a
file over its size budget, and one BULLET carrying more prose than its own budget — that last
measured without its trailing pointer run, so citing a test costs nothing. It cannot check
whether a rule is TRUE — only that its pointers land and its figures are not of the kind that rot.

A bullet over budget wants the split this section already prescribes: the imperative stays here,
the measurement and the refuted alternative move to the decision or javadoc it points at. Where
one entry point carries several rules, give each its own sub-bullet — that is the shape, not a
way to spend the budget twice.

# API surface rules — do not bypass these methods

**The largest group of these rules is not in this file.** The drug-reference and drug-safety subsystem carries its own, in `api/src/main/java/org/openmrs/module/chartsearchai/reference/CLAUDE.md`; read that file in full before changing anything in that directory. What remains below has no one directory to sit beside, each rule binding code in several packages at once; that is why it stayed, and it is not a claim that the rules over there bind only theirs.

These methods are the ONLY correct entry points for their respective operations. Do not reimplement their logic inline, call their internal helpers directly, or hardcode their output values. Where a bullet cites an ADR decision, that decision is canonical for the reasoning — including for alternatives already measured and rejected, which should not be re-proposed without new evidence.

## Text and vector helpers

- **Prefixed text**: Use `ChartSearchAiUtils.buildPrefixedText(resourceType, text)`. Never call `getEmbeddingPrefix()` directly (it is private) or hardcode prefix strings like `"Clinical observation: "`.
- **Cosine similarity**: Use `ChartSearchAiUtils.cosineSimilarity()`. Never reimplement the formula.

## Citations and grounding

- **Whether a citation may be grounding-verified**: Use `ChartSearchAiUtils.isGroundingDemoteOnly(type)`, a named view of `referenceGroup()`. For any question that is not about grading, ask `referenceGroup(type)` against `REFERENCE_GROUP_REFERENCE` directly — do NOT borrow this one, which NAMES a grounding rule. **Never test `resourceType` against `drug_reference`** — that is how `safety_finding` was graded as chart evidence for two releases (#122). **Mutate the site you are about to change and read the failures.** #354 added a THIRD reference-group type, which is what these guards were waiting for — but what each site reddens differs, and three successive attempts to write that mapping down here were each falsified by the next measurement, so no mapping is published. Do not assume a site is covered because a neighbour is, and note that `ReferenceProseFidelityCheck`'s own gate is still unguarded, which the third type did not change. The wire serializer is guarded separately (next bullet). The same rule binds consumers of the wire format — `README.md` requires a client to treat every `group=reference` citation alike, and the reference frontend still keys its badge, label and chart-tab route off `resourceType`, so that half of #201 is a change in `openmrs-esm-chartsearchai`.
- **Whether a grounding verdict may be PUBLISHED**: `ChartSearchAiRestController.groundedForWire()` is the ONLY place a `grounded` value reaches the wire. A `reference`-group citation always serializes `null` — never `true`, never `false` (#201) — because only `group` tells "this citation is not about that record" apart from "this claim may not be supported", and a client reading it as the latter rendered a deterministic Major-interaction finding as *Unsupported*, in red. Never publish `ref.getGrounded()` directly, and never re-derive the carve-out from a type name. → `ChartSearchAiReferenceGroundingWithholdingTest.theWireSerializerMustNotNameAReferenceGroupResourceType` (scope is exactly the controller's own class files; a hardcode elsewhere is invisible).
- **Where one sentence ends and the next begins**: ONE terminator set, `ChartSearchAiUtils.SENTENCE_TERMINATORS`, and three questions over it, each with its own entry point — `SENTENCE_BOUNDARY` SPLITS a text into units, `mayEndASentence` asks whether a sentence COULD have ended in one GAP (`ReferenceProseFidelityCheck`, #337), `DrugSafetyValidator.endSentence` asks whether a string already ends one. **Never a fourth regex or a character literal at a call site** (#260's shape). The two prose questions are not interchangeable and the difference is load-bearing both ways: the splitter is strict (terminator followed IMMEDIATELY by whitespace); the gap question is weak (terminator ANYWHERE in the gap) because both its uses are silencing. The set is interpolated through `Pattern.quote` so it can be edited as a SET. Shrinking it is the silent failure, which is why `ReferenceProseFidelityTest.everyWayASentenceCanEndInTheSharedRuleEndsAnAnswerSentence` spells the members out as LITERALS rather than iterating the constant.
- **Whether the answer's rendering of a cited reference record is faithful**: `ReferenceProseFidelityCheck` (#337) reports, at WARN, an answer that reproduces at least `MIN_REPRODUCED_WORDS` consecutive words of a cited reference-group record and then states different words inside the sentence it was reproducing. It scopes itself with `ChartSearchAiUtils.referenceGroup` and never a type name. **The `safetyWarnings` chips are NOT that check and never were** — they carry the deterministic text but are an independent list nothing reconciles against the answer. Do not restate that claim anywhere: say what checks it (`ClassCodeFidelityCheck` for an ATC token, this one for prose) or link the decision. **Sweep the CLAIM in several phrasings, over comments as well as docs** — one sweep was defeated by a wording carrying none of its search tokens, the next by an enumeration that said "in its javadoc" and so scoped itself out of a line comment. → ADR Decision 61.
  - **Its answer is PUBLISHED** (#337 round two): `ChartAnswer.getUnfaithfullyRenderedCitations()`, the `unfaithfullyRenderedCitations` key — the CITATION and never a word of either text. Resolved ONCE at the check's own call site, never re-derived at a consumer. `null` is no measurement, `[]` a measurement of none, and `[]` is **not** a certificate of faithfulness. **Do not move the check ahead of `searchStreaming`'s ungrounded handoff.** `ClassCodeFidelityCheck` publishes nothing, deliberately. → ADR Decision 74; `ChartSearchAiUnfaithfulRenderingTest`.
- **Whether a chart citation can be the ACTIVE ORDER its sentence names**: `ActiveOrderCitationFidelityCheck` (#377) reports, at WARN, a chart-group citation in the marker RUN after `DrugSafetyValidator.ACTIVE_ORDER_INTERACTION_PHRASE` whose type `ChartSearchAiUtils.mayDescribeAMedicationOrder` refuses, or whose `RecordMapping.getOrderActive()` is `FALSE`. **The unit is that run and never the sentence** — the issue's own answer states five findings in one, two of them cited correctly. The predicate is an ALLOW-LIST, so an undeclared type is REPORTED. **Its answer is PUBLISHED** — `ChartAnswer.getMisattributedOrderCitations()`, the `misattributedOrderCitations` key: `null` is no measurement, `[]` a measurement of none and **not** a certificate. It tests what a record CAN be, never which order the finding came from. → ADR Decision 75; `ActiveOrderCitationFidelityTest`, `MedicationOrderRecordTypeTest`.
- **Inline citation markers**: `ChartSearchAiUtils.INLINE_CITATION` is the single parsing pattern and is deliberately single-index. Compact shorthand (`[6, 7]`, `[6/7]`) is normalized upstream by `LlmAnswerExtractor.normalizeSlashCitations(text, citations)` and ONLY when the structured citations array corroborates the group — never loosen the pattern or split bracket groups elsewhere; uncorroborated numeric brackets are clinical values (`[120, 80]`) and splitting them fabricates references. **Decoding a marker to an INDEX is `ChartSearchAiUtils.citedIndexes`**; reading the pattern directly is for callers needing something a set of indexes cannot carry — each marker's text offset, or the text with markers removed. **And an index is not a citation until the answer's own resolution admits it** — that check intersects what it decodes with the list `extractCitedReferences` produced, which promotes every IN-RANGE bracketed integer, so what the intersection excludes is a number the chart has no record for. → ADR Decision 59; `ArchitectureGuardTest.classCodeFidelityCheckReachesMarkersOnlyThroughTheSharedDecodeStep` (CLASS-scoped, a source-text check, so a hand-rolled dialect written BESIDE a retained call is out of its reach).
- **Reading an index out of the structured `citations` field**: `LlmAnswerExtractor.citationIndex()` — an integral JSON number, or a string that is entirely one integer (#219: the json_schema is server-enforced, so a remote that approximates it can send `["9","10"]`). The asymmetry with prose is deliberate and neither side may cite the other to widen itself: an array entry has no competing reading so its TYPE is coerced and reported at WARN, while a bracket in answer text can always be a clinical value. The widening is over types only; `LlmInferenceService.extractCitedReferences` remains the only thing deciding which indices become references. The same accessor also reads the whole field when it is not an array (#221, via `readNonArrayCitations`) — container and entries must admit the same JSON types, and routing both through one reader is what stops them drifting. Do not give the container a rule of its own.
- **Whether a non-conformant `citations` field is reported**: it is, at WARN, in both shapes — an array whose entries misbehave (`reportNonConformantCitations`) and a container that is not an array (`readNonArrayCitations`). Two channels for one failure was the inconsistency, not the warning. **The one silent case is an explicit `null`, and the reason is not "it is not an array"** — it is what the container ASSERTS: `null` asserts ABSENCE, the same statement as an omitted field, so nothing is lost and nothing is guessed. Everything reaching `readNonArrayCitations` asserts PRESENCE of something unusable. Absence honoured is not a defect; presence discarded is. Do not fold the two on the strength of both being non-arrays.

## Chart assembly

- **Chart assembly**: Use `ChartBuildingStrategy.buildChart()` → `QueryStoreChartBuilder.build()`. Never fetch or serialize a patient chart by another path; querystore owns retrieval.
- **Which chart-assembly mode produced an answer**: `ChartBuildingStrategy.searchModeLabel(chart)`, read off the answer as `ChartAnswer.getSearchMode()`. Never re-derive it at a consumer from `chartsearchai.chartMode` or `chartsearchai.embedding.preFilter` — that was #178, where both audit-write sites branched on preFilter alone, so the shipped `CHART_MODE_DEFAULT` could not reach the `search_mode` column at all and a maintainer reading those rows was reading a constant. The label is computed from `PatientChart`'s own stamps (`isQueryScoped()`, `isPreFiltered()`), never a fresh GP read, which also means labelling needs no `Context`. Two consequences: every stamp must be carried across `DrugReferenceInjector.injectRecords`, which rebuilds the chart from scratch — a dropped stamp is lost silently and **fail-open**, which has happened twice; and `SEARCH_MODE_QUERY_SCOPED` is defined AS `CHART_MODE_QUERY_SCOPED`, so renaming that GP token silently rewrites every subsequent row for readers outside this module. → `ChartSearchAiAuditSearchModeTest` pins the four spellings as literals, because every other assertion compares a constant to itself.
- **Whether a chart record's drug order is still in force**: `SerializedRecord.getOrderActive()` — and `PatientChartSerializer.RecordMapping.getOrderActive()` where a consumer reads a built chart. Written in exactly ONE place, `QueryStoreChartBuilder.toSerializedRecords`, the funnel all three build paths share; never re-derive it, and in particular never from the rendered text. That was #317. 
  - **It is three-valued and the third value is the guard** — `TRUE` in force, `FALSE` this patient's order and not in force, `null` the module cannot say. 
  - **The situations `null` covers are enumerated in exactly ONE place — the `SerializedRecord.orderActive` field javadoc — and every other site, this one included, points at it rather than restating it.** Do not copy it here or into a decision; a second copy is a second thing to forget to update. Never collapse it to a boolean, and never read `isEmpty()` on an active-order set as "could not read" — an empty active set is a real and common state, and exactly the one the mark must fire on. It reads the patient's orders ONCE and keeps TWO sets out of that read: "absent from the active set" alone cannot tell an ended order from a record whose order the module cannot identify. 
  - **Evaluate each order in its own try** — `Order.isActive()` THROWS where `dateStopped` is after `autoExpireDate`, so one such row inside a chart-wide try silently takes the mark off every record for that patient. 
  - **`describesEndedOrder` is now AND-ed with this, never ranked against it** — neither overrules the other and each can only exclude more, which is what keeps the #118 name fallback intact. Do not "simplify" it into a precedence rule. Scoped to `drug_order` deliberately. Mutate the guards and read the failures. → ADR Decisions 46, 47.

## Tests and eval

- **Test datasets**: Use `TestDatasetHelper.FULL_PATIENT_DATASET`, `TestDatasetHelper.SECOND_PATIENT_DATASET`, `TestDatasetHelper.toSerializedRecords()`, `TestDatasetHelper.inferResourceType()`, `TestDatasetHelper.stripDatasetPrefixAndDate()`. Never duplicate these helpers in individual test files.
- **Category hints in tests**: Use `TestDatasetHelper.FULL_DATASET_CATEGORY_HINTS` (and per-dataset variants). Never duplicate hints maps in individual test files.
- **Stripping category hints**: Use `ChartSearchAiUtils.stripCategoryHints()`. Never reimplement the hint-detection pattern.
- **Saying an absent-data answer may name its topic two ways**: put the alternatives in `expectedAnswerContainsAny` (OR). **Never add a second element to `expectedAnswerContains` for that** — it is AND, so a second element makes the case stricter, the opposite of what a second correct name needs (#216). Neither list is the place to accommodate a wording you have not measured: an OR element is a new way to pass, and `AbsentDataEvalTest.anAnswerNamingNoTopicFailsEveryCaseThatNamesOne` reddens if one is loose enough to match an answer naming nothing. Where a single stem covers the variants (`smok`, `vaccin`) that stem in the AND list is the narrower expression and stays.
